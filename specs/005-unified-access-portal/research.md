# البحث والقرارات: بوابة الوصول الموحدة

## R1 — مكان البوابة الموحدة

**القرار:** `index.php` هو واجهة العرض العامة الموحدة، ويُستخرج جسم بطاقة الدخول إلى `includes/public_login_portal.php`. يبقى `login.php` مدخلاً متوافقاً لمعالجة الدخول والروابط القديمة.

**السبب:** يحافظ على الرابط العام والتصميم الحالي ولا يكرر منطق المصادقة.

**البدائل المرفوضة:**

- تحويل `index.php` بالكامل إلى `login.php`: يفقد التحكم بالمقدمة والخدمات العامة ويعرّض الشكل للتراجع.
- إنشاء تطبيق frontend مستقل: يخالف modular monolith ويضيف stack موازياً.

## R2 — إزالة المرحلة دون كسر التوافق

**القرار:** إزالة المرحلة من قرار المصادقة والعرض الجديد، مع قبول معاملات `stage` القديمة وإهمالها أو تحويلها إلى الوجهة الموحدة.

**السبب:** المرحلة خاصية تعليمية للحساب/المحتوى وليست عامل إثبات هوية، والروابط القديمة قد تبقى في bookmarks أو Teams.

## R3 — أسلوب Teams التلقائي

**القرار:** يطلب `teams/app.html` الرمز فور `microsoftTeams.app.initialize()` ويرسله إلى `auth/teams_token_handler.php` عبر POST same-origin. لا ينتظر رسالة `request_sso` من بطاقة الدخول.

**السبب:** يحقق الدخول دون نقرة، ويقلل postMessage، ويجعل fallback تحت تحكم الغلاف.

**البديل المرفوض:** الإبقاء على handshake الحالي الذي لا يبدأ إلا بعد ضغط زر Microsoft؛ لا يحقق المتطلب.

## R4 — قاعدة إثبات الحساب

**القرار:** نجاح Teams الصامت يتطلب في كل مرة:

1. token صحيحاً لمستأجر وجمهور معتمدين؛
2. Microsoft ID محلياً مرتبطاً؛
3. بريداً موثقاً من Microsoft؛
4. تطابق البريد الموثق مع `users.email`؛
5. تطابق البريد نفسه مع `users.username`؛
6. حساباً واحداً نشطاً ودوراً صالحاً.

تطبيع البريد يقتصر على trim وlowercase. Microsoft ID لا يتجاوز أي شرط.

**السبب:** يطبق شرط المستخدم عند تغير البريد ويمنع الارتباط الصامت الخاطئ.

## R5 — الربط التفاعلي مقابل الصامت

**القرار:** مسار Teams الصامت لا ينشئ أو يصلح الربط. زر Microsoft اليدوي يبقى خاضعاً لسياسة الربط الحالية، وأي تغيير فيها خارج النطاق.

**السبب:** الربط عملية ذات أثر أمني تحتاج تفاعلاً وسياسة مستقلة، ولا يجب أن تحدث كأثر جانبي لفتح tab.

## R6 — نموذج الضيف

**القرار النهائي:** ألغي نموذج الضيف بالكامل. لا صف مستخدم ولا دور session ولا كتالوج ولا صفحة خدمات. `guest.php` تحويل توافق إلى المواد فقط.

**السبب:** يمنع تسرب صلاحيات الأدوار وopen redirects والمحتوى العشوائي.

**البديل المرفوض:** إنشاء مستخدم مشترك باسم Guest؛ يخلط التدقيق والجلسات ويزيد خطر التصعيد.

## R7 — نشر المواد

**القرار المنفذ:** أعيد استخدام حقلي `materials.enabled` و`materials.downloadable` الموجودين. لا تظهر في القائمة العامة إلا المادة المفعلة والمرتبطة بمرحلة وصف نشطين، ولا يسمح endpoint التنزيل إلا عندما تكون المادة مفعلة وقابلة للتنزيل والخدمة العامة نفسها مفعلة. لم تُنشأ migration أو projection جديدة.

**الدليل:** مركز المواد الحالي يكتب `enabled` و`downloadable`، ومسار `LegacyMaterialCatalogAdapter` يفرضهما في الاستعلامات، بينما `material_download.php` يعيد فحصهما عند كل طلب ولا يعرض مسار التخزين في القائمة.

**الحد النهائي:** `enabled` هو قرار ظهور المادة نفسه للطالب والزائر، و`downloadable` قرار التنزيل. لا يوجد إعداد خدمة أو علم نشر عام مستقل.

## R8 — فرض إتاحة الخدمة

**القرار النهائي:** الواجهة ليست حاجز الأمان. `material_download.php` يعيد فحص المادة والمرحلة والصف و`enabled/downloadable` والمسار الحقيقي وقت الطلب؛ `materials.php` بوابة تحويل للمقدمة فقط.

## R9 — سياسة المقدمة

**القرار:** cookie first-party يحمل وقت آخر عرض معتمد لمدة 15 يوماً، مع session fallback. لا يحتوي cookie بيانات هوية. وجهة العودة code ثابت مثل `portal` أو `materials` تُترجم إلى مسار allow-listed.

**السبب:** القرار يحدث قبل عرض الصفحة، وlocalStorage وحده لا يكفي لتحويل خادمي آمن.

**البديل المرفوض:** `return_url` خام؛ يخلق open redirect.

## R10 — تخطي المقدمة في Teams

**القرار:** سياق Teams الموثوق يأتي من صفحة الغلاف ومسار معروف، مع الحفاظ على `from_teams=1` توافقياً. لا يمنح هذا المعامل هوية أو صلاحية؛ تأثيره الوحيد تخطي الفيديو وطريقة العرض.

## R11 — بيئات Microsoft SSO

**القرار:** البناء الحالي لاختيار local/production callback هو الأساس ويُختبر، ولا تُصلح أخطاء `AADSTS50011` بالتحويل القسري إلى production. يجب تسجيل URI المحلي والإنتاجي في Entra.

**السبب:** Redirect URI عقد ثلاثي بين الطلب و`.env` وEntra Portal، ومطابقته حرفية.

## R12 — رسائل تعطيل الحساب

**القرار:** إعادة استخدام سياسة AccountAccess/التعطيل الحالية وإضافة regression matrix فقط. السبب المخصص غير الفارغ يظهر كنص الأدمن وحده؛ السبب الفارغ يعرض الرسالة العامة وحدها.

**السبب:** القاعدة نُفذت بالفعل في العمل الحالي ولا ينبغي إنشاء فرع رسائل داخل بوابة أو SSO.

## R13 — الواجهة البصرية

**القرار:** الحفاظ على logo/background/footer/dark mode والحركة الحالية، ودمج بطاقة الدخول دون أسماء مراحل. تُنقل قواعد CSS الجديدة إلى `assets/css/public-portal.css` ويستمر `buttons.css` مرجع الأزرار.

**السبب:** يحقق الحفاظ البصري ويلتزم بمركزية CSS.

## R14 — الأعلام والتراجع

**القرار:** علم للبوابة الموحدة وعلم مستقل لـTeams auto SSO. عند إيقاف علم البوابة يعاد توجيه المدخل العام إلى `public_portal.php` القديم، وعند تفعيله تصبح الروابط القديمة adapters إلى المدخل الموحد. لا توجد schema جديدة لهذه الميزة.

**السبب:** يمكن إيقاف الجزء الخطر دون فقد الإعدادات أو تعطيل الدخول اليدوي.

## R15 — التدقيق والذرية

**القرار النهائي:** لا توجد كتابة لإعداد خدمات ضيف. تظل كتابة `enabled/downloadable` وتدقيقها لدى مركز المواد الحالي، ولا تضيف PublicPortal مسار كتابة ثانياً.

## أسئلة تم حسمها

- هل تظهر رسالة عامة مع السبب المخصص؟ **لا؛ المخصص وحده.**
- هل ينطبق التعطيل على الفردي والجماعي وكل طرق الدخول؟ **نعم.**
- هل تغير البريد لدى Microsoft يُسمح له بالمرور عبر Microsoft ID؟ **لا.**
- هل الحساب غير المرتبط يدخل تلقائياً من Teams؟ **لا؛ يرى البوابة.**
- هل المقدمة تظهر داخل Teams؟ **لا.**
- هل تظهر عند رابط المواد لأول مرة؟ **نعم، ثم تعود للمواد.**
- هل توجد روابط يضيفها الأدمن للضيف؟ **لا؛ وضع الضيف ملغى وزر المواد ثابت.**
