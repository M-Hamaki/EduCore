# دليل التحقق التشغيلي للخطة

هذا الدليل يحدد كيف يُثبت التنفيذ المستقبلي صحة المنظومة قبل تفعيلها. لا يُشغَّل حاليًا على قاعدة `educore`.

## 1. متطلبات البيئة

- قاعدة معزولة باسم ينتهي بـ `_test`.
- نسخة بيانات مصغرة منزوعة الحساسية أو seed مخصص.
- جميع feature flags الجديدة في `off` افتراضيًا.
- أجهزة/ملفات بصمة اختبارية فقط.
- مستخدمون ممثلون:
  - عامل عادي.
  - مدير مباشر.
  - مدير إداري.
  - مدير إضافي.
  - HR محدود النطاق.
  - Finance maker/checker.
  - Super Admin.
- تقويم اختبار يتضمن يوم عمل وعطلة ويومًا جزئيًا ووردية ليلية.

## 2. بيانات السيناريو المرجعية

| الرمز | الوصف |
|---|---|
| A | عامل ضمن قوة «الإدارة»، مسمى «سكرتير»، ومجموعة «وردية صباحية» |
| B | عامل له تخصيص فردي يعلو قواعد المجموعة والمسمى والقوة |
| M1 | المدير المباشر لـ A |
| M2 | المدير الإداري |
| M3 | مدير إضافي بالمرحلة الثالثة |
| P1 | سياسة عامة 07:30–14:30 |
| P2 | سياسة القوة 08:00–15:00 |
| P3 | سياسة المجموعة 07:00–14:00 |
| P4 | تخصيص B الفردي 09:00–16:00 |

## 3. بوابات قبل أي اختبار

1. مراجعة `git status` وعزل ملفات التنفيذ عن عمل المستخدم الحالي.
2. التحقق أن DSN يشير إلى `_test` وإيقاف الاختبار إذا لم يفعل.
3. تشغيل migrations الإضافية فقط، دون `DROP/TRUNCATE` للمصادر القديمة.
4. تشغيل:
   - `composer audit-write-coverage`
   - الاختبارات العقدية المركزة
   - `composer architecture-audit`
5. فشل أي سياسة تدقيق أو رفع ملفات أو حماية داخلية يمنع المتابعة.

## 4. سيناريوهات القبول

### Q01 — أولوية الدوام

1. انشر P1 عامة وP2 للقوة وP3 للمجموعة وP4 للعامل B.
2. احسب دوام A وB في يوم السريان.
3. المتوقع:
   - A يأخذ P3.
   - B يأخذ P4.
   - النتيجة تحفظ سبب الاختيار والنسخة.
4. أنشئ تعارضًا متساويًا في المجموعة؛ يجب رفض النشر برسالة مفهومة.

### Q02 — التاريخ وعدم تغيير الماضي

1. احسب شهرًا بسياسة v1.
2. انشر v2 من أول الشهر التالي.
3. أعد فتح تقرير الشهر القديم.
4. المتوقع: يبقى v1؛ إعادة الحساب التاريخي لا تتم إلا بإجراء مدقق ومقصود.

### Q03 — وردية ليلية وتقويم

1. وردية 20:00–04:00.
2. بصمة 19:55 و04:03.
3. المتوقع: يوم عمل واحد بلا غياب أو انصراف مبكر.
4. يوم عطلة بلا بصمة لا يدخل مقام الغياب.

### Q04 — إذن حضور متأخر

1. دوام 07:30، إذن معتمد لمدة ساعتين حتى 09:30.
2. بصمة 09:00.
3. المتوقع: صفر تأخير محتسب.
4. غيّر البصمة إلى 10:00.
5. المتوقع: 30 دقيقة غير مغطاة، مع تفسير واضح.

### Q05 — إذن انصراف مبكر

1. نهاية الدوام 14:30، إذن من 12:00.
2. بصمة خروج 12:00.
3. المتوقع: صفر انصراف مبكر.
4. بصمة خروج 11:45.
5. المتوقع: 15 دقيقة غير مغطاة.

### Q06 — مأمورية وبصمات متعددة

1. دخول 07:25، خروج 10:00، عودة 12:00، خروج 14:30.
2. مأمورية 10:00–12:00.
3. المتوقع: لا نقص في الفترة، وتظهر المأمورية منفصلة عن الوجود.

### Q07 — بصمة ناقصة/مكررة/غير معروفة

1. أرسل الحدث نفسه مرتين؛ يُحفظ مرة واحدة.
2. أرسل رقم بصمة بلا mapping؛ يحفظ الخام كـ unmatched ولا ينسب لعامل خطأ.
3. أرسل بصمة دخول فقط؛ تظهر exception ولا تُختلق بصمة خروج.

### Q08 — اعتماد متعدد المراحل

1. العامل يقدم إذنًا.
2. لا يستطيع M2 القرار قبل M1 إذا كان المسار تسلسليًا.
3. يوافق M1 ثم M2 ثم M3.
4. المتوقع: الاعتماد النهائي فقط ينشر التغطية ويعيد حساب اليوم.
5. محاولة العامل أو مدير غير مسند القرار ترجع 403 ورسالة مجال.

### Q09 — التفويض وتعارض المصالح

1. أنشئ تفويضًا مؤقتًا لـ M1.
2. النائب يعتمد ويحفظ `acting_for`.
3. بعد انتهاء التفويض يُرفض القرار.
4. شكوى ضد M1 لا تظهر له وتتجاوز مرحلته.

### Q10 — سباق الحصة

1. اضبط الحد المتبقي على إذن واحد/60 دقيقة.
2. أرسل طلبين متزامنين كل منهما 60 دقيقة.
3. المتوقع: واحد يحجز وينجح، والآخر `QUOTA_EXCEEDED`.
4. رفض الأول يحرر الحصة، وتنجح إعادة تقديم الثاني.

### Q11 — الرصيد والإجازة

1. أنشئ opening balance وحركة استحقاق.
2. قدم طلبين متزامنين على آخر رصيد.
3. لا يسمح باستهلاك مزدوج.
4. اختبر إجازة عابرة لسنتين وعطلة ونصف يوم.
5. المتوقع: تفصيل الأيام والحركات حسب الفترة والسياسة.

### Q12 — المرفق الصحي

1. ارفع PDF صالحًا؛ يخزن خاصًا ولا يعرض URL مباشرًا.
2. جرّب MIME مخالفًا واسمًا مزدوج الامتداد وملفًا زائد الحجم.
3. يجب رفضها.
4. افشل كتابة DB بعد رفع ملف جديد؛ يجب إزالة الملف الجديد.

### Q13 — التأديب والتظلم

1. سجل واقعة وافتح قضية.
2. تحقق من فصل recorder/investigator/decider/appeal reviewer.
3. أصدر قرارًا وأخطر العامل ثم قدم تظلمًا.
4. القرار الأصلي يبقى، والنتيجة الجديدة تؤيده أو تعدله أو تلغيه.
5. أي خصم ينتقل كـ fact idempotent للمالية ولا ينشأ مرتين.

### Q14 — ارتق والسرية

1. العامل ينشئ شكوى ضد مديره ومقترحًا عاديًا.
2. الشكوى لا تظهر للمدير المشتكى ضده؛ المقترح يتبع مسار التصنيف.
3. Push يعرض نصًا محايدًا فقط.
4. مستخدم يملك URL بلا صلاحية يحصل على 403.
5. الرسائل والقرارات لا تُحذف ماديًا.

### Q15 — التقارير

أنشئ:

- تقرير فرد من فترة إلى فترة.
- تقرير قوة/مسمى/مجموعة.
- ملخص شهري غياب فقط.
- شهري غياب وأذونات.
- سنوي ونسبة غياب.

المتوقع:

- كل إجمالي قابل للانتقال إلى الأيام والأسباب.
- النسبة تعرض المقام: أيام العمل المؤهلة.
- العطلات والإجازات والمأموريات لا تختلط بالغياب غير المبرر.
- التقرير المقفل ثابت حتى إعادة فتح مدققة.
- CSV لا ينفذ قيمًا تبدأ بـ `=`, `+`, `-`, `@`.

### Q16 — الخدمة الذاتية متعددة الأدوار

1. سجل الدخول كمعلم لديه ملف عامل نشط.
2. تظهر خدمات العامل داخل بوابته دون تغيير دوره إلى employee.
3. لا يرى طلبات أو أرصدة عامل آخر بتغيير ID.

### Q17 — الرسائل المفهومة

اختبر duplicate، تجاوز الحصة، تداخل، نقص المرفق، تعارض النسخة، وفقد المدير.

المتوقع:

- رسالة عربية موجهة للمستخدم.
- لا SQLSTATE أو اسم index أو stack trace.
- سجل الخادم يحتفظ بالمرجع التقني الآمن للتشخيص.

### Q18 — إذن بلا حضور كافٍ

1. اعتمد إذن تأخير حتى 09:30 ولا تسجل أي بصمة دخول.
2. اعتمد إذن انصراف مبكر لعامل لا يملك بصمة دخول.
3. المتوقع: لا يصبح أي يوم حاضرًا أو بعذر كامل؛ تظهر حالة غياب/بصمة ناقصة وتغطية الإذن منفصلة.

### Q19 — اعتراض العامل وتصحيح الحضور

1. العامل يطلب مراجعة يوم ذي بصمة ناقصة مع سبب ومرفق.
2. لا يستطيع اعتماد طلبه أو تعديل الخام.
3. بعد اعتماد المراجع تُنشأ نسخة يوم جديدة تشير للقديمة وتظهر في التقرير كتعديل معتمد.

### Q20 — تضارب هوية البصمة والأحداث المتأخرة

1. حاول ربط رقم بصمة بعاملين خلال فترة واحدة؛ يجب الرفض.
2. أنهِ ربط العامل الأول وأعد الرقم لاحقًا للثاني؛ تظل الأحداث القديمة للأول.
3. أرسل أحداثًا قديمة بعد أحداث أحدث وبانحراف ساعة؛ تحفظ أوقات الجهاز والاستلام، ويعاد ترتيب الحساب دون تعديل الخام.
4. الحدث بعد الإقفال يدخل قائمة إعادة فتح ولا يغير الرسمي تلقائيًا.

### Q21 — الاستراحة والوردية المنقسمة والتبديل والعمل الإضافي

1. طبق وردية بمقطعين بينهما استراحة غير مدفوعة.
2. اعتمد تبديل وردية مؤقتًا بين عاملين وفق السياسة.
3. سجل وقتًا إضافيًا بلا اعتماد ثم باعتماد.
4. المتوقع: الاستراحة لا تعد نقصًا ولا عملًا، والتبديل يؤثر على أيامه فقط، والعمل الإضافي غير المعتمد لا ينشئ استحقاقًا.

### Q22 — وسيلة حضور بديلة

1. فعّل وسيلة بديلة لعامل يتعذر عليه استخدام البصمة مع مدة وسبب.
2. العامل لا يستطيع اعتماد تسجيله لنفسه.
3. بعد المراجعة يظهر الحدث كحضور بديل لا كبصمة جهاز، مع السبب والدليل.
4. بانتهاء صلاحية الاستثناء تُرفض محاولات التسجيل التالية.

### Q23 — actor مكرر ونصاب وتعادل

1. اجعل المدير نفسه محلولًا كمدير مباشر وإداري.
2. المتوقع: دمج أو بديل حسب السياسة، ولا يحتسب القرار مرتين.
3. اختبر مرحلة أغلبية بأصوات متعادلة ومرحلة `all` بها رفض واحد.
4. يجب تطبيق قاعدة التعادل/الرفض المنشورة، لا ترتيب وصول القرارات.

### Q24 — نقل أو انتهاء خدمة أثناء الطلب

1. قدم طلبًا مستقبليًا يبدأ بعد نقل العامل إلى قوة ومدير جديدين.
2. المتوقع: تثبت السياسة والمسار النافذان في تاريخ الاستحقاق.
3. أنهِ خدمة العامل أثناء طلب معلق.
4. يمنع الطلب الجديد، وينتقل المعلق حسب السياسة مع تحرير الحجز غير المستحق.
5. أبق جلسة العامل/المدير مفتوحة؛ أول طلب محمي تالٍ يجب أن يرفض الصلاحية المنتهية.

### Q25 — تعديل بعد الإقفال أو الرواتب

1. اقفل شهر الحضور وأرسل أثره إلى Finance.
2. اعتمد إذنًا متأخرًا أو ألغ إجازة أثرت في الشهر.
3. المتوقع: لا يتغير الرسمي أو الراتب صامتًا؛ ينشأ طلب إعادة فتح أو fact عكسي بمفتاح idempotency.
4. تكرار العملية لا يكرر الأثر المالي.

### Q26 — تصحيح تنظيمي بأثر رجعي

1. صحح قوة أو مسمى أو مديرًا أو عطلة في شهر سابق.
2. تعرض المعاينة العاملين والأيام والطلبات والتقارير المتأثرة.
3. بعد الاعتماد يعاد فقط النطاق المحدد، مع نسخ جديدة وأسباب.
4. الإلغاء يعيد القراءة للنسخة السابقة دون حذف التاريخ.

### Q27 — حد التشغيل وفترة حظر الإجازات

1. قدم عاملان طلبين متزامنين يهبطان بالقوة عن الحد الأدنى.
2. المتوقع: تمنع السياسة الاعتماد أو تطلب استثناءً من مخول.
3. اختبر فترة حظر واستثناءً مسببًا.
4. لا يتغير الرصيد إلا وفق حجز/استهلاك الطلب الفعلي.

### Q28 — شكوى عاجلة وجماعية وسحب

1. قدم شكوى خطر فوري ضد مدير داخل المسار.
2. تذهب مباشرة لفريق الحماية ولا تظهر للمدير أو في إشعار كاشف.
3. أضف عدة مشتكيـن ومشكو في حقهم واربط تذكرة مكررة دون نسخ المحتوى السري.
4. اطلب السحب بعد بدء تحقيق؛ يسجل الطلب ولا يمحى الأصل، ويقرر الفريق استمرار الالتزام الوقائي.

### Q29 — إجراء احترازي وإعادة فتح قضية

1. طبق إجراءً احترازيًا أثناء التحقيق بمدة ومراجع وموافقة.
2. لا يعرض كجزاء نهائي ولا يرسل خصمًا تلقائيًا.
3. أغلق القضية ثم أضف دليلًا جديدًا.
4. إعادة الفتح تحتاج مخولًا وتحفظ القرار السابق وكل الآثار العكسية.

### Q30 — استئناف الترحيل والكتابات أثناء التحويل

1. أوقف batch بعد checkpoint ثم شغله بالمفتاح نفسه.
2. المتوقع: يستأنف من موضعه دون تكرار.
3. افتح نافذة cutover بوضع `capture` أو `freeze` معلوم، ونفذ كتابة من المسار القديم.
4. يجب التقاطها أو منعها وفق الوضع، ثم تطابق counts/checksums قبل `new_only`.
5. افشل المصالحة؛ يعود القارئ للقديم وتبقى سجلات الدفعات للتحقيق.

### Q31 — عزل وتحميل حزمة القبول

1. حاول تحميل الحزمة على قاعدة لا تنتهي بـ `_test` ولا تحمل marker demo مصرحًا.
2. المتوقع: فشل مغلق قبل أول كتابة.
3. حمل إصدار الحزمة نفسه مرتين على قاعدة القبول.
4. المتوقع: الأعداد والـchecksums ثابتة ولا توجد حسابات أو سجلات مكررة.
5. تحقق أن الأسماء والهواتف والهويات والمرفقات كلها تجريبية ولا تستخدم سرًا حقيقيًا.

### Q32 — رحلة متصفح كاملة متعددة الأدوار

1. سجل الدخول كعامل وأنشئ إذنًا وإجازة واعتراض حضور ورسالة ارتق.
2. سجل الدخول كمدير مباشر ثم إداري ونفذ الاعتماد والرفض والإعادة.
3. سجل الدخول كـHR وتابع الاستثناء وإعادة الاحتساب والتقرير.
4. سجل الدخول كـFinance وتحقق من fact والأثر/العكس دون وصول لتفاصيل سرية.
5. سجل الدخول كسوبر أدمن وراجع السياسات والمسارات والتدقيق دون self-approval.
6. المتوقع: تنجح كل رحلة حرجة من الواجهة وتطابق النتائج التقرير والحصة والرصيد.

### Q33 — ترك البيانات والاستعادة للمستخدم

1. بعد إتمام الاختبار اترك الحزمة والحسابات والنتائج في بيئة القبول.
2. اتبع دليل التسليم من حساب العامل حتى ظهور الإذن المعتمد في تقرير الحضور.
3. غيّر بعض بيانات الحزمة ثم نفذ استعادة baseline.
4. المتوقع: تعود كيانات الحزمة ونتائجها المرجعية فقط، ولا يتغير أي سجل خارج manifest.
5. أعد تجربة الرحلة بعد الاستعادة لإثبات أن البيئة ما زالت صالحة للمستخدم.

## 5. التحقق من الترحيل

### `off`

- الجداول والعقود غير مستخدمة.
- سلوك الصفحات القديمة كما هو.

### `shadow`

- الاستيراد والحساب الجديدان يعملان دون تغيير التقرير الرسمي.
- كل صف legacy له mapping أو استثناء موثق.

### `compare`

- لوحة الفروق تصنف: سياسة، وردية ليلية، duplicate، إذن، بصمة ناقصة، هوية.
- لا قبول على نسبة تطابق عامة فقط؛ السيناريوهات الحرجة يجب أن تكون 100%.
- تشغيل شهرين ممثلين على الأقل، يشملان عطلات وتغييرات وظيفية.

### `display`

- مستخدمون محددون يرون التقرير الجديد مع fallback القديم.
- لا dual-write يدوي من الصفحة.

### `official`

- الجديد مصدر الحقيقة.
- adapter توافق يمد الصفحات القديمة بالقيم المتوقعة.
- feature flag يسمح برجوع القراءة إلى القديم أثناء نافذة الاستقرار.

## 6. التحقق من الرجوع

الرجوع التشغيلي:

1. أوقف النشر الرسمي الجديد.
2. أعد القراءة إلى legacy adapter.
3. لا تحذف الجداول أو الأحداث أو نتائج shadow.
4. أوقف Outbox consumers الجديدة إن كانت سبب العطل مع الاحتفاظ بالرسائل.
5. صالح آخر batch ودوّن فترة التأثر.

الرجوع لا يعني:

- حذف بصمات خام.
- إسقاط migrations فورًا.
- إعادة قرار اعتماد أو قيد مالي بالحذف.
- تشغيل `git reset --hard` أو تنظيف شجرة العمل.

## 7. الاختبارات الإلزامية قبل الإغلاق

- Unit: precedence، windows، coverage، quotas، balance ledger، state machines.
- Contract: auth، CSRF، role scope، HTTP/JSON، audit، upload، module contracts.
- Integration: transaction rollback، concurrency، outbox retry، Finance idempotency.
- Characterization: الصفحات والمسارات والحقول القديمة.
- UI: الخدمة الذاتية، صندوق المدير، الرسائل العربية، RTL، الفلاتر والتصدير.
- Security: IDOR، self-approval، delegation expiry، confidential fields/files، CSV injection.
- Performance: 500 عامل، خمس سنوات نتائج، paging server-side، لا N+1.

أوامر الإغلاق المستقبلية:

```text
php -l <كل ملف PHP معدل>
composer audit-write-coverage
composer upload-policy-audit        # عند وجود رفع/تنزيل
composer architecture-audit
composer quality
git diff --check
```

لا يجوز إضعاف gate أو توسيع baseline لمجرد الحصول على نجاح.

## 8. حزمة القبول التي تُترك للمستخدم

### الشخصيات التجريبية

| المفتاح | الشخصية | الغرض |
|---|---|---|
| `DEMO-EMPLOYEE-A` | عامل بدوام صباحي | الطلبات والبصمات والتقارير |
| `DEMO-EMPLOYEE-B` | عامل بورديّة/استثناء مختلف | الأولوية والتعارض والحضور البديل |
| `DEMO-DIRECT-MANAGER` | مدير مباشر | المرحلة الأولى والنطاق |
| `DEMO-ADMIN-MANAGER` | مدير إداري | المرحلة الثانية والإقفال |
| `DEMO-HR` | مسؤول HR محدود النطاق | السياسات والاستثناءات والتصحيح |
| `DEMO-FINANCE-MAKER` | منفذ مالي | استقبال facts |
| `DEMO-FINANCE-CHECKER` | مراجع مالي | الاعتماد/العكس |
| `DEMO-SUPER-ADMIN` | سوبر أدمن | الإعداد والتدقيق دون اعتماد ذاتي |

الأسماء مفاتيح ثابتة وليست أكواد موظفين حقيقية، وكلمات المرور تُسلّم خارج المستودع والتقرير.

### البيانات المتروكة

- قوة ووحدة ومسمى ومجموعة وتعيينات مديرين مؤرخة.
- سياسة دوام عامة وأخرى للقوة والمجموعة والعامل، مع وردية ليلية واستراحة.
- بصمات طبيعية ومتأخرة ومكررة وناقصة وهوية غير مربوطة.
- أذونات في حالات draft/pending/approved/rejected/cancelled.
- إجازات وأرصدة وحركات وطلب يعبر فترة استحقاق.
- قضية تأديبية وتظلم وإجراء احترازي تجريبي.
- تذاكر ارتق عادية وسرية وعاجلة وجماعية.
- شهر حضور مفتوح وآخر مقفل، وتقارير شهرية/فترية قابلة للانتقال للتفاصيل.

### ملف التسليم

- عنوان بيئة القبول وطريقة تشغيلها.
- مفاتيح الشخصيات وطريقة استلام بيانات الدخول بأمان.
- ترتيب السيناريوهات والخطوات والنتيجة المتوقعة.
- إصدار dataset ووقت آخر baseline وchecksum.
- نتائج تجربة المنفذ من المتصفح وروابط الأدلة والعيوب المعروفة.
- خطوات الاستعادة والتحذير الصريح من استخدامها على بيانات فعلية.
