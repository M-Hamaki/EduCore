# AI Change Checklist

هذا الملف بوابة عملية لأي تغيير ينفذه مساعد ذكاء اصطناعي. يبقى `AGENTS.md` المصدر الملزم، وتشرح `docs/architecture.md` و`docs/project-structure.md` الحدود الحالية؛ لا يعيد هذا الملف نسخ تلك القواعد.

## قبل التعديل

- [ ] اقرأ `AGENTS.md` والوثائق المعمارية المرتبطة بالنطاق قبل استكشاف واسع للمستودع.
- [ ] افحص حالة Git وحدد الملفات التي كانت متسخة قبل بدء المهمة؛ لا تستبدلها أو تضمها في staging/commit إلا إذا كان التغيير المطلوب فيها قابلاً للفصل وإثبات ملكيته.
- [ ] عرّف نطاقاً صغيراً، والسلوك الذي يجب أن يبقى متوافقاً، والملفات التي لن تتغير.
- [ ] ابحث في الكود والوثائق والاختبارات والاستدعاءات قبل إنشاء `helper` أو `service` أو validator أو abstraction جديد.
- [ ] أعد استخدام المكوّن المعتمد إن كان مناسباً؛ وإن لم يكن، وثّق الفرق الذي يمنع إعادة الاستخدام وتأكد من عدم إنشاء مسار موازٍ لنفس المسؤولية.
- [ ] حدّد الوحدة المالكة للبيانات وقاعدة العمل، والعقد الذي يسمح للوحدات الأخرى بالتعامل معها.
- [ ] حافظ على اتجاه الاعتماد: Presentation → Application → Domain/contracts، وتنفّذ Infrastructure العقود؛ لا يعتمد Domain على HTTP أو PDO ولا تصل وحدة إلى internals وحدة أخرى مباشرة.
- [ ] صنّف كل مسار متأثر: public entrypoint مطلوب، أم ملف داخلي يجب ألا يكون قابلاً للوصول عبر HTTP. لا تستنتج التصنيف من اسم المجلد وحده؛ افحص الروابط و`include`/`require` والاستدعاءات أولاً.
- [ ] إذا تغيّر schema، صمّم migration إصدارية ذات preconditions وخطة rollback/restore؛ يُمنع إنشاء أو تعديل schema أثناء الطلب أو تشغيل التطبيق (runtime DDL).
- [ ] حدّد الاختبارات المناسبة والخطوات الدقيقة للتراجع قبل التنفيذ، ولا تستخدم قاعدة `educore` لاختبار يكتب بيانات.
- [ ] إذا مس التغيير رفعًا أو تخزينًا أو تنزيلًا، اقرأ `docs/file-upload-standard.md` وحدّث تصنيف `tools/upload_policy_manifest.json` واختبارات rollback والصلاحيات.
- [ ] صنّف كل عملية كتابة جديدة، بما فيها العمليات الصغيرة والدفعات والإعدادات والملفات والآثار الخارجية: مالكها، سياسة التدقيق، قابلية التراجع، الحجب، وحدود المستخدم والتعارض.
- [ ] شغّل `composer audit-write-coverage` قبل التنفيذ وبعده؛ أي مرشح جديد يجب أن يكون مسجلاً أو مفوضاً لمالك مسجل، ولا يُقبل تصنيف false positive بلا دليل قابل للمراجعة.
- [ ] عند إضافة حقل لكيان مغطى، راجع دخوله في before/after diff وتسميته وحجبه. عند إضافة جدول فرعي أو ملف أو أثر خارجي، صمّم تغطيته وترتيب rollback صراحة.
- [ ] حدّد هل يلزم ADR: يلزم عند تغيير حدود وحدة، اتجاه اعتماد، عقد مشترك، public surface، ملكية بيانات، أو استثناء دائم من قاعدة معمارية.

## أثناء التعديل

- [ ] اجعل entrypoint مسؤولاً عن الطلب والمصادقة/التفويض وCSRF والاستجابة، وانقل workflow إلى application service وقواعد المجال إلى موضعها المالك.
- [ ] لا تغيّر URL أو أسماء الحقول والمعرّفات أو session keys أو JSON contracts أو قواعد العمل تحت اسم refactor.
- [ ] استخدم عقد service/query موثقًا للتواصل بين الوحدات؛ إذا لم يوجد، عرّف أصغر عقد تملكه الوحدة أولًا. لا تضف SQL متقاطعًا أو `include` لمكوّن داخلي من وحدة أخرى؛ أي استثناء مؤقت يحتاج ADR محكومًا.
- [ ] أبقِ الملفات الداخلية محمية deny-by-default، ولا تحجب endpoint عاماً مثبتاً مثل endpoint AJAX لمجرد وجوده داخل مجلد مشترك.
- [ ] اربط كتابة بيانات العمل وسجل التدقيق/التراجع بمعاملة واحدة حيث يمكن، واجعل فشل التدقيق الإلزامي يعيد العملية كلها؛ استخدم batch ID وتراجعاً ذرياً للعمليات المركبة.
- [ ] استخدم مكونات المسودة ورسالة التراجع المشتركة في footers؛ لا تنشئ localStorage key أو toast أو Ctrl+Z أو منطق استرجاع محلياً داخل الصفحة.
- [ ] اجعل كل دفعة عكوسة وذات غرض واحد، وافصل refactor عن feature أو schema change غير الضروري.
- [ ] لا توسّع النطاق بسبب finding مجاور؛ سجّله كمخاطر أو مهمة لاحقة مع الدليل.

## بعد التعديل

- [ ] راجع diff وتأكد من عدم وجود أسرار أو ملفات غير مرتبطة أو تغييرات user-owned.
- [ ] شغّل lint والاختبارات المركزة واختبارات التكامل فقط في بيئة اختبار محمية، ثم نفّذ فحوص المشروع المطلوبة للنطاق.
- [ ] شغّل `composer architecture-audit` لأي تغيير يمس PHP أو حدود الويب أو فاحص المعمارية أو baseline، وتحقق من أن عدد regressions يساوي صفراً.
- [ ] شغّل `composer upload-policy-audit` لأي تغيير يمس الملفات أو مسارات الرفع/التنزيل أو `APP_URL` أو حماية `uploads/`.
- [ ] شغّل `composer audit-write-coverage` لأي تغيير PHP أو مسار كتابة، ويجب أن تكون `AUDIT_REVIEW_REQUIRED=0`.
- [ ] شغّل `composer admin-ui-audit` عند إضافة أو تعديل صفحة إدارة، وشغّل اختبار role coverage عند إضافة form أو footer لدور جديد.
- [ ] شغّل `composer quality` قبل الإغلاق؛ هذا هو نفس المدخل الذي يفرضه CI ولا يجوز حذف بوابة منه لتجاوز فشل.
- [ ] اختبر حدود public/internal عند إضافة endpoint أو نقل ملف أو تعديل قواعد الخادم.
- [ ] نفّذ أو أثبت خطوات rollback بما يتناسب مع المخاطر، ولا تعتمد على عبارة "يمكن عمل revert" وحدها عندما توجد بيانات أو migration.
- [ ] حدّث الاختبارات والوثائق، وأنشئ/حدّث ADR إذا تغيّر قرار أو حد معماري أو عقد عام.
- [ ] عند إزالة مخالفة مسجلة، احذف مدخلها من baseline في الدفعة نفسها حتى يمنع الفاحص عودتها.

## سياسة baseline المعماري

- baseline آلية ratchet لتجميد الدين المعروف، وليس قائمة سماح أو طريقة لإخفاء regressions.
- المقارنة الحالية على مستوى مسار الملف؛ لا تكشف تلقائيًا زيادة الدين داخل ملف مدرج أصلًا، لذلك راجع diff تلك الملفات يدويًا.
- لا تعدّل `tools/architecture_audit_baseline.json` فقط لجعل الفحص ينجح.
- أي توسيع للـbaseline يتطلب قراراً معمارياً منفصلاً ومراجعاً يذكر finding الدقيق، والدليل، وسبب تعذر الإصلاح الآن، والمخاطر، والمالك، وخطة الإزالة؛ ومن دون هذا القرار يجب إصلاح regression أو إيقاف التغيير.
- لا تجمع توسيع baseline مع feature غير مرتبط، ولا تحوّل finding جديداً إلى "دين قديم" بأثر رجعي.

## دليل الإغلاق المطلوب

سجّل في تسليم المهمة أو وصف commit/PR:

- النطاق والملفات المتغيرة، وما تم استبعاده عمداً.
- المكوّن الموجود الذي أُعيد استخدامه، أو سبب موثق لإنشاء abstraction جديد.
- الاختبارات والفحوص ونتائجها، ومنها `composer architecture-audit` عند انطباقه.
- أثر public/internal boundaries وأثر قاعدة البيانات.
- خطة rollback وحالة ADR (`غير مطلوب` مع السبب، أو رقم/رابط القرار).
- فرق baseline؛ يجب أن يكون صفراً ما لم يوجد قرار معماري مستقل.

## توقف واطلب قراراً

توقف عندما تكون قاعدة العمل أو الصلاحية أو ملكية البيانات أو caller/route غير مؤكدة، أو قد تتأثر بيانات production، أو يتداخل التغيير مع عمل متسخ لا يمكن فصله، أو لا يوجد اختبار مناسب أو rollback آمن، أو لا يمكن تمرير البوابة إلا بتوسيع baseline بلا قرار.
