# الملخص التنفيذي للتدقيق المعماري

**تاريخ خط الأساس:** 2026-07-12
**تاريخ إغلاق الدفعات الآمنة:** 2026-07-13
**النطاق:** الشجرة الحالية في `C:\xampp\htdocs\EduCore`
**الحالة الحالية (2026-07-15):** نُفذت خارطة الترحيل ذات الأولوية وأصبحت البنية Modular Monolith تدريجية مع adapters متوافقة وحواجز آلية؛ تبقى أعمال تشغيلية بعد النشر ومخاطر legacy مصرح بها، لا كوارث معمارية مخفية في الملفات المستهدفة.

## الحكم العام

النظام **يعمل ويحتوي على أجزاء هندسية جيدة، لكنه غير مستقر معماريًا في عدد من الحدود الحساسة**. أفضل وصف له هو: تطبيق PHP تقليدي من نوع **Page Controller / Transaction Script** تطور تدريجيًا إلى **Modular Monolith غير مكتمل الحدود**. توجد خدمات جيدة مثل `AssessmentEngine`, `StaffAttendanceService`, `ActivityLog` و`UndoManager`، لكن كثيرًا من الصفحات ما زال يجمع المصادقة والتحقق وSQL وقواعد العمل وHTML وJavaScript في ملف واحد.

لا يوصى بإعادة كتابة شاملة، ولا بتبنّي Framework كبير أو Microservices. المطلوب هو **إعادة هيكلة جزئية وتدريجية** تحافظ على PHP وPDO وURLs والجلسات والنماذج وقاعدة البيانات الحالية.

## حالة الإغلاق بعد الدفعات الآمنة

المشروع أصبح **Modular Monolith عمليًا ومتدرجًا** في النطاق المخطط: قُسمت الملفات الخمسة ذات الأولوية، نُقلت وحدات الطلاب والعاملين والتقييم السلوكي إلى PSR-4 مع aliases توافقية، وأزيل runtime DDL والملفات التي تتجاوز حد 2000 سطر من نتائج الحارس. كما أُغلقت فجوات CSRF والاستجابات الآمنة والتخزين الخاص ومعاملات workflows المستهدفة واختبارات قاعدة البيانات المعزولة.

## لماذا النتيجة ليست «كارثة كاملة»؟

- الاتصال بقاعدة البيانات والإعدادات الحساسة متمركزان في `config/` و`.env`.
- المصادقة المشتركة موجودة في `Utilities::validateSession()`، والجلسة وCSRF لهما ملفات مشتركة.
- بعض الوحدات الحساسة، خصوصًا محرك التقييمات، تستخدم تحقق صلاحيات ومعاملات وتدقيقًا جيدًا.
- توجد migrations واختبارات وحدوية وأدوات lint وتدقيق واجهة.
- توجد طبقات CSS/JS مشتركة وتعليمات مشروع مركزية في `AGENTS.md`.

لكن هذه النقاط الجيدة ليست مطبقة باتساق على كل المسارات.

## أخطر خمسة مخاطر

1. **بقايا كلمات مرور قابلة للعكس:** أصبح قرار الدخول hash-first، وترتقي الحسابات القديمة بعد دخول ناجح، لكن الغلاف القابل للفك باقٍ لدعم reveal الإداري ويحتاج قرار استعادة حسابات مستقلًا.
2. **سطح ويب أوسع من التطبيق نفسه:** عند خط الأساس كان جذر المشروع كله تحت XAMPP. حُميت المجلدات الداخلية الثمانية وأضيف حارس CLI لـmigration runner، لكن حماية production و`vendor/phpmyadmin` و`uploads/` الحساسة ما زالت غير محسومة.
3. **تشغيل migrations بعد النشر:** الكود لا ينفذ DDL أثناء الطلب، لكن تأخر تشغيل migrations سيوقف الميزات الجديدة بوضوح.
4. **classmap القديم:** PSR-4 مفعل للوحدات المنقولة، لكن `classes/` classmap باقٍ مؤقتًا حتى ينتقل جميع المستدعين المثبتين.
5. **مخاطر توريد متغيرة زمنيًا:** الاعتماديات المستخدمة حاليًا ليست زائدة، لكن advisories الجديدة تتطلب `composer audit` دوريًا.

## التحسينات الخمسة الآمنة المنفذة

1. توثيق المعمارية الحالية والمستهدفة وقواعد الاعتماد، وتثبيت `AGENTS.md` مصدرًا أعلى مع دستور وقوالب واختبار drift.
2. منع HTTP المباشر للمجلدات الداخلية الثمانية وإضافة حارس CLI لـ`tools/run_migrations.php` مع اختبار حدود.
3. إنشاء فاحص معماري read-only صارم يرصد الملفات الكبيرة وruntime DDL ومرشحي CSRF وحماية المجلدات دون توسيع baseline لإخفاء الدين.
4. حماية كل عمليات الكتابة المحلية في `admin/classes.php` بـCSRF قبل DB/POST مع اختبار عقد 9/9.
5. منع تفاصيل الاستثناء من `UndoManager::undo()` ومسارات `Throwable` في `api/undo.php` مع اختبار فشل معزول 11/11.

## القيود التشغيلية المتبقية

- لا يُحذف `classes/` classmap حتى تنتقل كل الفئات القديمة ويثبت عدم وجود مستدعين للأسماء العامة.
- يجب تشغيل migrations في نافذة النشر قبل تفعيل الكود المعتمد عليها.
- مخطط التقييمات والتقارير يعمل عبر عدة أدوار وجداول؛ لا يجوز نقله أو إعادة تسميته قبل اختبارات تكامل على قاعدة staging.
- لا يجوز حذف `archive/`, `scratch/`, `tmp/` أو ملفات قد تبدو قديمة بالاسم فقط؛ الحماية والحصر يسبقان الحذف.
- لا يجوز تشغيل migrations أو اختبارات تكامل كتابية على قاعدة `educore`; تستخدم `educore_test` مع الحارس الصريح فقط.

## المعمارية المستهدفة

**Modular Monolith تدريجي** مع:

- بقاء ملفات URLs الحالية كـ entry-point adapters رفيعة.
- طبقة مشتركة للمصادقة والتفويض وCSRF والاستجابة والأخطاء.
- وحدات أعمال واضحة للطلاب، العاملين، الهيكل الأكاديمي، التقييمات، الحضور، المالية، النقل، المحتوى، والإشعارات.
- Application Services لقواعد سير العمل.
- Repositories/Data Gateways لـSQL، دون فرض ORM.
- Validators مركزية أو خاصة بكل وحدة.
- Views لا تنفذ SQL ولا تغيّر مخطط البيانات.
- migrations هي المسار الوحيد لتغيير schema.

## مسار الانتقال المتوقع

1. تثبيت خط الأساس والوثائق وقواعد عدم الانحراف.
2. حماية حدود الويب وإضافة فحوص معمارية read-only.
3. توحيد bootstrap/CSRF/error handling دون تغيير URLs.
4. توحيد validators وschema inspection.
5. استخراج الخدمات من الملفات العملاقة، وحدة واحدة في كل مرة.
6. نقل SQL إلى repositories بعد وجود اختبارات عقد وسلوك.
7. نقل التخزين الحساس خارج الويب عبر migration متوافق وخادم تنزيل مصرح.
