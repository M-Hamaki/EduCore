# خطة تطوير وتعميم منظومة التدقيق والتراجع وحماية المسودات

## 1. الغرض والنطاق

تهدف هذه الخطة إلى ضمان تسجيل كل تغيير مهم في EduCore، مع توفير تراجع أو استرجاع آمن عندما تسمح طبيعة العملية، من دون إبطاء المسارات اليومية أو كسر التوافق الحالي.

تشمل الخطة جميع نقاط الكتابة في الإدارة والمعلمين والطلاب والمتخصصين والمشرفين والمعلمين الخارجيين، بما في ذلك صفحات PHP وواجهات API وطلبات AJAX والاستيراد والعمليات الجماعية والمهام المجدولة وأدوات الصيانة المعتمدة.

لا تعني شمولية التسجيل أن كل عملية قابلة للتراجع المباشر. سجل التدقيق إلزامي لكل تغيير، بينما تحدد سياسة الكيان إن كان الاسترجاع مباشرًا أو عكسيًا أو غير مسموح به.

## 2. مبادئ ملزمة

1. كل كتابة ناجحة تنتج حدث تدقيق واحدًا على الأقل.
2. لا تظهر رسالة نجاح أو إمكانية تراجع إلا بعد نجاح معاملة البيانات وسجلها.
3. العملية التي تغير عدة سجلات أو جداول تحمل `batch_id` واحدًا وتُعامل كوحدة أعمال واحدة.
4. التراجع نفسه عملية أعمال مسجلة وغير قابلة للإخفاء.
5. التراجع لا يكتب فوق تعديل أحدث؛ التعارض يوقفه ويعرض سببه.
6. الماليات والنتائج المنشورة والعمليات الأمنية الحساسة تُعكس بعملية مقابلة عند الحاجة، ولا يُمحى تاريخها.
7. تخزين الحالة قبل وبعد التغيير يكون تلقائيًا قدر الإمكان، مع حجب الأسرار والبيانات غير اللازمة.
8. لا يفشل تغيير أعمال ناجح بصمت بسبب فشل التدقيق؛ تحدد السياسة هل يفشل الطلب كله أم يُسجل فشل حرج للمراقبة.
9. كل schema جديد يضاف عبر migration، ولا ينشأ جدول أثناء الطلب.
10. التعميم تدريجي، مع بقاء URLs وحقول النماذج والجلسات والصلاحيات والعقود الحالية متوافقة.

## 3. النموذج الوظيفي المستهدف

```text
HTTP / API / Job
      |
Application Service
      |
Database Transaction
      +-- Domain write(s)
      +-- Entity snapshot / diff
      +-- Audit event(s)
      +-- Undo entry or reversal reference
      |
Commit
      |
Unified result message / optional undo action
```

المكونات المستهدفة داخل المونوليث المعياري:

- `AuditService`: تسجيل حدث الأعمال وهوية المنفذ والسياق والتغييرات.
- `EntityChangeTracker`: بناء snapshot وdiff موحدين مع سياسة حجب الحقول.
- `UndoableActionService`: تسجيل وتنفيذ التراجع الذري وفحص التعارض والصلاحيات.
- `AuditPolicyRegistry`: سياسة كل كيان وعملية: التسجيل، مدة الاحتفاظ، قابلية التراجع، وحقول الحجب.
- `AuditContext`: المستخدم والدور والطلب و`request_id` و`batch_id` ومصدر العملية.
- adapters توافقية لـ`ActivityLog` و`UndoManager` أثناء الترحيل، دون إنشاء مسار تسجيل موازٍ دائم.

## 5. البيانات المطلوب تسجيلها

الحد الأدنى لكل حدث:

- معرف الحدث، `request_id`، و`batch_id` عند وجوده.
- وقت UTC ووقت العرض المحلي.
- هوية المنفذ الفعلية والدور الفعلي والدور المستخدم ومصدر العملية.
- الوحدة، نوع الكيان، معرفه، واسمه الآمن للعرض.
- نوع العملية والنتيجة والسبب أو الوصف.
- snapshot قبل وبعد أو diff منظم وفق السياسة.
- route أو endpoint وطريقة الطلب، مع IP وuser-agent عند الحاجة الأمنية.
- معرف الحدث الأصلي عند التراجع أو العكس.
- نسخة policy/schema المستخدمة لتفسير الحدث.

يُمنع تسجيل كلمات المرور وhashes وCSRF tokens ومفاتيح API وaccess tokens وبيانات الجلسة والمحتوى الكامل للملفات. تخضع الهواتف والعناوين والهوية والبيانات الطبية لسياسة حجب وعرض وصلاحيات منفصلة.

## 6. دعم الحقول والكيانات المستقبلية

يدخل الحقل الجديد تلقائيًا في السلوك عندما تمر الكتابة عبر خدمة التطبيق ويكون الكيان مسجلًا في `AuditPolicyRegistry`. يقرأ `EntityChangeTracker` الصف قبل وبعد الكتابة ويولد الفرق تلقائيًا، لذلك لا تحتاج الحقول العادية إلى استدعاء يدوي جديد.

تتطلب الحالات التالية قرارًا صريحًا عند الإضافة:

- حقل سري أو حساس: يضاف إلى قائمة الحجب أو التحويل إلى fingerprint.
- حقل كبير أو binary/JSON ضخم: يسجل ملخصًا أو hash ومرجعًا بدل المحتوى الكامل.
- جدول جديد: يحدد المالك والمفتاح الأساسي وسياسة الاحتفاظ والتراجع والعلاقات.
- عملية متعددة الجداول: تعرف كوحدة أعمال وتنتج batch واحدًا.
- قيمة مشتقة أو cache: لا تسجل كتغيير أعمال مستقل إلا عند الحاجة التشغيلية.

يضاف فحص معماري آلي يفشل عند اكتشاف نقطة كتابة جديدة لا تمر عبر خدمة معتمدة أو لا تعلن سياسة التدقيق، مع baseline مرحلي للدين الحالي لا يُوسع دون مراجعة.

## 7. تطوير مخطط البيانات

تُحسم الأسماء النهائية بعد جرد schema الحالي، ثم تنفذ migrations متوافقة وإضافية. المتطلبات المنطقية:

- توسيع سجل النشاط أو إنشاء store موحد يملك: `event_id`, `request_id`, `batch_id`, actor fields, module/entity/action/result, before/after/diff, metadata, policy version, timestamps.
- توسيع `undo_log` بـ: الحالة، نوع الاسترجاع، مدة الصلاحية، revision متوقع، سبب عدم القابلية، event الأصلي، المنفذ، ووقت التنفيذ.
- ربط `recycle_bin` بالحدث والـbatch وسياسة الاحتفاظ وحالة الملف عند وجود مرفق.
- جدول اختياري لحزم العمليات `audit_batches` لتلخيص الاستيراد والنقل الجماعي.
- فهارس مركبة على الوقت، المنفذ، الكيان، `request_id`, `batch_id`, الحالة، وصلاحية التراجع.
- قيود تمنع تكرار تنفيذ التراجع وتدعم idempotency.

قبل أي migration: نسخة احتياطية موثقة، تقدير حجم الجداول، اختبار مدة التنفيذ على قاعدة `_test` مماثلة، وخطة rollback أو forward-fix واضحة.

## 8. مراحل التنفيذ

### المرحلة 0: تثبيت القياس والحوكمة

المخرجات:

- قاموس موحد للعمليات والكيانات والحقول الحساسة.
- مالك لكل وحدة وسياسة تصعيد للعمليات عالية الخطورة.
- مؤشرات baseline للأداء وحجم سجلات الكتابة وفشل الطلبات.
- قرار معماري ADR لاعتماد حدود الخدمات وسياسة التدقيق والتراجع والاحتفاظ.

معيار القبول: اعتماد السياسات وعدم وجود نوع بيانات حرج بلا مالك أو قرار.

### المرحلة 1: الجرد الكامل لنقاط الكتابة

يشمل الجرد `INSERT/UPDATE/DELETE`، model/repository methods، POST/AJAX/API، imports، jobs، الملفات، والتكاملات الخارجية. ينتج سجل تغطية يحتوي route والخدمة والجداول والصلاحية والمعاملة والتدقيق الحالي والتراجع الحالي والمخاطر.

معيار القبول: كل نقطة كتابة مصنفة إلى مغطاة، تحتاج ترحيلًا، استثناء موثق، أو غير مؤكدة تحتاج اختبارًا. لا تُقبل نسبة 100% بالبحث النصي وحده؛ تضاف اختبارات تشغيلية للمسارات الحرجة.

### المرحلة 2: تقوية الأساس الحالي

المخرجات:

- إصلاح قائمة الكيانات المدعومة وعدم تطابقها مع الاستدعاءات الحالية.
- منع toast التراجع ما لم تكن العملية قابلة للتراجع فعليًا.
- توحيد `batch_id` والتراجع الذري والمعاملات وفحص التعارض.
- جعل `ActivityLog` و`UndoManager` يعيدان نتائج قابلة للمراقبة بدل الفشل الصامت.
- إزالة إنشاء schema وقت الطلب إن وجد ونقله إلى migrations.
- اختبارات characterization للسلوك الحالي قبل تغيير العقود.

معيار القبول: لا يوجد تراجع جزئي عند فشل عنصر داخل batch، ولا رسالة مضللة، وتنتهي اختبارات التعارض والصلاحيات بنجاح.

### المرحلة 3: إنشاء الخدمات والعقود المركزية

تنشأ العقود والخدمات داخل حدود معمارية متوافقة مع الوحدات الحالية. تبقى الفئات القديمة adapters مؤقتة، وتمنع كتابة الأعمال الجديدة مباشرة إلى جداول السجل.

معيار القبول: نموذج إضافة وتعديل وحذف متعدد الجداول يعمل عبر API موحد، ويشمل الحقول الجديدة تلقائيًا، ويحجب الأسرار.

### المرحلة 4: تجربة وحدتين حرجتين

الوحدتان المقترحتان: ملفات الطلاب/العاملين، ثم الدرجات أو الحضور. تمثلان عمليات متعددة الجداول وصلاحيات وعلاقات وتعارضات حقيقية.

معيار القبول: نجاح اختبارات الأدوار والمعاملات والتراجع والتعارض والأداء، وإثبات rollback على قاعدة اختبار معزولة.

### المرحلة 5: ترحيل الوحدات على موجات

ترتيب مقترح حسب الخطورة والاعتماد:

1. الهيكل الأكاديمي والطلاب والعاملون والحسابات.
2. الدرجات والتقييم والتقارير والحضور.
3. الماليات والرواتب والخصومات والسلف مع reversal فقط.
4. النقل والمكتبة والمواد والإشعارات والمرفقات.
5. الإعدادات والصلاحيات والتكاملات والنسخ الاحتياطي.
6. بوابات المعلم والطالب والمتخصص والمشرف وواجهات API والمهام المجدولة.

كل موجة تتطلب تحديث سجل التغطية واختبار المسارات وعدم زيادة زمن الكتابة فوق الميزانية المعتمدة.

### المرحلة 6: توحيد تجربة المستخدم

- مكون toast مركزي يعرض العملية الدقيقة ومدة التراجع وحالته.
- حالات موحدة: قابل للتراجع، انتهت المدة، تعارض، يحتاج صلاحية، تم العكس، فشل آمن.
- صفحة تدقيق قابلة للبحث حسب المستخدم والوحدة والكيان والفترة والعملية والنتيجة.
- صفحة نسخ/سلة محذوفات تعرض ما يمكن استعادته ولماذا لا يمكن استعادة غيره.
- Bootstrap modal للتأكيدات الحساسة، دون `confirm()` أو SweetAlert.
- تحميل حماية المسودات لكل الأدوار عبر footer مشترك مناسب، مع opt-out صريح للنماذج الحساسة.

معيار القبول: نفس العملية تعرض الرسالة والسلوك نفسيهما من كل entrypoint مدعوم، مع اختبار RTL والجوال ولوحة المفاتيح وإتاحة الوصول.

### المرحلة 7: الأداء والاحتفاظ والمراقبة

- قياس p50/p95/p99 قبل وبعد لكل مسار كتابة حرج.
- كتابة السجل ضمن transaction عندما تكون سلامة الأعمال ملزمة، واستخدام outbox/queue فقط للأعمال الثانوية بعد اعتماد ADR وتشغيل worker موثوق.
- batch insert للعمليات الجماعية، ومنع استعلام لكل عنصر عند إمكان الجمع.
- partition/archive أو ترحيل بارد بناءً على الحجم الفعلي، لا على تقدير نظري.
- retention مختلفة لسجلات الأعمال والأمن والتراجع والمسودات، مع legal hold عند الحاجة.
- تنبيهات لفشل التدقيق، تراكم queue، تضخم الجداول، بطء الاستعلامات، وفشل الاسترجاع.

معيار القبول المبدئي: لا يتجاوز overhead للتسجيل 10% من p95 أو 50ms للمسار المعتاد، أيهما أقل، بعد القياس على بيانات مماثلة. تُراجع القيمة إذا أثبت baseline أنها غير واقعية.

### المرحلة 8: الإغلاق ومنع الارتداد

- بوابة CI لنقاط الكتابة الجديدة وسياسات الكيانات والحقول الحساسة.
- تقرير تغطية يولد دوريًا ويقارن بالbaseline.
- إزالة adapters والاستدعاءات اليدوية القديمة فقط بعد وصول مستهلكيها إلى صفر.
- تحديث وثائق المعمارية وقاعدة البيانات وrunbooks وسجل التنفيذ.

معيار القبول: كل نقطة كتابة لها سياسة واختبار أو استثناء معتمد بمالك وتاريخ انتهاء، ولا توجد رسالتا تدقيق/تراجع متنافستان.

## 9. استراتيجية الاختبار

تُنفذ اختبارات الكتابة على قاعدة معزولة اسمها منتهٍ بـ`_test` فقط:

- Contract tests لخدمات التدقيق والتغيير والتراجع.
- اختبارات insert/update/delete/status لكل سياسة.
- اختبار batch متعدد الجداول مع فشل متعمد في المنتصف.
- اختبار تعديل أحدث قبل التراجع، وحذف اعتماد، وتغير الصلاحية.
- اختبارات idempotency للنقر أو إعادة إرسال الطلب.
- اختبارات الأدوار لكل بوابة وAPI.
- اختبارات الحجب للتأكد من عدم تسرب الأسرار أو الملفات.
- اختبارات imports كبيرة وعمليات جماعية وقياسات p95.
- اختبارات migration forward وrollback/forward-fix.
- اختبارات واجهة للـtoast والمسودة وسلة المحذوفات وانتهاء المدة.
- اختبار استعادة دوري عشوائي لعينة من الأحداث القابلة للتراجع.

## 9.1 بوابة اعتماد المحرك قبل التعميم

لا تبدأ المرحلة الخامسة ولا يُربط المحرك بوحدة إضافية حتى يجتاز الإصدار المرشح جميع البنود التالية:

- **Atomicity:** نجاح كل عناصر العملية أو رجوعها جميعًا، بما فيها سجل التدقيق وبيانات التراجع وفق السياسة.
- **Consistency:** احترام المفاتيح الأجنبية وقواعد المجال وعدم إنتاج سجل يمكن استعادته إلى حالة غير صالحة.
- **Isolation:** اختبار تعديلين متزامنين وتراجع متزامن ومنع lost update بالتأكد من revision أو snapshot متوقع.
- **Durability:** بقاء الحدث وحالة التراجع صحيحة بعد commit وإعادة تشغيل الطلب أو worker.
- **Idempotency:** إعادة إرسال الطلب أو نقر التراجع مرتين لا يكرر الكتابة ولا يعكس العملية مرتين.
- **Authorization:** فصل صلاحية مشاهدة السجل عن تنفيذ التراجع أو الاستعادة أو العكس المالي، مع منع المستخدم من تجاوز نطاقه.
- **Tamper evidence:** منع تعديل سجلات التدقيق عبر واجهات الأعمال، وتقييد الوصول المباشر، وتوفير ترابط أو checksum عندما يعتمد ADR ذلك.
- **Privacy:** حجب الأسرار والحقول الحساسة وتطبيق أقل قدر لازم من البيانات وسياسة الاحتفاظ والحذف القانوني.
- **Conflict handling:** إيقاف التراجع عند وجود تغيير أحدث أو اعتماد جديد، وإظهار سبب قابل للفهم دون تعديل جزئي.
- **Relationship restoration:** استعادة العلاقات التابعة بالترتيب الصحيح، أو رفض الاستعادة عندما لا يمكن إثبات سلامتها.
- **Files and external effects:** عدم الادعاء بإلغاء بريد أو إشعار أو تكامل خارجي تم بالفعل؛ استعادة الملفات فقط عند وجود نسخة سليمة موثقة.
- **Bulk safety:** حدود لحجم batch، وتسجيل progress والنتيجة، ومنع استهلاك ذاكرة يتناسب خطيًا مع payload ضخم.
- **Observability:** metrics وسجل أخطاء منظم وcorrelation، وتنبيه واضح لفشل capture أو execute أو archive.
- **Performance:** اجتياز ميزانية p95 المعتمدة مع explain للفهارس والاستعلامات الحرجة واختبار حجم مماثل للإنتاج.
- **Compatibility:** بقاء العقود الحالية وURLs وحقول النماذج والجلسات ورسائل JSON متوافقة أثناء الترحيل.
- **Recovery drill:** تنفيذ تمرين استعادة موثق على قاعدة `_test` من البداية للنهاية، يشمل فشلًا متعمدًا وتحققًا من النتيجة.

يعاد تشغيل هذه البوابة عند تغيير schema المحرك أو سياسة التعارض أو نموذج الصلاحيات أو التخزين أو مدة الاحتفاظ، وليس عند الإصدار الأول فقط.

## 9.2 سيناريوهات مرجعية إلزامية

يجب أن تغطي مجموعة الاختبار، على الأقل:

1. إضافة سجل بسيط ثم التراجع عنه.
2. تعديل حقل واحد وعدة حقول، بما فيها حقل أضيف حديثًا دون تعديل يدوي لمسجل الحدث.
3. حذف سجل له توابع، واستعادته بالترتيب الصحيح.
4. محاولة التراجع بعد تعديل لاحق من مستخدم آخر.
5. عملية متعددة الجداول تفشل عند أول عنصر ووسط batch وآخره.
6. استيراد كبير ينجح، واستيراد جزئي مرفوض، واستيراد يعاد إرساله بنفس مفتاح idempotency.
7. تعديل درجات أو حضور داخل فترة مفتوحة وبعد القفل والنشر.
8. إلغاء دفعة مالية بقيد عكسي دون حذف السجل الأصلي.
9. تغيير صلاحية قد يؤدي إلى فقد آخر مدير أو تجاوز نطاق المنفذ.
10. حذف مرفق مع وجود نسخة quarantine وبدونها.
11. إرسال إشعار خارجي لا يمكن سحبه، وإلغاء إشعار مجدول لم يُرسل.
12. انتهاء مدة التراجع، حذف actor، تغير اسم الكيان، أو تغير schema بعد تسجيل الحدث.
13. انقطاع الاتصال أو deadlock أو timeout أثناء capture والتنفيذ.
14. محاولة تعديل سجل التدقيق أو تنفيذ التراجع عبر CSRF أو دور غير مصرح.
15. عمليتان متزامنتان على السجل نفسه وعمليتان مستقلتان داخل batchين مختلفين.

## 10. خطة النشر والرجوع

يستخدم التعميم feature flags على مستوى الوحدة والعملية: `audit_write`, `undo_capture`, `undo_execute`, `unified_ui`. يبدأ التسجيل في shadow/compare mode حيث أمكن، ثم يفعّل العرض، ثم التنفيذ.

عند ظهور مشكلة:

1. يعطل `undo_execute` أولًا مع استمرار التدقيق.
2. يعود entrypoint إلى adapter المتوافق دون حذف السجلات الجديدة.
3. لا تُرجع migration مدمرة؛ يستخدم forward-fix إلا إذا كان rollback مختبرًا ولا يفقد بيانات.
4. تُحفظ الأحداث الفاشلة في قناة تشخيص آمنة وتُراجع قبل إعادة التشغيل.
5. لا يعاد تنفيذ batch إلا بمفتاح idempotency وبعد إثبات حالته.

## 11. مؤشرات النجاح

- تغطية نقاط الكتابة المصنفة: 100% بسياسة أو استثناء معتمد.
- أحداث بلا actor أو request correlation: صفر في المسارات التفاعلية.
- أسرار ظاهرة في السجل: صفر.
- رسائل تراجع لعملية غير قابلة للتراجع: صفر.
- تراجع جزئي داخل batch: صفر.
- فشل تدقيق غير مراقب: صفر.
- نسبة نجاح الاسترجاع للعمليات المؤهلة: تحدد بعد baseline وتراقب لكل وحدة.
- أثر الأداء ضمن الميزانية المعتمدة لكل مسار.
- أي حقل أو نقطة كتابة جديدة تفشل في CI إذا لم تعلن سياستها.

## 12. سجل التسليم لكل موجة

يجب أن توثق كل موجة:

- الملفات والroutes والجداول والعقود والصلاحيات المتأثرة.
- العمليات التي أصبحت مدققة أو قابلة للتراجع ونوع الاسترجاع.
- migrations ونسخة policy.
- نتائج الاختبارات والأداء وحجم البيانات.
- الحالات المستثناة وأسبابها ومالكها وتاريخ مراجعتها.
- خطوات النشر والرجوع وfeature flags.
- تحديث `docs/architecture-audit/15-implementation-log.md` بعد التنفيذ الفعلي.

## 13. تعريف الاكتمال الشامل

لا تعتبر المنظومة معممة بالكامل لمجرد وجود `ActivityLog` و`UndoManager` أو ظهور toast. تكتمل عندما يثبت سجل الجرد والاختبارات والقياس أن كل نقطة كتابة في كل دور وواجهة لها سياسة مطبقة، وأن العمليات المؤهلة تُستعاد كوحدة آمنة، وأن العمليات غير القابلة للتراجع تحتفظ بتاريخ عكسي واضح، وأن الحقول والكيانات الجديدة لا تستطيع تجاوز الحوكمة تلقائيًا.
