# سجل القرارات المعمارية

يسجل هذا الملف القرارات المعمارية الدائمة المؤكدة في 2026-07-12. القرارات هنا مختصرة، وتفاصيل الأدلة والمخاطر وخطة التنفيذ موجودة في `docs/architecture-audit/`. عند التعارض، تبقى قواعد `AGENTS.md` الجذرية هي المرجع الملزم.

## ADR-079 — اعتماد تغييرات الدوام وإقفال الحضور والدليل البديل

- **الحالة:** معتمد ومنفذ في 2026-08-13.
- **تغيير الدوام:** تملك Staff مسار الاعتماد وقراراته، بينما تملك Attendance طلب تغيير الدوام وتفسير الدوام الفعلي. يمر الأثر النهائي عبر `ApprovalWorkflowOutcomeHandler` ضيق، ويعاد قفل طلب Attendance والتحقق من ملكية مسار `schedule_change` عبر `ApprovalDecisionEvidenceQuery`. يحتوي تبديل الورديات لقطة مستقلة لكل مشارك، ويختار المحلل لقطة العامل الحالي. يبحث العمل الإضافي المعتمد في اليوم الكامل مع نافذة الوردية الليلية؛ غير المعتمد لا يؤثر.
- **إعادة التحقق:** تظل لقطة المسار ثابتة كدليل، لكنها لا تمنح مديرًا سابقًا صلاحية دائمة. يعيد `ApprovalManagerRelationshipRevalidationQuery` التحقق من علاقة المدير الحالية قبل القرار باستخدام هوية العامل المستخرجة من التعيين المجمد، ويفشل مغلقًا بعد النقل أو انتهاء العلاقة.
- **إقفال الفترات:** صفحات الإدارة مهايئات مصادقة وCSRF لخدمة Attendance فقط. ينشئ أي تغيير بعد الإقفال حقيقة معلقة ويتطلب قرار إعادة فتح بقفل تفاؤلي؛ إعادة القرار نفسها idempotent، ولا تعدل Attendance بيانات Finance مباشرة.
- **الحضور البديل:** يسمح نطاق `self_manager` للعامل بتسجيل دليل append-only ولنفسه فقط، وللمدير المرتبط حاليًا بالمراجعة. تمنع المراجعة الذاتية، وتفلتر العناصر قبل العرض، وإنهاء الوسيلة يمنع أدلة جديدة دون حذف التاريخ.

## ADR-078 — إزالة وضع الضيف واعتماد مسار مواد الطلاب للوصول العام المباشر

- **الحالة:** معتمد ومنفذ في الكود في 2026-08-11، ويحل محل أجزاء الضيف وإعداد الخدمة العامة في ADR-077.
- **القرار:** لا يوجد زر أو صفحة أو دور أو كتالوج أو إعداد لخدمات الضيف. تعرض بوابة الدخول زرًا واحدًا باسم «الذهاب لتحميل الشيتات والملفات مباشرة بدون تسجيل دخول». يعمل `materials.php` كبوابة توافق وسياسة مقدمة فقط ثم يحول إلى `student/materials/`، كما تحول روابط `guest.php` القديمة إلى المسار نفسه دون إنشاء هوية أو صلاحية ضيف.
- **النشر والوصول:** يرى المستخدم غير المسجل نفس واجهة المواد التي يراها الطلاب ونفس الصفوف المنشورة. لا يوجد حقل مستقل للنشر العام؛ `materials.enabled` مع نشاط المرحلة والصف يقرر الظهور، و`materials.downloadable` يقرر السماح بالتنزيل. يعيد `material_download.php` فحص هذه الشروط ومعرف الملف واسمه ومساره الحقيقي عند كل طلب، ولا يصدر مسار التخزين للمتصفح.
- **الإدارة والتوافق:** أزيلت صفحة إعداد خدمات الضيف من القائمة، وتحول مسارها القديم بعد التحقق من جلسة الأدمن إلى `admin/materials_center.php`، وهو مالك التفعيل وإتاحة التنزيل. لا كتابة إعداد جديدة ولا تدقيق كتابة مطلوبان؛ أي صف قديم تحت `public_portal_services` يصبح خاملاً ولا يقرأه التنفيذ.
- **المقدمة والتراجع:** يحافظ مسار `materials.php` على فيديو أول زيارة ودورية 15 يوماً وتخطي Teams قبل التحويل. التراجع هو إعادة توجيه زر المواد إلى الكتالوج العام السابق إن أعيد اعتماده في قرار لاحق؛ لا توجد migration أو بيانات أعمال جديدة.

## ADR-077 — بوابة عامة موحدة وضيف بلا حساب وTeams صامت بلا ربط

- **الحالة:** معتمد ومنفذ في الكود في 2026-08-11؛ أجزاء الضيف وإعداد خدماته فقط استبدلها ADR-078، بينما تبقى قرارات البوابة وTeams والمقدمة سارية.
- **القرار:** `index.php` هو واجهة الدخول الموحدة، و`login.php` يبقى مالك POST اليدوي المتوافق، وتصبح معاملات المرحلة بلا أثر على المصادقة. تملك وحدة `PublicPortal` كتالوج الخدمات وسياسة المقدمة وعقود القراءة والإعدادات؛ الضيف ليس مستخدماً أو دوراً ولا ينشئ جلسة صلاحيات.
- **الخدمات والمواد:** تخزن حالة الخدمات وترتيبها تحت المفتاح `public_portal_services` في جدول `settings` الموجود، ويشترك الحفظ مع `AuditService` في معاملة واحدة. يصنف فاحص تغطية الكتابة صفحة الإدارة كـadapter مفوض إلى `UpdateGuestServices` و`PdoPublicPortalRepository` مع دليل rollback، ولا توجد migration جديدة. يعاد استخدام `materials.enabled` و`materials.downloadable` للنشر، ويعيد endpoint التنزيل فحص الخدمة والحالة والمرحلة والصف واحتواء المسار عند كل طلب. الخدمة default-deny، بينما يظل اختصار المواد ظاهراً ويعرض حالة عدم الإتاحة عند تعطيلها.
- **Teams:** يبدأ الغلاف محاولة واحدة تلقائياً بمهلات محدودة ويرسل الرمز POST same-origin ولا يخزنه. المسار الصامت لا يربط حساباً؛ يلزم ربط `azure_id` سابق وتطابق البريد الموثق مع `users.email` و`users.username` في كل دخول. أي فشل يعيد البوابة الموحدة، والفيديو متخطى داخل Teams.
- **المقدمة والتراجع:** يعرض الفيديو عند أول زيارة عادية ثم بعد 15 يوماً، ويدعم وجهتي `portal|materials` فقط. يفصل علما `UNIFIED_ACCESS_PORTAL_ENABLED` و`TEAMS_AUTO_SSO_ENABLED` التراجع؛ إيقاف الأول يعيد مسار البوابة القديم، وإيقاف الثاني يبقي طرق الدخول التفاعلية.

## ADR-076 — إعداد Microsoft SSO يختار Localhost والإنتاج دون خلط callbacks

- **الحالة:** معتمد ومنفذ في الكود في 2026-08-11؛ تسجيل Redirect URIs في Microsoft Entra والنشر على الخادم إجراءان تشغيليان منفصلان لم ينفذا من مساحة العمل.
- **القرار:** `MicrosoftSsoEnvironment` يختار مفاتيح `AZURE_LOCAL_*` في الوضع التلقائي فقط للمضيفين الصريحين `localhost`, `127.0.0.1`, و`::1`، ويستخدم `AZURE_*` لأي مضيف آخر. يثبت الإنتاج عبر `MICROSOFT_SSO_ENV=production`، ويسمح وضع `local` الصريح باختبار HTTPS Tunnel بشرط callbacks محلية مهيأة صراحة؛ لا يشتق callback من Host غير loopback. إذا غاب callback على loopback فقط يبنيه من الأصل ومسار التطبيق. يمكن أن تستخدم البيئة المحلية App Registration مستقلاً أو ترث بيانات اعتماد الإنتاج، لكن كل callback يجب أن يكون مسجلاً في Entra.
- **ربط الهوية:** يقبل Microsoft SSO حساباً واحداً فقط عندما يطابق البريد الموثق كلاً من `users.email` و`users.username`. وجود `azure_id` لا يتجاوز المطابقة؛ تغيير بريد Microsoft أو تكرار البريد/المعرف يفشل مغلقاً حتى يصحح المسؤول بيانات الحساب، ولا يُنقل الربط تلقائياً إلى حساب آخر.
- **فشل التدقيق والنشر:** يحمل `MicrosoftSSO` خدمة التدقيق صراحة عند وجودها. فشل تحميلها أو ربط الحساب أو حفظ حدث الدخول يمسح جلسة SSO الجزئية ويعيد فشل دخول منضبطاً؛ لا يستمر الدخول بلا تدقيق. نقاط دخول Microsoft/Teams تعطل عرض أخطاء PHP وتكتب التفاصيل في سجل الخادم. يلزم نشر `classes`, `src`, وComposer autoload المتوافقة معاً.

## ADR-075 — تعليق دخول الطالب قرار حساب موحد ومدقق وذري

- **الحالة:** معتمد ومنفذ في الكود في 2026-08-11؛ ترحيل قاعدة البيانات لم يُشغّل على `educore` ضمن هذا التغيير.
- **القرار:** يبقى `users.status` ملخص التحكم المتوافق، وتضيف migration حقول `login_disabled_reason`, `login_disabled_at`, و`login_disabled_by`. السبب الفارغ ينتج الرسالة العامة الثابتة، والسبب المكتوب يعرض نصه وحده بلا بادئة أو لاحقة. لا يُكشف سبب خاص في دخول كلمة المرور إلا بعد نجاح التحقق من كلمة المرور، بينما Microsoft SSO يكشفه فقط بعد تحقق الهوية من Microsoft.
- **الملكية والتنفيذ:** تملك `StudentAccountBulkCommandService` تغييرات التفعيل والتعطيل الفردية والجماعية من `student_accounts.php`. تستخدم الدفعة معرفًا واحدًا، وتكتب تغيير الحساب وسجل التدقيق/التراجع في معاملة واحدة، وتفشل كاملة عند تعذر أي عنصر؛ الحساب المعطل بالفعل لا يُعاد تعديل سببه، والتفعيل يمسح السبب الحالي ولا يمس التاريخ المدقق.
- **حماية دورة الطالب:** `StudentLoginAccessPolicy` هو قرار الدخول المشترك لكلمة المرور وMicrosoft SSO والجلسة المفتوحة. حالات القيد/الدراسة النهائية في الملف أو القيد السنوي تسبق التعطيل الإداري ولا يجوز لإدارة الحسابات تغييرها. يعاد فحص الطالب في `Utilities::validateSession()` ويُنهى وصول جلسته عند الطلب التالي دون نقل السبب في URL.

## ADR-074 — منسق ترحيل Staff-HR يثبت النوافذ والدفعات ولا يملك تحويل الصفوف

- **الحالة:** معتمد ومنفذ في 2026-08-11، ومثبت على قاعدة MariaDB مؤقتة تنتهي بـ `_test` حُذفت بعد الاختبار؛ لم يُشغّل على `educore`.
- **القرار:** يملك `StaffHrMigrationCoordinator` فقط نافذة التحويل، دفعة الترحيل، checkpoint، الحجر، المصالحة، وإيصال rollback. يبقى تحويل صف legacy إلى نموذج Staff مسؤولية worker خاص بالترحيل؛ لا يضيف المنسق mapping عامًا أو SQL لجدول أعمال، ولا تشغله صفحة HTTP. يركبه `StaffModuleFactory::migrationCoordinator()` للأدوات التشغيلية المحروسة فقط.
- **الاستئناف والكتابة المتزامنة:** فتح النافذة وبدء الدفعة يحملان مفاتيح idempotency، ويعمل `resume_token` مع counts تراكمية وبصمة SHA-256 كهوية checkpoint. replay المطابق لا يكتب، وتغيير المحتوى أو رجوع العداد يفشل مغلقًا. وضع `capture` يحرك source watermark مع حدث تدقيق؛ `freeze` و`new_only` يمنعان كتابة legacy. لا ينتقل الوضع إلى `new_only` إلا بعد اكتمال كل الدفعات دون حجر مفتوح وتطابق الأعداد والبصمات.
- **الحجر والرجوع:** الصف الملتبس يسجل مرة في `staff_hr_migration_exceptions` بمفتاح المصدر وكود السبب وبصمة payload، ولا يُخمن. rollback يستدعي executor خاصًا بالترحيل مع manifest من معرفات الموارد المملوكة فقط داخل المعاملة؛ يعيد `legacy_only` ويسجل بصمة الإيصال، ويُبقي النوافذ والدفعات والاستثناءات للتحقيق. لا ينفذ المنسق حذفًا عامًا أو اسم جدول قادمًا من الطلب.
- **التدقيق والتحقق:** كل انتقال جديد يمر عبر `AuditEventWriter` داخل المعاملة؛ الأسباب والمفاتيح والـpayload لا تدخل سجل التدقيق نصًا بل بصماتها. اجتاز `tests/staff_hr_migration_coordinator_integration_test.php` replay/checkpoint/concurrent-write/quarantine/reconciliation/manifest rollback على قاعدة مؤقتة، كما اجتاز bootstrap والصياغة والتدقيق المعماري وتغطية الكتابة.

## ADR-073 — التصحيح التنظيمي الرجعي معاينة ثابتة وقرار مستقل وأثر محدد قابل للعكس

- **الحالة:** معتمد ومنفذ في 2026-08-11، ومثبت على الذاكرة وقاعدة MariaDB مؤقتة تنتهي بـ `_test`؛ لم يُطبّق الترحيل على `educore`.
- **القرار:** يملك `StaffOrganizationCorrectionService` مسارًا واحدًا لتصحيح القوة أو المسمى أو المدير أو مرجع التقويم بأثر رجعي. الطلب الأول يثبت نوع التصحيح ونطاقه والفترة والمرجع المقترح وقائمة العاملين والأيام والطلبات وفترات التقارير في snapshot غير قابل للتعديل؛ لا يصبح أثرًا معتمدًا قبل قرار مستقل. إعادة مفتاح idempotency بالمحتوى نفسه تعيد الإيصال، وبمحتوى مختلف تفشل مغلقة.
- **الفصل والصلاحيات:** لا يستطيع مقدم التصحيح اعتماد طلبه. القرار النهائي متاح فقط لـ`super_admin` حي أو مدير HR فعال مؤرخ في `staff_manager_assignments`، ويعاد فحص الدليل داخل المعاملة. لا تؤخذ الصلاحية أو هوية العامل أو النطاق من المتصفح، ولا يوسع وجود جلسة admin وحده صلاحية الاعتماد.
- **الأثر والرجوع:** الاعتماد ينشر فقط snapshot المجمد كحقائق أثر ملحقة من نوع يوم حضور أو مسار طلب أو فترة تقرير؛ هذه حقائق إعادة احتساب/إسقاط محددة وليست تعديلًا مباشرًا لسجل Attendance أو الطلب أو التقرير. يظل المستهلك المالك مسؤولًا عن إنشاء النسخة التشغيلية الجديدة وإعادة تفويض المورد. الإلغاء يضيف correction عكسيًا جديدًا مرتبطًا بالأصل ويعيد نشر النطاق المجمد نفسه؛ لا يحرر أو يحذف preview أو القرار أو الأثر القديم.
- **التدقيق والخصوصية:** تحفظ الأسباب في سجل Staff الخاص، لكن سجل التدقيق المشترك لا يحمل نص السبب أو snapshot؛ يحمل بصماتهما فقط. الجداول الثلاثة مسجلة كموارد لا تملك direct undo، وتمنع مشغلات MariaDB التحديث والحذف. فشل نشر الأثر أو التدقيق يلغي القرار والآثار في المعاملة نفسها.
- **الواجهة والرجوع التشغيلي:** يضيف `admin/hr_organization.php?tab=corrections` معاينة للأعداد والنطاق قبل القرار، ويستخدم CSRF/PRG وBootstrap modals للقرار والعكس. الرجوع التشغيلي هو إخفاء التبويب وعدم تشغيل المستهلك؛ تبقى الأدلة المضافة ولا تُمحى.
- **التحقق:** اجتاز `tests/staff_hr_organization_correction_test.php` الفصل والصلاحيات والتكرار والنطاق والعكس وفشل المعاملة، واجتاز `tests/staff_hr_organization_correction_integration_test.php` تطبيق الترحيل مرتين وحواجز append-only على قاعدة مؤقتة حُذفت بعد الاختبار، كما اجتازت البوابات المعمارية وتغطية الكتابة وتدقيق واجهة الإدارة.

## ADR-072 — مركز HR يركّب إسقاطات تشغيلية موجزة خلف تدرج Staff ويحافظ على المسارات القديمة

- **الحالة:** معتمد ومنفذ في 2026-08-09 بعد موافقة صريحة على الدمج مع تعديلات صندوق الاعتمادات الموجودة مسبقًا.
- **القرار:** يبقى `admin/hr_center.php` نقطة الدخول القديمة نفسها، ويضيف في وضعي `display|official` تبويب قراءة للخط الزمني وتنبيهات انتهاء الأدلة. الصفحة تركّب `StaffHrTimelineQuery` و`StaffDocumentExpiryService` من `StaffModuleFactory` ولا تضيف SQL أو مستودعًا محليًا. العامل يُختار من قائمة العاملين الفعالين، والفترة تتحقق بصيغة `Y-m-d` وتتحول إلى نافذة نصف مفتوحة قبل الاستعلام.
- **الخصوصية والتعطل:** يعرض المركز نوع/مصدر الحدث ومعرف المورد وحالته وإصداره فقط، وتنبيه الوثيقة يعرض العامل والنوع وتاريخ الانتهاء والحالة/الإصدار. لا يعرض event ID أو عنوان الدليل أو الجهة أو المرفق أو payload خاصًا. فشل مصدر خط زمني يتحول إلى كود تحذير محايد، وفشل إسقاط الانتهاء لا يكشف SQL أو exception ولا يغير البيانات المحفوظة.
- **التوافق والرجوع:** تبقى tabs والطلبات وصندوق الاعتمادات وCSRF/PRG والروابط القديمة كما هي؛ `tab=credentials` يُطبع إلى `timeline` لحماية روابط التنبيه المنشأة قبل الواجهة. في `off|shadow|compare` لا يُعرض التبويب الجديد، وفي `official` فقط تختفي quick actions القديمة وفق العقد القائم. الرجوع هو إخفاء التبويب عبر rollout mode؛ لا migration ولا حذف بيانات.
- **التحقق:** يثبت `tests/staff_hr_center_ui_contract_test.php` حدود الجلسة والفترة والعامل والحقول والتدرج والتوافق، واجتاز مع اختبارات الخط الزمني/الوثائق/الاعتمادات/السجل القديم. اجتازت الصفحة فحص الصياغة، التدقيق المعماري الصارم، تغطية الكتابة، وتدقيق واجهة الإدارة.

## ADR-071 — سجل HR التشغيلي قراءة مقيدة لمورد التدقيق المركزي ولا يملك undo

- **الحالة:** معتمد ومنفذ كسطح قراءة مستقل ومربوط من مركز العمليات الموحد في 2026-08-09.
- **القرار:** `admin/hr_audit.php` يستخدم `Operations/Audit/SystemActivityLogQuery` بدل SQL صفحة مباشر، ويثبت `target_type_prefix=staff_` بصورة ثابتة. توسع الاستعلام المركزي بفلتر prefix مُعلّم ومُمرّر كوسيط SQL؛ prefix غير الصالح ينتج مجموعة فارغة بدل البحث الشامل. تبقى صفحة السجل العام ومسؤولية `UndoManager` كما هما.
- **الخصوصية والصلاحية:** السطح يتطلب جلسة admin قبل الاتصال، ويعرض الوقت والفاعل والعملية وهوية المورد والنتيجة وحالة الاستعادة فقط. لا يعرض `details` أو metadata أو سبب طلب/إجازة أو نص شكوى أو مرفق، ولا يملك POST أو زر undo/redo. تُعاد صلاحية المورد عند أي سطح تفصيلي لاحق.
- **التحقق والرجوع:** يثبت اختبار `system_activity_log_undo_query_test.php` عزل prefix وفشله المغلق، ويثبت `tests/staff_hr_audit_surface_contract_test.php` حدود الصفحة وصلاحيتها وغياب SQL/DDL والبيانات الحساسة. الرجوع هو إخفاء رابط الصفحة؛ لا يُعدل سجل التدقيق أو يمسح أي حدث.

## ADR-070 — واجهة التنظيم والتعيينات تنسق أوامر مؤرخة ولا تملك SQL أو تعديلًا مباشرًا

- **الحالة:** معتمد ومنفذ كواجهة إدارة تدريجية في 2026-08-09؛ لا يطبق migration ولا يغير أي صف في `educore` عند الفتح.
- **القرار:** `admin/hr_organization.php` نقطة الدخول الإدارية للقوى/الوحدات والمسميات والمجموعات وعضوياتها وعلاقات المديرين والتعيينات. تتحقق الجلسة قبل إنشاء الاتصال، وتتحقق من CSRF قبل كل POST، ثم تمرر الحقول إلى `StaffOrganizationService` عبر `StaffModuleFactory` وتستخدم PRG ورسائل عربية مفهومة. لا تستقبل الصفحة دورًا أو مصدرًا أو صلاحية من المتصفح؛ خدمة الأوامر تعيد التحقق من دليل `admin`/`super_admin` الحي وتسجل العملية في معاملة واحدة مع التدقيق.
- **حد القراءة:** أضيف `StaffOrganizationAdministrationQuery` و`StaffOrganizationAdministrationReadRepository` للفصل بين عرض القوائم وبين محول الكتابة. يعيد المحول PDO معرفات وأسماء وفترات وحالات فقط من الموارد المملوكة، ولا يعيد ملف العامل أو سجل التدقيق أو أسباب أو مرفقات. يتحقق الاستعلام من صلاحية المسؤول ويفرض حدًا أقصاه 200 صف قبل قراءة خيارات النماذج والسجل. غياب migration أو القراءة غير المتاحة ينتج رسالة تشغيلية محايدة، لا SQL أو استثناء تقنيًا في الشاشة.
- **التاريخ والرجوع:** الصفحة لا تعرض تعديلًا أو حذفًا لسجل مؤرخ؛ النقل أو التصحيح يضيف فترة لاحقة، وتبقى خدمة التنظيم صاحبة رفض تداخل التعيين الأساسي أو نطاق المدير أو عضوية المجموعة ودورة المدير. الرجوع هو إزالة مدخل القائمة/عدم استخدام الصفحة مع بقاء الخدمات والجداول والتاريخ دون حذف.
- **التحقق:** يثبت `tests/staff_hr_organization_admin_surface_test.php` على SQLite حدود القراءة وصلاحية admin/super-admin والحدود وحقول العرض، ويثبت ترتيب session/CSRF/PRG وغياب SQL وDDL و`confirm`/SweetAlert من الصفحة. كما اجتاز اختبار Bootstrap وفحص الصياغة والتدقيق المعماري الصارم.

## ADR-069 — أدلة مؤهلات العامل وتدريبه ووثائقه سجلات ملحقة غير قابلة للتعديل

- **الحالة:** معتمد ومنفذ ومتحقق في قاعدة اختبار مؤقتة معزولة في 2026-08-09؛ لم يُطبّق على `educore` ولم تُنشأ بيانات تجريبية فيه.
- **القرار:** يملك `StaffDocumentExpiryService` تسجيل الدليل من نوع `qualification` أو `training` أو `document` عبر `StaffCredentialRepository`. جدول `staff_credential_records` سجل أدلة ملحق: كل حفظ جديد يحمل مفتاح idempotency وبصمة payload ونسخة، ولا يُعدَّل أو يُحذف. عند اختلاف دليل يحمل نفس `(staff, kind, credential_key)` يضاف خلفًا مرتبطًا بالسجل السابق؛ لا تغير النسخة السابقة، وتقرأ إسقاطات انتهاء الصلاحية النسخة الحالية فقط. إعادة مفتاح idempotency بمحتوى مختلف تفشل مغلقة، كما يعاد الدليل المطابق بلا كتابة أو حدث تدقيق مكرر.
- **الخصوصية والأثر:** يحتفظ السجل داخليًا بالعنوان وجهة الإصدار ومرجع مرفق عددي فقط، ولا يقبل مسار تخزين أو رابطًا عامًا أو نص مرفق. جميع هذه الحقول وبصمات الحفظ محجوبة من سجل التدقيق؛ الإيصال والخط الزمني والتنبيه لا يعيدون إلا المعرف والنوع والتاريخ والحالة والإصدار. إنشاء الدليل وحدث `AuditEventWriter` يقعان داخل معاملة واحدة، فيفشل الحفظ عند فشل التدقيق. `staff_credential_records` مسجل صراحة كمورد غير قابل لـ direct undo؛ التصحيح لاحقًا يكون بسجل خلف أو إلغاء ملحق.
- **الانتهاء والإشعار:** الانتهاء حالة قراءة محسوبة محليًا في توقيت القاهرة (`expired` أو `expires_today` أو `expires_soon`) ولا يكتب مجدول حالة جديدة. التنبيه يستخدم Outbox المملوك للإشعارات، مفتاحًا idempotent يتضمن السجل والتاريخ والحالة، ونصًا عربيًا محايدًا ورابطًا نسبيًا مع إعادة تفويض عند الفتح. فشل تنبيه دليل لا يمنع بقية التنبيهات ولا يظهر تفصيل العطل.
- **التكامل والرجوع:** `PdoStaffCredentialTimelineEventSource` يضيف فقط ملخصات تاريخ الأدلة إلى عقد الخط الزمني؛ لا يقرأ العنوان أو المُصدر أو المرفق. migration `20260809_staff_hr_credential_expiry.php` إضافية وتبني حواجز MariaDB تمنع التحديث والحذف. فحصها في قاعدة `*_test` مؤقتة أثبت الجدول والمشغلات والسجل الخلف، ثم حُذفت القاعدة. الرجوع التشغيلي هو عدم تركيب واجهة الإدارة/المصدر الجديد؛ لا يحذف السجل أو يغير البيانات القائمة.
- **التحقق:** اجتازت `tests/staff_hr_credential_expiry_service_test.php` و`tests/staff_hr_credential_repository_test.php` و`tests/staff_hr_timeline_query_test.php` و`tests/staff_hr_audit_policy_contract_test.php` على الذاكرة المعزولة، إضافة إلى فحص migration المؤقت وفحوص bootstrap والتدقيق المعماري وتغطية الكتابة.

## ADR-068 — الخط الزمني للعامل إسقاط موحد لأحداث موجزة من مصادر مالكة

- **الحالة:** معتمد ومنفذ كطبقة قراءة في 2026-08-09؛ لا يطبق migration ولا يكتب إلى `educore`.
- **القرار:** يملك `StaffHrTimelineQuery` دمج مصادر `StaffTimelineEventSource` المعلنة صراحة. المصدر يعيد فقط معرف حدث ومورده وتاريخه ونوعه وحالته وإصداره؛ لا يمر سبب إذن أو إجازة، نص شكوى، دليل تأديبي، مرجع مرفق، بيانات صحية، أو أثر مالي إلى الإسقاط العام. يرفض المحول صفًا غير مطابق أو خارج الفترة، يمنع تكرار `(source,event_id)`، ويرتب الأحداث حتميًا بوقت الحدث ثم المصدر/المعرف.
- **التعطل والصفحات:** عطل مصدر واحد أو رده غير الصحيح لا يخفي السجل بصمت؛ يظهر تحذير محايد للمشغل دون نص الاستثناء. الاستعلام ليس حد صلاحية؛ صفحة HR اللاحقة تثبت نطاق المشاهد أولًا، وكل رابط إلى المورد يعيد تفويض المالك. لا يستقبل المصدر دور جلسة أو permission من المتصفح، ولا يوسع قدرته إلى قرار أو تعديل حالة.
- **الملكية والتدرج:** مصادر Staff الحالية هي `PdoStaffAssignmentTimelineEventSource` لسجل التعيينات الأساسية المؤرخة و`PdoStaffCredentialTimelineEventSource` لسجل المؤهلات/التدريب/الوثائق؛ لا يعيد أي منهما أسماء وحدة/مسمى أو ملفًا قديمًا أو عنوان دليل/مصدره/مرفقه. يضيف Attendance وطلبات الإذن/الإجازة والتأديب وارتق مصادرها المنفصلة عبر العقد نفسه عند تركيب لوحة HR؛ لا يضيف محول الخط الزمني SQL مباشرًا إلى جداول وحدة أخرى.
- **التحقق والرجوع:** يثبت `tests/staff_hr_timeline_query_test.php` دمج عدة مصادر، الحد، الترتيب، التكرار، الرد الخاطئ، العطل، وإزالة الحقول الخاصة، كما يثبت مصدر التعيين على SQLite. الرجوع هو عدم تركيب مصدر/صفحة الخط الزمني الجديدة مع بقاء المراجع ومخطط التاريخ دون تغيير.

## ADR-067 — أهلية بوابة العامل لا تتبع الدور النشط وتفصل دليل المدير عن صلاحية القرار

- **الحالة:** معتمد ومنفذ كطبقة قراءة في 2026-08-09؛ لا توجد migration أو كتابة على `educore` ضمن هذا القرار.
- **القرار:** يملك `Application/Portal/StaffPortalEligibilityService` عقد `StaffPortalEligibilityQuery` ويجمع فقط دليل حساب نشط و`staff_profiles` من `StaffPortalEligibilityReadRepository` مع التعيين الأساسي المؤرخ من `StaffAssignmentAtDateQuery`. لا يقرأ `active_role` أو دور الجلسة أو عضويات `user_role_assignments`، فلا يحتاج المعلم أو المختص إلى حساب عامل آخر أو إلى تبديل دوره كي تظهر خدمة العامل. لا تمنح إلا قدرة ثابتة `staff.portal.self_service` للعامل ذي التعيين `active` أو `rehired` الفريد.
- **نطاق المدير:** تضيف طبقة القراءة `staff.portal.manager_approval_inbox` فقط إذا وجدت علاقة مباشر/إداري فعالة تقود فعليًا إلى عامل آخر نشط. تعلو علاقة العامل الصريحة على نطاق الوحدة، وتفشل علاقات الأولوية المتعارضة أو التعيين الأساسي الغامض مغلقة. هذه القدرة مؤشر لعرض صندوق المدير فقط؛ تبقى رؤية طلب بعينه واتخاذ القرار مملوكة لاستعلام/خدمة الاعتماد التي تعيد فحص النطاق عند كل طلب.
- **حدود الهوية والرجوع:** لا تصبح هذه الطبقة نظام مصادقة أو مخزن أدوار أو تفويضًا عامًا، ولا تقبل دورًا أو capability من المتصفح. المصادقة الحالية وصلاحية الصفحة تظل سابقة عليها، وتبقى البيانات التاريخية و`staff_profiles` القديمة خارج تفسير التعيين. الرجوع التشغيلي هو استمرار البوابات الحالية دون استدعاء المحول؛ لا يحذف القرار أي سجل أو مخطط.
- **التحقق:** يثبت `tests/staff_hr_multi_role_portal_contract_test.php` حساب معلم/مختص متعدد الأدوار، وملف عامل بدور مختلف، وعلاقة مدير مباشرة ثم نطاق وحدة ثم تجاوز خاص، مع الوقف والانتهاء والحساب غير النشط والملف الغائب وغموض التعيين. الاختبار SQLite في الذاكرة فقط.

## ADR-066 — خطط الدرجات الجماعية تملك نطاقًا صريحًا وجاهزية مستقلة عن دورة الحالة

- **الحالة:** معتمد ومنفذ في المصدر في 2026-08-09؛ لا تطبق migration تلقائيًا ولا تغيّر بيانات `educore` القديمة.
- **القرار:** تملك `AssessmentSchemeBatchService` إنشاء عائلة خطة لكل صف محدد، وخطة مستقلة لكل ترم، داخل معاملة واحدة ومدققة بمعرف دفعة واحد. تشمل هوية منع التكرار رمز الطلب والحمولة المطبعة للترمات والنطاق والإعدادات، فلا يعيد إرسال معدل مجموعة قديمة بصمت، بينما يبقى الضغط المزدوج لنفس الحمولة آمنًا. يفسر `AssessmentSchemeScopeResolver` وحده نطاق الصف/الفصل للخطط الجديدة، بينما تظل الخطط القديمة متوافقة عبر `subject_grade_assignments` حتى يقرر المسؤول استبدالها صراحة. لا تكتب صفحات الإدارة أو الرصد أو النوافذ إلى جداول النطاق مباشرة.
- **المخطط والترحيل:** تضيف migration `20260809_assessment_scheme_families.php` عائلات الخطط، ونطاقاتها، وسياسة أوزان نهاية العام، وسجل مراجعة للبيانات القديمة؛ لا تنشئ عائلات أو نطاقات أو أوزانًا تخمينية للخطط القديمة. تعالج migration اللاحقة `20260809_assessment_scheme_scope_identity.php` فهرسة النطاق الذي يحتوي `NULL` بصورة متوافقة مع MySQL.
- **الجاهزية ودورة الحياة:** `readiness_status` و`readiness_reason` ليستا حالة نشر. يمكن إنشاء مسودة قبل ربط المادة، ثم تبقى `waiting_for_subject_link` أو `needs_components` حتى يكتمل الربط وتتوازن البنود؛ التفعيل فقط هو الذي يغير `status`، ويرفض تفعيل أي خطة غير جاهزة أو متداخلة. يحدّث مالك روابط المادة الجاهزية في المعاملة نفسها عند إضافة الرابط أو تعطيله أو حذفه، كما تعيد عمليات إضافة/تعديل/تعطيل/حذف البنود الفردية والجماعية حسابها وتدقيقها ذريًا. ترث الخطط القديمة `legacy` افتراضيًا بدل افتراض جاهزيتها، وتظل أي حالة `ready` ورثتها نسخة مبكرة من migration مسجلة للمراجعة دون إعادة كتابة تخمينية.
- **نهاية العام والنطاق التشغيلي:** سياسة العائلة تدعم أي عدد من الترمات بأوزان مجموعها 100% وترفض نتيجة سنوية جزئية. محرك التقرير لا ينشر تقريرًا سنويًا حين ينقص ترم مساهم، كما ترفض نوافذ الرصد وشاشات الرصد والإدخال الإداري أي فصل خارج نطاق الخطة. وإذا فقدت خطة جماعية كل صفوف نطاقها الصريح بسبب تغيير هيكلي، تفشل مغلقة وتصبح بلا نطاق بدل الرجوع إلى نطاق الخطة القديمة أو الاتساع إلى الصف كله. تغيير حالة الخطة لا يقبل من نموذج التعديل، بل يمر فقط بإجراء التفعيل/التعطيل الذي يعيد فحص الجاهزية؛ كما لا تعدل الخطة النشطة أو خطة فردية مرتبطة ببيانات تشغيلية، ويكون التصحيح بخطة بديلة. بنود الخطة النشطة غير قابلة للإضافة أو النقل أو التعديل أو التعطيل أو الحذف، فرديًا أو جماعيًا؛ يلزم تعطيل الخطة أولا ثم إعادة تفعيلها بعد إعادة فحص الجاهزية. كما لا يتغير بند استُخدم بالفعل في نافذة أو درجة أو تقرير حتى بعد تعطيل الخطة؛ التصحيح البنيوي يكون ببند/خطة بديلة كي لا يعاد تفسير التاريخ.
- **التدقيق والرجوع:** جميع عمليات الإنشاء والتفعيل والتعطيل الجماعي تسجل عبر `AuditService` و`UndoManager` في نفس المعاملة. التعطيل الجماعي قابل للعكس: تعيد عملية التفعيل كل خطط الترمات معًا وتمسح `archived_at` للعائلة في دفعة التدقيق نفسها بعد إعادة فحص الجاهزية والتداخل. لا يسمح جدول الخطط بإجراء فردي لتفعيل/تعطيل/نسخ/حذف ترم تابع لعائلة؛ صفحة إدارة المجموعة هي مالك العملية الجماعية. الرجوع التشغيلي هو العودة إلى أسطح الخطط القديمة مع إبقاء العائلات والمراجعات وسجل التدقيق دون حذف تلقائي.

## ADR-065 — استعلام دورة خدمة العامل يعيد فحص الوصول ولا يفسر الحالة الحالية من الملف القديم

- **الحالة:** معتمد ومنفذ في طبقة القراءة في 2026-08-09؛ يستخدم فقط مخطط HR غير المطبق على قاعدة المدرسة.
- **القرار:** يملك `Infrastructure/Organization/PdoStaffAssignmentAtDateQuery` عقدي `StaffAssignmentAtDateQuery` و`StaffAccessEligibilityQuery`. يعيد التعيين الأساسي الفريد الساري في اليوم، مع الوحدة والمسمى وعضويات المجموعة السارية وحالة الخدمة، ويرفض تعدد التعيينات الأساسية بدل اختيار صف. يستمر `Infrastructure/PdoStaffPopulationAtDateQuery` كمحوّل توافق لتعداد الحضور فقط، ويعد العاملين `active` و`rehired` دون الموقوف أو المنتهي؛ بذلك لا ينشئ الحضور وردية أو توقعًا جديدًا لمن لا يملك أهلية عمل حالية.
- **الوصول الحي:** يقبل محوّل الوصول فقط أشكال قدرات Attendance الثابتة `self` و`manager` و`hr` ومراجع المورد الثابتة؛ أي سلسلة مجهولة تفشل مغلقة. في كل استدعاء يعيد قراءة حالة الحساب، وتعيين منفذ الأمر، وتعيين العامل الهدف، وعلاقة المدير الفعالة أو عضوية `admin`/`super_admin` الحالية. المدير يفقد الوصول مع نهاية العلاقة، والعامل الموقوف أو المنتهي يفقده في الطلب التالي حتى إن بقيت جلسة أو عضوية دور نشطة. حساب إداري فعّال لا يملك سجل عامل يبقى مسموحًا لنطاق HR؛ أما حساب له سجل خدمة منتهٍ فلا يحتفظ بالنطاق لمجرد بقاء الدور.
- **حدود الصلاحية:** لا تستقبل الطبقة دورًا أو علاقة من المتصفح، ولا تملك إدارة الأدوار أو حسابات المستخدمين. قراءة `users` و`user_role_assignments` هي دليل هوية حي ومحدود لمحوّل Staff، بينما تظل بوابة البوابة متعددة الأدوار وتفاصيل قدرات الخدمة الذاتية مملوكة لخدمة Portal اللاحقة.
- **التحقق والرجوع:** يثبت `staff_hr_lifecycle_access_test.php` حد النقل، الوقف، العودة، التعيين الثانوي المتزامن، غموض التعيين الأساسي، انتهاء علاقة المدير، انتهاء الخدمة، وإبطال حساب HR المنتهي. لا يكتب الاستعلام أو يطبق migration أو يعدل `educore`؛ الرجوع التشغيلي يعيد قارئي feature-flag للتوافق القديم.

## ADR-064 — أوامر هيكل العاملين مؤرخة ومدققة دون تغيير سجل الماضي

- **الحالة:** معتمد ومنفذ في طبقة التطبيق في 2026-08-09؛ يعتمد تشغيله على migration الهيكل غير المطبقة على قاعدة المدرسة.
- **القرار:** تملك `StaffOrganizationService` وحدها أوامر إنشاء وحدة تنظيمية ومسمى وظيفي ومجموعة سياسة وعضويتها وعلاقة مدير وتعيين صريح مؤرخ. تبقى صفحات الإدارة ومحوّلات HTTP عملاء للخدمة ولا تكتب جداول `staff_org_*` أو `staff_assignments` مباشرة. يظل مسار تعريف/تفويض الاعتماد مملوكًا لخدمة الاعتماد الحالية ولا يمتد إليه هذا المالك.
- **سلامة الفترة والنطاق:** كل فترة تاريخها شامل للطرفين (`valid_to` يشمل يومه). ترفض الخدمة تداخل رمز الوحدة أو المسمى أو المجموعة، وتداخل عضوية فعالة للمجموعة، وتداخل مدير فعّال بنفس النطاق/النوع/الأولوية، وتداخل تعيين أساسي لنفس العامل. التعيين الثانوي المتزامن مسموح صراحةً؛ المؤقت والمنتهي يحتاجان نهاية محددة. لا تستنتج الخدمة قوة أو مسمى أو مديرًا من حقل قديم حر.
- **المدير والحساب:** يثبت adapter داخل حد Staff أن منفذ الأمر حساب نشط يملك دور `admin` أو `super_admin` الحالي، بما في ذلك العضويات الفعالة متعددة الأدوار؛ لا يقبل الدور أو هوية المنفذ من المتصفح. كما يتحقق من عضوية العامل وحساب المدير النشط، ويحجب المدير الذاتي وكل دورة مدير فعالة عند أي حد تاريخ داخل فترة الأمر. قراءة `users` و`user_role_assignments` هنا دليل هوية/صلاحية حي محدود، ولا تصبح نقلًا لملكية حسابات أو بوابة مصادقة موازية.
- **التدقيق والرجوع:** يغلق adapter الموارد ذات الصلة داخل معاملة واحدة، وتكتب الخدمة حدث التدقيق المشترك قبل الالتزام؛ فشل التدقيق يعيد كتابة العمل. تسجل الموارد كسجلات لا تملك تراجعًا عامًا مباشرًا في `AuditPolicyRegistry`؛ النقل أو الوقف أو العودة أو التصحيح اللاحق ينشئ تغييرًا مؤرخًا ومدققًا ولا يمحو التاريخ أو سجلات التوافق.
- **التحقق:** يثبت `staff_hr_organization_service_test.php` رفض منفذ غير مخول وتداخل الفترات ودورات المدير، وسماح التعيين الثانوي، وإرجاع كتابة العمل عند فشل التدقيق. يثبت اختبار bootstrap تركيب العقد وadapter وfactory، ولا يُشغّل أي اختبار على `educore`.

## ADR-063 — توافق تعيينات العاملين سجل مراجعة مؤرخ لا تخمين بيانات قديمة

- **الحالة:** معتمد ومنفذ في المخطط فقط في 2026-08-09؛ لم يطبق على قاعدة المدرسة.
- **القرار:** تضيف migration `20260730_staff_hr_assignment_backfill.php` جدول `staff_assignment_legacy_links` كسجل append-only لقرار ربط مصدر قديم بتعيين مؤرخ أو حجره للمراجعة. لا تقرأ migration نفسها `staff_profiles` أو `staff_job_movements`، ولا تنشئ وحدة/مسمى/تعيين تلقائيًا، ولا تعدل أو تحذف المصدر القديم. يظل إنشاء القرار الفعلي وتشغيل الدفعة والمصالحة مملوكًا لمنسق migration اللاحق داخل معاملة مدققة.
- **الالتباس والتاريخ:** القرار `mapped` لا يقبل إلا مرجع تعيين scalar وتاريخ نفاذ صحيح، بينما `quarantined` لا يقبل إلا مرجع استثناء migration scalar. يحتفظ السجل بمفتاح المصدر وSHA-256 فقط بدل نسخ نص القوة أو المسمى الحر؛ عدم إمكانية المطابقة أو تعددها لا ينتج تعيينًا تخمينيًا. التصحيح البشري ينشئ قرارًا successor جديدًا بتاريخ جديد يشير إلى `supersedes_id`، ولا يحرر الحجر أو التاريخ السابق.
- **ترتيب migrations والعقود:** اسم الملف يسبق أبجديًا migration الهيكل وعمليات الدفعات؛ لذلك `assignment_id` و`migration_batch_id` و`migration_exception_id` مراجع scalar مقصودة لا مفاتيح أجنبية عكسية. يتحقق المنسق اللاحق من وجودها وملكية الدفعة في المعاملة نفسها قبل الإدخال. قيد الذات فقط يمنع حذف سلسلة القرارات، ولا يسمح هذا الاستثناء بوصول SQL عابر للوحدات من خدمة أو صفحة.
- **التدقيق والرجوع:** القرار المسجل لا يقبل update أو delete بفضل triggers، والجدول مسجل في `AuditPolicyRegistry` بلا direct undo مع حجب مفتاح المصدر وhash ومفتاح إعادة المحاولة. الرجوع التشغيلي يعيد القارئ إلى `staff_profiles`/سجل الحركة بواسطة العلم المرحلي ويترك السجل والمصدر كما هما؛ لا يوجد حذف آلي أو backfill إلى `educore` ضمن التطوير.

## ADR-062 — «ارتق» سجل علاقات عاملين سري ومسار حماية مستقل

- **الحالة:** معتمد؛ طبقة المخطط أُضيفت في 2026-08-09 ولم تُطبّق على قاعدة المدرسة.
- **القرار:** تضيف migration `20260730_staff_hr_ertaq.php` تذكرة منفصلة عن الرسائل والأطراف والإسناد والمتابعين وروابط التذاكر وأحداث SLA ومسار الحماية العاجل وقرارات السحب. لا تُحذف التذكرة أو الرسالة أو الرابط أو الحدث حذفًا ماديًا؛ التصحيح والإسناد الجديد والتصعيد والسحب والقرار اللاحق أدلة منفصلة أو انتقالات مقيدة، وتبقى رسالة العامل الأصلية محفوظة عند تحويلها إلى قضية أو مبادرة.
- **السرية والرؤية:** تملك التذكرة درجة سرية، بينما يملك كل طرف ورسالة ورابط ومتحدث نطاق رؤية مستقلًا. يسجل المسار العاجل لقطة التوجيه واستبعاد التعارض في `staff_ertaq_urgent_events`، فلا يستنتج المدير المشكو في حقه أو متابع غير مخول أن تذكرة موجودة. محتوى الرسالة والعنوان وأسباب السحب والإغلاق وإعادة الفتح ولقطات المسار حقول محجوبة في سجل التدقيق، ولا يوجد بحث أو عداد أو إشعار يملك حق قراءة المحتوى خارج خدمة مفوضة لاحقة.
- **حدود الوحدات:** يحتفظ Ertaq فقط بمعرفات scalar للمستخدمين والفرق والقضية التأديبية والمبادرة والإشعار والملف؛ لا ينشئ FK عابرًا لوحدة ولا ينسخ نص شكوى سرية إلى التأديب أو Finance. ستكون خدمات Ertaq هي وحدها مخولة لطلب تحويل التذكرة عبر عقد Discipline/Initiative صغير بعد فحص السرية والصلاحية.
- **مالك الأمر الأول:** يملك `ErtaqTicketService` فتح التذكرة الذاتية، وتثبيت تصنيف/سرية/SLA من `ErtaqTicketPolicyResolver`، والإسناد وسلسلة إعادة الإسناد، والانتقالات العادية فقط. يتحقق `ErtaqTicketAuthorization` حيًا من الممثل ونطاق الهدف قبل الكتابة، بينما يبقى مسار الحماية والسحب والمحادثة وSLA والتنبيهات خدمات مستقلة ولا يقبل الخدمة حالة عامة تقفز إليها.
- **مالك المحادثة والسحب:** يملك `ErtaqConversationService` الرسالة المرسلة غير القابلة للتعديل، والأطراف، والروابط الجماعية/المكررة/المرجعية، وطلب السحب وقراره فقط. يشتق `ErtaqConversationAuthorization` نطاق رؤية كل رسالة/طرف/رابط، ولا يعيد الإيصال أو التدقيق النص الحر. يسجل طلب السحب الحالة السابقة ويستعيدها فقط بقرار مستقل من غير مقدمه، أو يغلق التذكرة بسبب موثق عند قبول السحب؛ لا ينسخ الرابط إلى القضية ولا يحذف الرسالة أو الأطراف.
- **مالك الحماية العاجلة:** يملك `ErtaqUrgentRoutingService` تحويل حالة تذكرة عادية إلى `urgent_protected` وتسجيل وجهة فريق الحماية وإقرار الاستلام فقط. يجمع من سجل الأطراف معرفات المشكو في حقهم/المتعارضين كأقل دليل ممكن، ويمررها إلى `ErtaqUrgentRoutingAuthorization` الذي يحل الفريق والمستلمين؛ إذا أعاد المسار مستلمًا مستبعدًا تفشل الكتابة قبل إنشاء الحدث. لا تظهر لقطة المسار أو قائمة الاستبعاد في الإيصال أو تدقيق الحدث، ولا تستدعي الخدمة Push أو Finance أو قضية أو نظام وصول خارجي.
- **SLA والحماية:** تظل سياسة SLA ووجهة الفريق لقطة على التذكرة/الحدث؛ العامل القادم للتصعيد لا يقرأ من الصفحة ولا يرسل push مباشرة. يملك `ErtaqSlaService` سجلات المهلة المحلية فقط: ينشئ أحداث `created`/`reopened` وسجلات الاستجابة/التجاوز الحتمية من نسخة SLA المثبتة، ويقفل الصف المستحق قبل أن يعيد فحص سلطة عامل الطابور ويفوض وجهة تصعيد حية. التذكرة المغلقة أو المحمية أو المسحوبة، وكذلك المهلة التي اختلفت بصمتها عن نافذة SLA الحالية، تلغى قبل إنشاء وجهة. عند إعادة الفتح يجدد فقط حقلا الموعد من دقائق النسخة المثبتة داخل معاملة انتقال إعادة الفتح نفسها ولا يغير الحالة أو قفل التفاؤل. لا تصبح هذه الخدمة جزاءً أو أثرًا ماليًا، ولا تسجل لقطة التوجيه أو النص الحساس في التدقيق؛ التنبيه المحايد يظل مالكًا منفصلًا لاحقًا ويقرأ حدثًا مطلقًا بعد فحص الرؤية.
- **المرفقات والتنبيه المحايد:** تضيف migration `20260809_staff_hr_ertaq_private_attachments.php` جدول `staff_resource_attachments` كملكية Staff مقيدة حاليًا بتذكرة/رسالة Ertaq فقط، مع مرجع `private:ertaq_attachments/...` وmetadata قابلة للتدقيق لا مسارًا مطلقًا أو URL. يمر `ErtaqAttachmentNotificationService` عبر `ErtaqAttachmentStorage` الذي يستخدم `FileUploadGuard` لملفات PDF/JPEG/PNG حتى 10 MiB، ويحركها إلى `storage/private/ertaq_attachments` باسم عشوائي. لا يتغير أصل المرفق ولا يحذف ماديًا؛ يفشل إدخال metadata أو التدقيق أو enqueue التنبيه فينظف الملف الجديد. يحدد `ErtaqAttachmentNotificationAuthorization` نطاق الرؤية والمستلمين والمسار الداخلي حيًا، بينما النص ثابت ومحايد ولا يحتوي اسم ملف أو مسار أو عنوان/متن شكوى. يسجل تدقيق المرفق قبل enqueue، ويجب أن يشترك adapter المرفق و`StaffNotificationPort` في معاملة PDO المالكة عند ربطهما في factory لاحق؛ download/controller لا ينشأ قبل فحص مستقل للصلاحية.
- **القراءة والواجهة:** يملك `ErtaqInboxQuery` وعقد `ErtaqInboxReadRepository` إسقاطين ضيقين فقط: العامل يقرأ تذاكره ورسائل `requester` الخاصة بها، ومدخل `admin/hr_ertaq.php` يقرأ تذاكر الإسناد المباشر النشط للمستخدم ورسائل `requester`/`assigned_team` فقط. لا يضم الإسقاط هوية طرف أو متابع أو مسار حماية أو مرفق أو جدول وحدة أخرى، ولا يتيح بحثًا عامًا. رابط تذكرة موجودة خارج النطاق يرجع `403` برسالة محايدة وفق Q14، بينما المعرف غير الموجود يرجع `404`؛ لا يعيد أي منهما عنوانًا أو محتوى أو عدادًا. يظل `Presentation/ertaq_portal.php` مكوّن عرض بيانات فقط حتى تربطه بوابات العامل الحالية بمحوّل HTTP مصرح، ولا ينشئ مجلد دور أو مسار رفع/تنزيل جديدًا.
- **التدقيق والرجوع:** الموارد تسجل في `AuditPolicyRegistry` كموارد غير قابلة للتراجع المباشر، وتفشل الخدمة لاحقًا مغلقًا إذا تعذر تدقيق الكتابة. الرجوع التشغيلي يعطل القراء/الكتاب الجدد في بيئة معزولة؛ لا يشغّل migration ولا يحذف تاريخ شكوى في `educore`.

## ADR-061 — التأديب سلسلة قضية وأدلة لا صف جزاء قابل للحذف

- **الحالة:** معتمد؛ طبقة المخطط أُضيفت في 2026-08-09 ولم تُطبّق على قاعدة المدرسة.
- **القرار:** تضيف migration `20260730_staff_hr_discipline.php` سجلات مستقلة للواقعة، والقضية، والأطراف، والتحقيق، والأدلة، والإجراء الاحترازي، والقرار، والتظلم، والتنفيذ، وطلب الأثر المالي، وإعادة الفتح. تحفظ الحالة الرسمية في سجلات ذات مفاتيح إعادة محاولة وبصمات حتمية، وتمنع قاعدة البيانات الحذف المادي للأدلة والقضايا والقرارات والتظلمات والتنفيذ وإعادة الفتح؛ التصحيح يتم بسجل لاحق أو قرار عكسي مؤرخ.
- **العدالة والخصوصية:** تسجل القضية مستوى السرية، وأطرافها ونطاق رؤيتهم وتعارضاتهم، وتفصل معرفات مُعِدّ القرار وصاحبه، كما تمنع قاعدة البيانات المراجع من أن يكون صاحب القرار النهائي أو مقدم التظلم. تحفظ الأدلة الوصفية فقط تحت `storage_area=private` ولا تنشئ رابطًا عامًا أو مسار رفع موازٍ؛ يظل الرفع الفعلي لاحقًا مسؤولًا عن `FileUploadGuard` والتخزين الخاص.
- **حد التطبيق:** يمر فتح الواقعة والقضية وتعديل الأطراف عبر `DisciplineCaseService` فقط، الذي يعتمد على `DisciplineCaseRepository` و`DisciplineCaseAuthorization` وعقد التدقيق المشترك. لا تحمل خدمة التطبيق PDO أو الدور المرسل من المتصفح، ولا تملك التحقيق أو القرار أو التنفيذ.
- **التحقيق والمرفقات:** يمر تعيين المحقق وإتمامه وسلسلة الأدلة عبر `DisciplineInvestigationService` وحده. يتحقق من أن المحقق ليس مسجل الواقعة أو فاتح القضية، ويحفظ المرجع الخارجي كنوع/معرف فقط. يمر الملف بعد التفويض عبر `LocalDisciplineEvidenceStorage` و`FileUploadGuard` إلى `storage/private/discipline_evidence`؛ فشل قاعدة البيانات أو التدقيق يزيل الملف الجديد، ولا يظهر مرجع التخزين في إيصال الخدمة.
- **القرار والتبليغ:** ينشئ `DisciplineDecisionService` قرارًا مقترحًا فقط بعد تحقيق مكتمل وبفصل المُعدّ عن مسجل الواقعة وفاتح القضية والمحقق. يثبت نسخة `discipline_case` من مسار الاعتماد المشترك ويضيف معرف القرار إلى سياق النسخة، ثم يربط instance بالقرار داخل المعاملة نفسها. يملك `DisciplineDecisionApprovalOutcomeHandler` وحده تحويل المقترح إلى قرار صادر أو ملغى عند نتيجة الاعتماد، ويتحقق ثانيةً من أن المعتمد ليس العامل محل القضية أو أي صاحب دور متعارض.
- **الإشعار والاستلام:** بعد الإصدار يسجل المعالج نية إشعار محايدة فقط عبر `StaffNotificationPort`، من دون سبب القرار أو رمز الجزاء أو الدليل. تعذر إنشاء النية لا يحذف القرار الصادر؛ يسجل حالة `delivery_failed` وتدقيقًا غير حساس، بينما الاستلام لاحقًا مقصور على العامل محل القضية وذو إعادة آمنة. لا ينشئ أي من هذين المسارين أثرًا ماليًا؛ تبقى حقيقة Finance وخط الانعكاس لمالك مستقل لاحق.
- **التظلم والإجراء المؤقت:** يقرأ `DisciplineAppealService` نافذة التظلم وSLA ومبدأ وقف التنفيذ من لقطة سياسة القرار نفسه، فلا يطبق قيمة قانونية ثابتة أو سياسة حالية متغيرة. لا يقدم التظلم إلا العامل محل القضية، ولا يراجعُه صاحب القرار أو مسجل الواقعة أو فاتح القضية أو المحقق أو مقدم التظلم. الانسحاب أو انتهاء مهلة المراجعة يعيدان القضية إلى `decided` كسجل تاريخي؛ أما uphold/amend/revoke فتسجل نتيجة مستقلة ولا تعدل القرار الصادر في مكانه. الإجراء المؤقت يمر بطلب ثم تفويض ومراجعة منفصلة، ويسجل نية أثر وصول فقط ولا ينفذ أي صلاحية خارجية.
- **إعادة الفتح:** تضيف migration `20260809_staff_hr_discipline_appeal_reopen_hardening.php` ارتباطًا مقيدًا بين طلب إعادة الفتح وقرار قبول/رفض لاحق append-only، مع سبب حل للإجراء المؤقت وحراس انتقالات. الدليل الجديد يبقى من نفس القضية؛ لا يعاد فتح الحالة إلا بقرار مستقل من غير طالب إعادة الفتح، ثم تعود إلى `reopened` لتبدأ دورة تحقيق جديدة. لا تُعدّل migrations أو البيانات الحالية أثناء الطلب.
- **حدود الوحدات:** إشارات الحضور أو الشكاوى أو المستندات تبقى مراجع غير قابلة لتغيير مصدرها. حقيقة Finance في `staff_discipline_finance_effects` تحمل كودًا ووحدات ومفتاح أثر فقط، ولا تحتوي مبلغًا أو جدول رواتب أو اتصالًا مباشرًا بمالية؛ الإرسال والتنفيذ سيبقيان عقدًا صريحًا في خدمة لاحقة.
- **حقيقة Finance وعكسها:** يقرأ `DisciplineFinanceEffectService` من لقطة القرار الصادر فقط المفتاح `finance_effect` الذي يثبت `fact_type` و`effect_code` و`units` ونافذة التاريخ و`effective_period` الواحد. يتحقق من تطابق الفترة مع النافذة، ويبني مفتاح أثر ومفتاح إعادة محاولة حتميين، ثم يحفظ النية في `staff_discipline_finance_effects` داخل المعاملة والتدقيق نفسها؛ لا يمرر إلى `PayrollImpactGateway` مبلغًا أو سبب قرار أو دليلًا. الاعتماد النهائي قد يحفظ هذه النية المحلية فقط، أما عامل مستقل فيستأجرها ويرسلها لاحقًا. رفض Finance لفترة مقفلة يصبح `rejected` نهائيًا ولا يعيد الإرسال. عند تظلم `amended` أو `revoked` يُلغى الأثر غير المرسل، أو تُنشأ حقيقة عكسية جديدة مرتبطة بالأثر المقبول؛ لا يعدل الأصل.
- **واجهة التوافق:** يبقى `admin/disciplinary.php` رابطًا وإجراءً قديمين صالحين في أوضاع الرجوع، لكن لا يحذف أي سجل من `staff_disciplinary`؛ يحتفظ باسم `delete_action` ليعطي رسالة حماية متوافقة بدلاً من حذف مادي. عند `display` أو `official` يستعمل فهرسًا منفصلًا `DisciplineCaseAdminQuery` يعرض بيانات تشغيلية غير حساسة فقط. لعدم وجود مفوض صلاحيات تفاصيل القضية بعد، يفشل الفهرس مغلقًا على `normal` ويحجب تمامًا القضايا `restricted` و`highly_restricted` بدلاً من تخمين أن كل مدير مخول. يبقى فتح أو تعديل الواقعة الجديدة ضمن خدمات القضية المفوضة، لا ضمن صفحة قائمة عامة.
- **الرجوع:** قبل أي تطبيق فعلي تُؤخذ نسخة بيئة معزولة، ويكون الرجوع التشغيلي بإيقاف القراء/الكتاب الجدد لا بحذف السجل القانوني. لا تُشغّل migration على `educore` ضمن أعمال التطوير أو الاختبارات.

## ADR-060 — عامل الإرسال المالي للإجازات يستأجر الأثر المستحق ولا يملك المالية

- **الحالة:** معتمد ومنفذ في 2026-08-09.
- **القرار:** يضيف `LeaveFinanceEffectService::dispatchDueEffects()` دورة تشغيل مستقلة تنتقي فقط حقائق `leave_request` المتجهة إلى `finance` ذات الحالة `pending` أو `retry` المستحقة، أو عقد `processing` المنتهي، وبحد أقصى ثابت للدفعة. لا تعد القراءة حجزًا: يبقى `claimEffect()` تحديثًا شرطيًا ذريًا، لذلك إذا سبق عامل آخر إلى الحجز تعود النتيجة متخطاة ولا تستدعي Finance. يعالج العقد المنتهي كإعادة محاولة محتملة؛ تحمي `effect_key` الحتمية بوابة Finance من ازدواج الإرسال الخارجي.
- **حد Finance:** أداة CLI `tools/staff_leave_finance_effect_dispatcher.php` تقرأ فقط افتراضيًا. لا تسمح بـ`--apply` إلا مع اسم قاعدة مطابق للاتصال، actor موجب للتدقيق، وbootstrap نسبي يقدمه مالك Finance ويرجع `PayrollImpactGateway` أو factory له. لا توجد بوابة افتراضية أو كتابة إلى جدول Finance؛ غياب التركيب يفشل مغلقًا قبل أي إرسال خارجي.
- **التدقيق والرجوع:** كل claim/قبول/retry يستمر داخل خدمة Staff المدققة، وتتحول الاستجابة المرفوضة أو غير المتاحة إلى `retry` بمفتاح الأثر نفسه من دون تسريب رسالة البوابة أو payload حساس. إيقاف العامل يترك الآثار المؤجلة كما هي؛ لا يحذف أثرًا مقبولًا ولا يعدل راتبًا، وأي تصحيح لاحق يظل حقيقة Finance عكسية مملوكة للمالية.

## ADR-059 — استثناء حد التشغيل للإجازة دليل مستقل ومقيد بنسخة الطلب

- **الحالة:** معتمد ومنفذ في 2026-08-08.
- **القرار:** لا تكفي علامة `staff_leave_requests.staffing_override_granted` للسماح بالإرسال؛ هي إسقاط توافق فقط. يسجل `LeaveStaffingOverrideService` قرارًا واحدًا غير قابل للتعديل في `staff_leave_staffing_overrides` لكل `(leave_request_id, request_hash)`، مع سبب إلزامي، المدير المخوّل، مفتاح إعادة المحاولة، لقطة آمنة لمتطلبات التشغيل، وبصمة requirement حتمية تشمل نسخة السياسة والنطاق ومؤشرات السعة/فترة الحظر الحية. تملك `LeaveStaffingOverrideAuthorization` التحقق من أدوار القرار الحالية عبر عقد `ApprovalRoleAssigneeQuery` وتلتقط الأدوار المطابقة في السجل.
- **السلامة:** لا ينشئ قرار الاستثناء حركة رصيد أو طلب موافقة أو أثر حضور أو Finance. يعيد `LeaveRequestService` فحص السياسة عند الإرسال، ثم يقبل فقط قرارًا معتمدًا يطابق بصمة الطلب وبصمة متطلب التشغيل الحالية؛ تغير المسودة أو السعة أو سياسة التشغيل يجعل القرار السابق غير صالح. القاعدة الصلبة أو فترة الحظر غير القابلة للاستثناء تفشل مغلقًا ولا تتحول إلى صلاحية مدير.
- **التدقيق والرجوع:** سبب القرار ولقطة التقييم حقول حساسة محجوبة في التدقيق، وسجل القرار لا يخضع لـ direct undo. تعديل المسودة يصفر إسقاط التوافق فقط ولا يحذف القرار التاريخي؛ يتطلب الطلب المعدل قرارًا جديدًا. الرجوع التشغيلي هو تعطيل قارئ/كاتب المسار بعد حفظ الأدلة، وليس حذفًا لسجل التفويض.

## ADR-058 — قرار اعتماد الإجازة النهائي يملك التسوية الذرية للأثر التشغيلي

- **الحالة:** معتمد ومنفذ في 2026-08-08.
- **القرار:** يبقى `ApprovalWorkflowService` محايدًا لنوع المورد، ويوجّه `StaffApprovalOutcomeRouter` القرار النهائي فقط إلى مالك المورد: `PermissionApprovalOutcomeHandler` للإذن و`LeaveApprovalOutcomeHandler` للإجازة. يقفل معالج الإجازة الطلب والعامل ودليل حركة الرصيد، ثم يستهلك حجز الإجازة/التمديد أو يحرره عند الرفض. أما العودة المبكرة والإلغاء فلا يحجزان رصيدًا جديدًا؛ وبعد اعتماد كل منهما ينشئان حركة `restore` غير قابلة للتعديل تشير إلى استهلاك الطلب الأب ولا يمكنها تجاوز وحداته.
- **الحضور وFinance:** بعد تثبيت حالة الطلب داخل المعاملة نفسها، ينشر المعالج حقيقة يوم متأثر عبر `AttendanceCoverageChangeGateway` حتى يقرر مالك الحضور إعادة الحساب أو فتح الفترة المقفلة صراحة. ثم يحفظ فقط حقيقة Finance في طابور Staff عبر `LeaveFinanceEffectQueue`؛ لا يستدعي Finance مباشرة ولا يكتب أي جدول مالي. تركيب `leaveFinanceEffectQueue()` مخصص للاعتماد النهائي ولا يرسل خارجًا؛ الإرسال التشغيلي سيظل مسؤولية عامل مستقل مع بوابة Finance.
- **قراءة التغطية والرجوع:** تعرض قراءة الحضور طلبات الإجازة الحديثة المعتمدة كفترات تغطية، وتطرح نافذة العودة المبكرة/الإلغاء المعتمدة من طلبها الأب. يترك فشل التدقيق أو الأثر الخارجي أو الحضور المعاملة غير مكتملة، فلا يعتمد الطلب جزئيًا. لا توجد كتابة عكسية للسجل؛ كل تصحيح هو حركة رصيد أو حدث حضور أو حقيقة مالية مضافة بمفتاح حتمي.

## ADR-057 — شؤون العاملين ترسل حقائق إجازة إلى Finance ولا تحسب راتباً

- **الحالة:** معتمد ومنفذ في 2026-08-08.
- **القرار:** يملك `LeaveFinanceEffectService` تحويل قرار الإجازة النهائي إلى حقائق وحدات فقط عبر `PayrollImpactGateway`. يستخرج كود الأثر ووحدة الإجازة من لقطة السياسة المعتمدة للطلب، ويقسم الحقيقة حسب شهر كل يوم عمل؛ لا يقرأ السياسة الحالية ولا يرسل مبلغاً أو سبباً أو مرفقاً طبياً إلى Finance.
- **الانعكاس والهوية:** الإجازة والتمديد يرسلان وحدات موجبة، بينما الإلغاء والعودة المبكرة يرسلان وحدات سالبة تحت نفس كود السياسة ودليل اتجاه صريح. لكل طلب/شهر/اتجاه مفتاح أثر ومفتاح إعادة محاولة حتميان؛ إعادة المحاولة لا تنشئ حقيقة ثانية، وFinance هو المالك الوحيد لترجمة الكود إلى راتب أو لرفض فترة مقفلة أو إنشاء قيد عكسي.
- **التشغيل والتدقيق:** تحفظ النية أولاً في `staff_external_effects` داخل معاملة Staff وتدقيق مشترك، ثم تستأجر عملية الإرسال الحقيقة لمدة محددة وتعيدها إلى retry عند تعذر أو رفض بوابة Finance. لا تصل طبقة Staff إلى أي جدول Finance، ولا يحدث undo مباشر للأثر الخارجي؛ يظل القبول والترحيل والعكس المالي مملوكاً لFinance.
- **الرجوع:** إيقاف عامل الإرسال يترك الحقائق المؤرشفة غير المعالجة قابلة لإعادة المحاولة بالمفتاح نفسه ولا يعدل الراتب. لا يحذف سجل الإجازة أو الأرصدة أو الأثر المالي المقبول.

## ADR-057 — سجل عمليات الطلاب سطح مستقل والتراجع فيه مقيد بالسجل المرتبط

- **الحالة:** معتمد ومنفذ في 2026-08-08.
- **القرار:** أزيل تبويب سجل العمليات من `admin/students.php` وأصبح `admin/student_operations.php` سطح القراءة والإدارة المستقل لكل أحداث شؤون الطلاب المسجلة في بنية التدقيق المشتركة. يملك `StudentOperationLogQuery` تعريف نطاق الأحداث الطلابية والفلاتر والإحصاءات، وتمنح الصفحة لمدير شؤون الطلاب دون بوابة الأخصائي محدودة النطاق.
- **سياق العام الدراسي (2026-08-09):** تحفظ `activity_logs.academic_year_id` العام المختار وقت تنفيذ العملية من سياق التدقيق المشترك، وتقيّد `student_operations.php` القائمة والإحصاءات وخيارات الفلاتر والتحقق من التراجع وإعادة العمل بالعام الذي يختاره المستخدم من الشريط العلوي. يبقى `activity_logs.php` سجل النظام الموحد غير المقيد بعام. يرحّل `20260809_activity_log_academic_year_context.php` السجلات القديمة من تفاصيل التدقيق أو الكيان السنوي المرتبط ثم من نطاق تواريخ العام عندما يتوافر، وتبقى السجلات التي يتعذر إثبات عامها بلا نسبة بدل تخمين عام نشط.
- **سلامة التراجع:** لا تنفذ الصفحة SQL عكسياً ولا تنشئ مسار تراجع خاصاً بها؛ تقبل زوجاً مطابقاً من `activity_logs.id` و`undo_log.id` داخل نطاق الطلاب، ثم تفوض إلى `UndoManager` المشترك. تعرض كل عملية زر تراجع، لكنه يكون معطلاً مع سبب واضح إذا لم تكن العملية مرتبطة بسجل تراجع، أو اكتمل تراجعها، أو صنفت غير قابلة للتراجع. يظل فحص التعارض والمعاملة والدفعة الذرية تحت المالك المشترك.
- **حدود الاختصاص:** يستبعد سجل شؤون الطلاب عمليات درجات الطالب والرصد والتقييمات وحساب الطالب وحالة حسابه، حتى إذا صدر الحدث من مسار مشترك أو حمل هدفًا عامًا من نوع `student`. لا يتغير مالك الكتابة أو سجل التدقيق؛ تبقى هذه الأحداث كاملة في `admin/activity_logs.php` بوصفه سجل النظام الموحّد.
- **التراجع الموحّد:** يعرض سجل النظام حالة التراجع لكل حدث، ويتحقق من زوج `activity_logs.id` و`undo_log.id` نفسه قبل تفويض التنفيذ إلى `UndoManager`. التنفيذ من السجل الموحّد مقصور على الدور النشط `super_admin` لأن النطاق يعبر كل الوحدات، بينما تبقى الأزرار لدى بقية مشاهدي الصفحة معطلة وموضحة السبب. لا يسمح المسار بتراجع جزئي للدفعة أو تجاوز سياسة المورد أو فحص التعارض.
- **التوافق والرجوع:** تبقى بيانات التدقيق والتراجع ومفاتيحها دون تغيير، وتضاف الصلاحية عبر migration جمعي قابل لإعادة التشغيل. يمكن إعادة رابط السجل إلى قائمة الطلاب لإرجاع العرض فقط، لكن لا يعاد الاستعلام القديم المقيد بـ`target_type = student` ولا يسمح بتراجع غير مرتبط أو جزئي.

## ADR-056 — صفحات الإجازات القديمة تمر عبر حد توافق مملوك لشؤون العاملين

- **الحالة:** معتمد ومنفذ في 2026-08-08.
- **القرار:** تظل الروابط والحقول العامة في `admin/leaves.php` و`admin/leave_balances.php` متوافقة أثناء الترحيل، لكن الصفحتين لا تنشئان `StaffLeaveService` ولا تستدعيان فحص/تهيئة بنية قاعدة البيانات في الطلب. ينشئ `StaffModuleFactory` خدمة `LegacyLeaveCompatibilityService`، التي تعتمد على عقد `LegacyLeaveGateway`، ويكون `StaffLeaveLegacyGateway` هو الجسر المؤقت الوحيد إلى المالك القديم المدقق.
- **السلامة:** لا يوجد SQL أو DDL في الصفحتين أو الجسر الجديد. تبقى كتابة سجلات `staff_leaves` وإعدادات الرصيد وأرصدة الملفات تحت المعاملات وسجل التدقيق المشترك للمالك القديم إلى أن يكتمل تحويل البيانات والمسار الذاتي الجديد صراحة. أخطاء التحقق المعروفة فقط تظهر بلغة مفهومة؛ أما الاستثناءات غير المتوقعة فتسجل في الخادم برقم مرجعي ولا تعرض تفاصيل SQL أو الاستثناء للمستخدم.
- **الرجوع:** يمكن إرجاع تركيب المصنع إلى الجسر السابق عند عيب مثبت، مع إبقاء فحص البنية وقت التشغيل محذوفاً؛ لا تعاد أي تهيئة schema داخل GET/POST. لا يتغير مخطط البيانات أو السجلات بسبب هذا القرار.

## ADR-054 — تعيين المعلم لا يحمل تصنيفاً بديلاً غير تشغيلي

- **الحالة:** معتمد ومنفذ في 2026-07-30.
- **القرار:** يتحدد تعيين المعلم بالعام والنطاق الأكاديمي وحالة التفعيل وصلاحيتي الرصد والمراجعة فقط. أزيل خيار «معلم بديل» من واجهة الإدارة وعقود القراءة والكتابة والتدقيق والبيانات التجريبية لأنه لم يكن يغير أي صلاحية أو مسار تشغيلي.
- **المخطط:** يحذف migration مستقل ومحروس العمود `teacher_subject_assignments.is_substitute`. تبقى migrations التأسيسية المطبقة كما هي كسجل تاريخي غير قابل لإعادة الكتابة.
- **الرجوع:** يمكن إعادة العمود بقيمة افتراضية `0` عبر أمر الرجوع الموثق داخل migration، لكن القيم التاريخية لا تستعاد لأنها حذفت صراحة ولم تكن ذات أثر تشغيلي.

## ADR-051 — كتابات شؤون الطلاب ذرية وتحمي التاريخ والمراجع الرسمية

- **الحالة:** معتمد ومنفذ في 2026-07-30.
- **الحضور:** تملك `StudentAttendanceService` حفظ حضور فصل في يوم واحد لكل من الإدارة والمعلم. تتحقق الخدمة من التاريخ والعام والقائمة المقفلة كاملة، وتحدّث أو تضيف سجلات الطلاب الحاليين دون حذف سجلات اليوم أو الفصل حذفاً جماعياً؛ وجود سجل تاريخي للطالب في فصل أو عام آخر يفشل مغلقاً. تحفظ بيانات العمل والتدقيق والتراجع داخل المعاملة نفسها.
- **نقل الفصل:** تملك `StudentProfileCommandService::applyClassTransfer()` نقل الطالب بين الفصول. نقل الدفعة من `admin/class_lists.php` يستخدم معاملة و`batch_id` واحداً يشمل `users` و`student_profiles` و`student_enrollments` ودرجات الرصد وسجل النقل؛ لا يسمح بتراجع يعيد جدولاً واحداً ويترك بقية الحالة على الفصل الجديد. طلبات الأخصائي تبقى في دورة الموافقة الحالية وتستخدم المالك نفسه بعد الاعتماد.
- **العلاقات:** تملك `StudentRelationshipService` ربط وفصل الأشقاء وصلات القرابة ثنائياً مع القفل والتدقيق داخل المعاملة. صفحات الطلاب والأشقاء لا تكتب جداول العلاقات مباشرة ولا تعرض الطلاب المؤرشفين في أسطح البحث والتشغيل.
- **الأرشفة والحذف النهائي:** الأرشفة اللينة هي المسار المعتاد وتحفظ التاريخ. الحذف النهائي بعد مهلة التأكيد لا يعمل إذا وُجد قيد أو حضور أو تقييم أو درجات أو مالية أو نقل أو ترحيل أو طلب تعديل أو مرجع طلابي غير مصنف. توجد قائمة صريحة فقط لتوابع ملف الطالب المسموح بإزالتها؛ أي جدول طلابي جديد غير مسجل يفشل مغلقاً حتى تُقرر سياسته.
- **الإخراج:** تستبعد الإفادات والملفات والكروت والتصدير الطلاب المؤرشفين، وتعيد تطبيق نطاق الفصول عند وجوده. حقول وصيغ التصدير وخيارات الكروت مقيدة بقوائم سماح، وتُحيد بادئات صيغ الجداول الممتدة قبل إنشاء Excel/CSV.
- **الرجوع:** يمكن إزالة تفويض نقاط الدخول إلى الخدمات لإرجاع الكود، لكن لا يُعاد مسار الحذف الجماعي للحضور أو النقل الجزئي. دفعات النقل والحضور القابلة للتراجع تستخدم نظام التراجع المشترك؛ الحذف النهائي يبقى أثراً غير قابل للاستعادة ومحكوماً بالموانع السابقة.

## ADR-050 — الدرجات سجلات مستقلة وتدار مركزيًا مع استثناء حذف نافذة للسوبر أدمن

- **الحالة:** معتمد في 2026-07-29.
- **القرار:** `admin/assessment_marks.php` هو سطح الإدارة المركزي لدرجات الطلاب الأصلية عبر العام والمرحلة والصف والفصل والمادة والخطة والبند والأسبوع ونافذة الرصد. تستخدم القائمة قراءة مقسمة على الخادم، وتملك `AssessmentMarkAdministrationService` فقط أوامر التصحيح والحذف الاستثنائي.
- **عرض الشيت:** `admin/assessment_marks_sheet.php` سطح مصفوفي مستقل يختار الصف والترم ثم يعرض كل خطة مادة كتبويب مصنف سفلي، والطلاب كصفوف والمكوّنات المجمعة حسب الأسابيع كأعمدة. يبقى `admin/assessment_marks.php` سجل الإدارة التفصيلي ولا تستبدله صفحة الشيت. تعتمد الواجهة محرك Tabulator `6.5.0` المرخّص MIT والمثبت محليًا داخل `assets/vendor/` لتوفير التمرير الافتراضي، الأعمدة المجمدة، عناوين الصفوف والأعمدة، تحديد النطاق، والتنقل والتحرير بلوحة المفاتيح دون CDN أو إطار تطبيق جديد. يتيح الشيت تعديل الخلية وحفظها تلقائيًا، ونسخ/لصق ومسح نطاق أو تعديل خلايا وصفوف وأعمدة؛ عمليات النطاق ذرية بحد 200 خلية، والحذف الفعلي مؤكد بمودال ومقصور على `super_admin`. تمر كل الكتابات إلى `AssessmentMarkAdministrationService` نفسه تحت دفعة تدقيق وتراجع واحدة، ولا تعرض صفحة الشيت كلمات مرور أو تحفظ درجات في تخزين المتصفح أو تنشئ مسار قواعد أعمال موازياً.
- **إنشاء الخلية والتزامن:** لا تنشئ الخلية الفارغة سجلًا إلا إذا أعاد الخادم التحقق داخل المعاملة من نافذة واحدة فقط مفتوحة وضمن وقتها وتطابق الخطة والبند والأسبوع وفصل قيد الطالب الحالي؛ انعدام المرشح أو تداخل مرشحين يفشل مغلقًا. يحمي القيد الفريد خانة الطالب، وتُرسل حالة متوقعة للقيمة والحالة والملاحظة ووقت التحديث؛ التغيير المتزامن المختلف يعيد تعارضًا بدل الاستبدال الصامت، بينما إعادة المحاولة التي وصلت فيها النتيجة المطلوبة سابقًا تعد نجاحًا idempotent بلا سجل تدقيق مكرر.
- **ملكية البيانات:** الدرجة سجل أكاديمي أصلي يعرّفه الطالب والبند والأسبوع والعام والترم، بينما نافذة الرصد غلاف صلاحية وزمن وليست مالكة للدرجة ولا يوجد `window_id` داخل `student_marks`. لذلك لا يؤدي حذف نافذة إلى حذف درجات نطاقها، ولا يضاف حذف متسلسل ضمني قد يمس درجات تقع ضمن أكثر من نافذة.
- **الصلاحيات:** يستطيع مستخدم صفحة الإدارة تصحيح درجة غير مقفلة مع سبب إلزامي. تعديل درجة مقفلة، حذف درجات أصلية، وحذف نافذة ما زالت تحتوي درجات أو كانت مقفلة متاح فقط عند تفعيل دور `super_admin` والتحقق منه عبر `SystemAdministratorRoleService`. تبقى النافذة المفتوحة غير قابلة للحذف حتى تُغلق.
- **الحذف الاستثنائي للنافذة:** يتطلب السبب وكتابة اسم النافذة كاملًا، ويحذف سجل `assessment_windows` فقط مع عرض عدد الدرجات التي ستبقى. يستطيع السوبر أدمن حذف الدرجات نفسها من الصفحة المركزية باختيار صريح محدود؛ لا توجد عملية غامضة «احذف كل ما يطابق نطاق النافذة».
- **التدقيق والتراجع:** تصحيح الدرجات وحذفها وحذف النافذة الاستثنائي يتم داخل معاملات ذرية ويسجل عبر `AuditService` و`UndoManager` تحت `batch_id`، مع استمرار `student_mark_audit` كسجل تخصصي للدرجة. فشل التدقيق يلغي كتابة العمل.
- **التقارير:** نسخ التقارير المنشورة لقطات مستقلة لا تتغير عند تصحيح أو حذف الدرجة الأصلية أو نافذة الرصد. تعرض الواجهة الأثر وتحيل المستخدم إلى إلغاء النشر أو إعادة النشر صراحةً.
- **الرجوع:** يمكن إزالة رابط الصفحة ومسار الاستثناء مع إبقاء الجداول دون migration. يمكن التراجع عن كل دفعة من نظام التراجع المشترك ما لم يقع تعارض لاحق.

## ADR-049 — نوافذ الرصد تتبع دورة حالة صريحة ومحكومة بالخادم

- **الحالة:** معتمد في 2026-07-29.
- **القرار:** تملك `AssessmentWindowLifecycleService` انتقالات نوافذ الرصد: `draft → open → closed → locked`، مع السماح بـ`closed → open` وبـ`locked → open` فقط عبر صلاحية `reopen_window`. لا يسمح الإنشاء إلا بمسودة أو نافذة مفتوحة، ولا تعرض صفحة الإدارة ثلاثة أزرار حالة متعارضة؛ تعرض زر إدارة واحدًا والانتقالات الصالحة للحالة الحالية.
- **المعنى التشغيلي:** `open` وحدها تسمح للمعلم بالرصد ضمن المواعيد، و`closed` توقف الرصد وتسمح بالمراجعة، و`locked` اعتماد نهائي يمنع الرصد والمراجعة وتعديل الإعدادات والحذف. القفل يتطلب سببًا، وإذا كانت النافذة تتطلب مراجعة فيمنع ما دامت أي درجة غير معتمدة. إعادة الفتح تتطلب سببًا وموعد إغلاق جديدًا، وإعادة فتح المقفلة تتطلب صلاحية خاصة.
- **التزامن:** يقفل انتقال الحالة سجل النافذة داخل معاملة. يعيد حفظ المعلم ومراجعة الدرجات قفل النافذة وفحص حالتها داخل معاملة الكتابة، ولذلك يفوز أول كاتب ويُرفض الآخر دون حفظ جزئي. تعرض النوافذ المفتوحة ذات الموعد المستقبلي كـ«مجدولة» وذات الموعد المنتهي كـ«منتهية زمنيًا» دون كتابة خفية أثناء GET.
- **الدفعات والحذف:** الإغلاق الجماعي يقبل نوافذ مفتوحة فقط ويرفض الدفعة المختلطة كاملة قبل الكتابة. لا تحذف العمليات العادية أو الجماعية نافذة مقفلة أو ذات درجات؛ الاستثناء الفردي المحكوم للسوبر أدمن الذي يحفظ الدرجات الأصلية مملوك لـADR-050.
- **التدقيق والتراجع:** كل انتقال يسجل لقطة فعلية من `assessment_windows` عبر `AuditService` و`batch_id` داخل المعاملة نفسها. لا تدخل أعمدة الربط المشتقة في لقطة التراجع. تغيير سياسات التعديل أو المراجعة بعد وجود درجات ممنوع حتى لا يُتجاوز شرط الاعتماد.
- **الرجوع:** يمكن إعادة الصفحة إلى الأزرار القديمة وإزالة استدعاء الخدمة، لكن حالات البيانات تبقى من القيم الأربع المتوافقة ولا تحتاج migration. يمكن التراجع عن انتقال منفرد عبر نظام التراجع المشترك إذا لم يحدث تعارض لاحق.

## ADR-048 — إلغاء نشر التقرير يحذف اللقطات كدفعة قابلة للتراجع

- **الحالة:** معتمد في 2026-07-29.
- **القرار:** يظل الإخفاء إجراءً غير تدميري يحتفظ بنسخ الطلاب، بينما يملك `AssessmentEngine::unpublishReportWindow()` الإجراء الصريح «إلغاء النشر وحذف النسخ». يقفل نافذة التقرير ونسخها، يحذف تفاصيل النسخ ثم رؤوسها، ويعيد النافذة إلى حالة غير منشورة داخل معاملة واحدة.
- **التدقيق والتراجع:** تُسجل `published_report_details` ثم `published_reports` وتحديث `report_windows` تحت `batch_id` واحد، بحيث يعيد `UndoManager` النافذة ثم رؤوس النسخ ثم تفاصيلها بالترتيب الموافق للمفاتيح الأجنبية. فشل الحذف أو حفظ التدقيق يلغي المعاملة كاملة.
- **الواجهة:** يظهر الإجراء من صف نافذة التقرير مع عدد نسخ الطلاب المتأثرة ومودال تدميري مستقل. يبقى حذف النافذة معطلًا ما دامت النسخ موجودة، وبعد إلغائها يصبح حذف النافذة متاحًا. تميّز الحالة بصريًا بين «مخفي - النسخ محفوظة» و«غير منشور».
- **الحدود:** لا يحذف إلغاء النشر درجات الطلاب أو سجلات الرصد الأصلية، ولا يعمل خارج العام الدراسي القابل للكتابة. إعادة النشر بعد الإلغاء تنشئ لقطات جديدة من البيانات الحالية.
- **الرجوع:** يمكن التراجع عن دفعة الإلغاء عبر مسار التراجع المشترك ما لم يقع تعارض لاحق. الرجوع التشغيلي السريع للكود يعيد إخفاء زر الإلغاء، مع بقاء أي نسخ موجودة أو مستعادة دون تغيير.

## ADR-047 — عمليات التقييم الجماعية ذرية ومقيدة بالارتباطات التشغيلية

- **الحالة:** معتمد في 2026-07-28.
- **القرار:** تملك `AssessmentBulkActionService` تعطيل/إغلاق وحذف دفعات خطط الدرجات والبنود وقواعد الأسابيع ونوافذ الرصد. تتحقق الخدمة من العام الدراسي ومن جميع العناصر قبل الكتابة، وتنفذ الدفعة كاملة داخل معاملة واحدة أو تلغيها كلها عند أول مانع.
- **الحذف المركب:** يمكن للعملية نفسها تعطيل الخطة أو البند، أو إغلاق نافذة مفتوحة، ثم الحذف. وجود درجات أو نوافذ أو تقارير مرتبطة يبقى مانعًا ولا يمكن تجاوزه بالتعطيل. حذف الخطط والبنود يسجل العناصر التابعة وقواعد الأسابيع صراحة قبل الحذف المتسلسل.
- **التدقيق والتراجع:** تحمل جميع أحداث الدفعة `batch_id` واحدًا عبر `AuditService` و`UndoManager`، وتُسجل اللقطات بترتيب يعيد الآباء قبل الأبناء عند التراجع. أصبحت `assessment_windows` كيانًا مسجلًا قابلًا للتراجع مثل بقية جداول إعداد التقييم.
- **النسخ:** النسخ الجماعي معتمد للخطط فقط إلى ربط مادة/صف وترم هدف واضحين، وينشئ مسودات بأسماء فريدة ويسجل الخطة والبنود وقواعد الأسابيع في الدفعة نفسها. لا يُعمم النسخ على البنود أو القواعد أو النوافذ من دون عقد هدف منفصل يمنع تعارض النطاق والدرجات التاريخية.
- **الرجوع:** إزالة واجهة الدفعات واستدعاء الخدمة يعيد الصفحات إلى الإجراءات الفردية المتوافقة؛ سجلات البيانات الناتجة تُراجع أو تُتراجع عبر batch ID ولا تتطلب تغيير مخطط جديد.

## ADR-046 — مشاركة عامة قابلة للإلغاء وتصدير موحّد لدروس الذكاء الاصطناعي

- **الحالة:** معتمد ومنفذ في 2026-07-26.
- **القرار:** يملك `LearningContent` إنشاء رابط bearer عشوائي بطول 256 بت للدرس المكتمل وتجديده وإلغاءه. تبقى صفحات المعلم نقاط الدخول المالكة، بينما تعرض `shared_lesson.php` المحتوى المولد فقط دون جلسة أو تسجيل دخول بعد تحقق الخادم من الرمز وحالة المشاركة والدرس.
- **الأمان والخصوصية:** الرابط غير قابل للتخمين لكنه عام لكل من يملكه؛ لا يظهر في سجل التدقيق ولا في snapshots، وتلتقطه قاعدة إخفاء حقول `token`. تستخدم الصفحة العامة `noindex` و`no-referrer` و`no-store`، وتعرض الامتحان داخل iframe معزول. يعيد تنزيل الامتحان أو PowerPoint التحقق من الرمز، ويمنع مسار PowerPoint الخروج من جذر التطبيق.
- **التدقيق والتراجع:** إنشاء الرابط أو تدويره أو إلغاؤه كتابة مدققة داخل معاملة واحدة مع قفل ملكية الدرس. تسجل `ai_lessons` ككيان غير قابل للتراجع المباشر لأن استعادة bearer token قد تعيد فتح وصول عام ألغاه المعلم؛ الرجوع التشغيلي هو إنشاء رابط جديد صراحةً.
- **التصدير:** يملك `assets/js/lesson-export.js` جمع الأقسام في صفحات التوليد والأرشيف والمشاركة العامة. أزرار التبويب تمرر حاوية واحدة، والأزرار العامة تجمع كل الأقسام المتاحة مرة واحدة. تعيد نقطة `shared_lesson_export.php` العامة التحقق من bearer token النشط والدرس المكتمل في كل طلب، وتسمح فقط بـHTML وWord وPDF مع تحديد معدل الطلبات؛ وهي POST للقراءة والتحويل فقط ولا تنشئ أو تعدل بيانات أعمال، لذلك سُجل إعفاؤها من cookie CSRF بعقد `read_only_post`. يعيد `LessonExportService` التحقق من UTF-8 والحجم ومفاتيح الأقسام وإزالة التكرار والمحتوى التنفيذي قبل إنشاء الملف. يولد PDF فعليًا عبر Dompdf، وتمر عقد النص العربي فقط عبر `khaled.alshamaa/ar-php` قبل الرسم لضمان اتصال الحروف وترتيبها، بينما تبقى بنية HTML والمحتوى غير العربي دون تغيير.
- **اتساق الامتحان ودورة الحياة:** تستخرج أزرار نموذج الامتحان ومفاتيح الإجابة النماذج المضمّنة في `exam_html` المحفوظ بدل إعادة سحب الأسئلة أو خلطها، ولذلك يطابق كل مفتاح إجابة نموذجه المنشور حرفيًا. حذف الدرس مقيد بالمالك ومدقق داخل معاملة واحدة، ثم ينظف ملف PowerPoint بعد نجاح المعاملة فقط وبعد إثبات أن المسار داخل تخزين الدروس وغير مشارك مع سجل آخر.
- **المخطط والرجوع:** تضيف migration `20260726_ai_lesson_public_sharing.php` الرمز ووقت التفعيل والإلغاء وفهرسًا فريدًا. الرجوع ينشر أولًا كودًا لا يقرأ الأعمدة، ثم يحذف الفهرس والأعمدة؛ الروابط تصبح غير صالحة فور إزالة الكود أو القيم.

## ADR-045 — اسم وصفي قابل للتعديل للمرفقات مع بقاء التخزين والاسم الأصلي ثابتين

- **الحالة:** معتمد ومنفذ في 2026-07-22.
- **القرار:** يبقى `file_name` معرّف التخزين الخاص العشوائي، ويبقى `original_name` وصفًا تاريخيًا لاسم الملف وقت الرفع، بينما يكون `label` الاسم الوصفي الوحيد الذي يمكن للمسؤول تعديله للطالب أو العامل. يمتد endpoint المرفقات الحالي بإجرائي `rename` و`delete` بدل إنشاء مسار كتابة موازٍ، وتفوض الكتابات إلى خدمات المرفقات المالكة لكل وحدة.
- **الأمان والتدقيق:** تمر العمليات بالمصادقة وCSRF وحدود ملكية الطالب/العامل، ويُحجز الاسم `الصورة الشخصية` من إعادة التسمية. يشارك تحديث الاسم وسجل النشاط معاملة واحدة ويفشل التحديث إذا فشل التدقيق. حذف السجل يثبت أولًا داخل المعاملة المدققة ثم يُنظف الملف الخاص بعد نجاحها.
- **سياسة التراجع والتعارض:** تغيير الاسم قابل للعكس يدويًا بإعادة الاسم السابق ويُسلسل بقفل `FOR UPDATE`؛ لا تسجل جداول المرفقات الفرعية في `UndoManager` العام. حذف الملف أثر غير قابل للاستعادة بعد نجاح تنظيف التخزين، لذلك يبقى غير قابل للتراجع ويُسجل في سجل النشاط دون snapshot للملف.
- **التوافق:** لا يتغير مخطط قاعدة البيانات أو أسماء الملفات المخزنة أو الاسم الأصلي. يعرض التنزيل اسمًا آمنًا مشتقًا من `label` مع امتداد الملف الأصلي، وتبقى طلبات الرفع القديمة بلا `attachment_action` متوافقة بوصفها `upload`.
- **الرجوع:** تزال أزرار وإجراء إعادة التسمية ويعود اسم التنزيل إلى `original_name`. يمكن إبقاء قيم `label` الحالية كما هي؛ لا يلزم migration أو تعديل ملفات مخزنة.

## ADR-044 — أدوار متعددة للحساب مع دور جلسة نشط ونطاق سنوي مستقل لكل دور

- **الحالة:** معتمد ومنفذ في 2026-07-23.
- **القرار:** يملك الحساب الداخلي صفرًا أو أكثر من عضويات الأدوار في `user_role_assignments`، مع دور أساسي واحد فقط للتوافق مع `users.role`. لا تجمع الجلسة صلاحيات الأدوار؛ تختار دورًا نشطًا واحدًا في `active_role` ويظل `session.role` مرآة توافقية له. الحساب متعدد الأدوار يمر بصفحة اختيار بعد المصادقة، وكل تبديل يعيد التحقق من العضوية النشطة على الخادم ويجدد معرّف الجلسة.
- **نطاق البيانات:** تبقى عضوية الدور مستمرة بين الأعوام، بينما يضاف `role_key` إلى تعيينات الصفوف والفصول بحيث يكون المفتاح الفعلي `(staff_id, role_key, academic_year_id, grade_or_class_id)`. لا تنسخ تهيئة عام جديد هذه التعيينات؛ يبدأ نطاق كل دور في العام الجديد فارغًا.
- **التوافق المرحلي:** يبقى `users.role` هو الدور الأساسي فقط للقراءات القديمة، وتتحول استعلامات العضوية تدريجيًا إلى `user_role_assignments`. تتحقق الجلسة من الدور النشط في كل طلب محمي حتى تسقط الصلاحية فور إزالة الدور أو تعطيل الحساب.
- **قواعد الأعمال:** `employee` دور حصري لا يجتمع مع دور آخر، لكنه يملك الآن دخولًا محدودًا إلى `staff_hr_portal.php` فقط لتلبية عقد الخدمة الذاتية للعامل؛ البوابة تعيد التحقق من حالة الخدمة والتعيين وتمنح self-scope أو manager-scope من عقود Staff ولا تمنح أي صفحات إدارة. أدوار الإدارة العليا لا يضيفها أو يزيلها ولا يعطل أصحابها إلا جلسة تعمل فعليًا بدور `super_admin`، ولا يجوز إزالة أو تعطيل آخر مدير أعلى نشط. يجوز للمدير الأعلى تعديل عضويات أدواره الثانوية بنفسه، لكن تبقى عضوية `super_admin` والدور الأساسي ثابتين ولا يمكنه تعطيل حسابه ذاتيًا. صلاحية المشرف تظل خاصية للمعلم ولا تمنح صلاحيات أدوار أخرى.
- **التدقيق والتراجع:** استبدال عضويات الأدوار وتحديث مرآة الدور الأساسي يسجلان في دفعة تدقيق واحدة قابلة للتراجع، وتظل نطاقات كل دور موارد مدققة مستقلة. يسجل تبديل الدور كحدث أمني للجلسة دون تعديل عضوية الحساب.
- **الرجوع:** يعطل اختيار الأدوار المتعددة أولًا، ويستمر الدخول بالدور الأساسي في `users.role`. تبقى جداول العضوية وأعمدة `role_key` إضافة غير مدمرة حتى التحقق من عدم اعتماد أي حساب أو نطاق متعدد عليها؛ لا تحذف أثناء رجوع تشغيلي سريع.

## ADR-043 — نقل بيانات دخول الحسابات مستقل عن الأدوار والنطاق الأكاديمي

- **الحالة:** معتمد ومنفذ في 2026-07-22.
- **القرار:** تملك وحدة `Accounts` خدمة الاستيراد والتصدير الجماعي لبيانات الدخول، بينما تبقى تغييرات دور العامل وصلاحيات المشرف والنطاق الأكاديمي السنوي في مسار `Staff` المنفصل. يعتمد الربط في ملف النقل على `student_code` أو `employee_code` ولا يغيّر الملف الشخصي أو الدور أو الحالة.
- **الأمان:** ملفات التصدير لا تحتوي كلمات المرور الحالية مطلقًا؛ توفر عمود `new_password` فارغًا فقط. يمر CSV المرفوع عبر `FileUploadGuard` ويُقرأ من الملف المؤقت دون تخزينه، وتُنفذ الدفعة داخل معاملة واحدة مع سجل تدقيق موحد و`batch_id`، وتُلغى بالكامل عند خطأ أي صف.
- **واجهة الاستخدام:** تعرض صفحتا حسابات الطلاب والعاملين تصدير CSV قابلًا لإعادة الاستيراد. يفصل جدول العاملين زر بيانات الدخول عن زر الدور والصلاحيات، ولا يمكن إعداد دخول موظف بلا دور بوابة.
- **الرجوع:** تزال أزرار النقل والخدمة الجديدة ويعاد نموذج العاملين الموحّد؛ لا يلزم rollback للمخطط لأن القرار لا يضيف جداول أو أعمدة.

## ADR-042 — إشعار التراجع السريع مرتبط بالعملية والجلسة وليس بآخر سجل تاريخي

- **الحالة:** معتمد ومنفذ في 2026-07-22.
- **القرار:** يحتفظ سجل التدقيق والاستعادة بسياسة الاحتفاظ الطويلة، بينما تكون نافذة التراجع السريع من الإشعار خمس دقائق مستقلة يفرضها الخادم. كل سجل قابل للتراجع يضع معرّفه كإشعار معلق في جلسة الفاعل الحالية، وتستهلك نقطة الفحص هذا الإشعار مرة واحدة؛ لا تبحث الواجهة عن آخر سجل تاريخي عند تسجيل الدخول أو فتح تبويب جديد.
- **العقد:** يرسل زر الإشعار `undo_id` الصريح مع CSRF، ويتحقق الخادم من المالك والحالة والمهلة قبل تمريره إلى المحرك. يرسل الخادم `expires_in` محسوباً بساعته، فلا تفسر الواجهة توقيت MySQL ولا تعتمد على ساعة المتصفح أو `sessionStorage`.
- **التوافق:** تبقى `getLastUndoable()` وسياسة الاحتفاظ 720 ساعة لمسارات الاستعادة الإدارية الصريحة في سلة المحذوفات وسجل الإصدارات. لا تقيد مهلة الإشعار تلك المسارات، ولا تغير بنية قاعدة البيانات أو سياسة الدفعات الذرية.
- **التجربة:** يصاغ الإشعار حسب نوع الحدث (`تمت إضافة`، `تم تعديل`، `تم حذف`) ويظهر مرة واحدة بعد العملية المسجلة فقط. تدمير جلسة تسجيل الخروج يزيل أي إشعار لم يُستهلك.
- **الرجوع:** يعاد فحص آخر عملية في `api/undo.php` واستدعاء الواجهة السابق، وتحذف حالة الجلسة والمهلة السريعة؛ لا يلزم rollback للبيانات أو المخطط.

## ADR-041 — تخصيص واستنساخ الأدوار الإدارية مع وراثة السلوك المقيد

- **الحالة:** معتمد ومنفذ في 2026-07-22.
- **القرار:** يملك مدير النظام الأعلى وحده تعديل صفحات الأدوار `specialist` و`doctor` و`librarian` و`student_affairs_manager` و`transport_manager` و`roles_permissions_manager`، ويمكنه استنساخ أي منها إلى دور إداري جديد. تبقى أدوار `admin` و`super_admin` و`teacher` و`supervisor` و`external_teacher` و`student` و`employee` ثابتة.
- **حد الصفحات:** يحدد `AdminRolePageCatalog` صفحات المجال المراجعة لكل دور، ويعيد الخادم تقاطع الصفحات المرسلة مع هذا العقد؛ إخفاء الخيارات في الواجهة ليس حد الصلاحية.
- **وراثة السلوك:** يخزن `staff_roles.base_role_key` عائلة الدور المصدر للنسخ. يقرأ `StaffRoleCapabilityResolver` هذه العائلة كي ترث نسخ الأخصائي والطبيب وأمين المكتبة النطاق الأكاديمي السنوي، وكي ترث نسخة الأخصائي العام النشط وسلوك الطلبات بدل التحول إلى وصول غير مقيد.
- **لوحات الهبوط:** تبقى لوحة الأخصائي المتخصصة مستقلة، بينما تستخدم عائلات الطبيب وأمين المكتبة وشؤون الطلاب والحركة والصلاحيات لوحة `admin/role_dashboard.php` المشتركة. تُمنح اللوحة إلزاميًا وقت القراءة بحسب عائلة الدور ولا تدخل ضمن الصفحات القابلة للإلغاء؛ وتعرض روابط تقاطع خدمات العائلة مع منح الدور الفعلية فقط.
- **التدقيق:** يبقى إنشاء الدور وتعديل صفحاته داخل معاملة `staff_accounts.php` الحالية، ويشمل سجل النشاط مفتاح العائلة والصفحات. فشل التسجيل يلغي الكتابة.
- **الرجوع:** تعطّل أزرار الاستنساخ أولاً ثم تعاد قراءة الأدوار من مفاتيحها الأصلية؛ عمود العائلة additive ويمكن إبقاؤه فارغاً، ولا يحذف أثناء رجوع تشغيلي إلا بعد التأكد من عدم وجود أدوار مستنسخة تعتمد عليه.

## ADR-040 — فصل الإدارة العليا عن الإدارة العامة

- **الحالة:** معتمد ومنفذ في 2026-07-22؛ يرقّي ترحيل مدقق الحساب الذي يحدده إعداد النشر من `admin` إلى `super_admin` عند تهيئة النظام، مع تسجيل فرق الدور في سجل النشاطات.
- **القرار:** يحتفظ `admin` بإدارة صفحات النظام اليومية، بينما ينفرد `super_admin` بإنشاء الأدوار المخصصة وتعديل منح صفحاتها، ومنح أو سحب دوري `admin` و`super_admin`، وتنفيذ العمليات الحرجة المصنفة للإدارة العليا مثل إعادة ضبط جميع النقاط.
- **إنفاذ الخادم:** إخفاء عناصر الواجهة ليس حداً أمنياً. تتحقق معالجات POST ونقاط البيانات والصفحات الحرجة من الدور الفعلي، وترفض محاولات المدير العادي أو الدور الإداري المخصص حتى عند إرسال الطلب يدوياً.
- **حماية الاستمرارية:** يستطيع المدير الأعلى تعديل أدواره الثانوية بنفسه، لكن لا يستطيع إزالة عضوية `super_admin` أو تغييرها كدور أساسي أو تغيير حالة حسابه ذاتيًا، ولا يمكن تخفيض أو تعطيل آخر `super_admin` نشط. تقفل الخدمة صفوف المديرين الأعلى النشطين داخل معاملة التغيير قبل القرار.
- **التدقيق:** تغييرات أدوار الإدارة وحالات حساباتها تستخدم سجل النشاطات داخل معاملة الكتابة نفسها؛ فشل التدقيق يلغي التغيير. ترقية التأسيس أيضاً مسجلة كفرق `admin → super_admin` بواسطة migration محددة الحساب.
- **تصنيف فحص الكتابات:** `SystemAdministratorRoleService` مصنف false positive موثقاً لأنه ينفذ استعلامات `SELECT ... FOR UPDATE` فقط؛ مالك الكتابة والتدقيق الفعلي هو `admin/staff_accounts.php` داخل المعاملة نفسها.
- **الرجوع:** يتطلب الرجوع وجود مدير أعلى نشط بديل أولاً، ثم تخفيض الحساب من الواجهة المدققة؛ لا يُعاد الدور مباشرةً من قاعدة البيانات ولا يُعطل آخر مدير أعلى.

## ADR-039 — إزالة مفاتيح الأدوار المحجوزة غير المنفذة

- **الحالة:** معتمد ومنفذ في 2026-07-22.
- **القرار:** لا يُعرض أو يُحجز مفتاح دور لمجرد احتمال استخدامه مستقبلاً. أزيل مفتاح `parent` لأنه لا يملك بوابة أو تدفق مصادقة أو مالك صلاحيات حالي، بينما تبقى أدوار الطالب والمعلم الخارجي والمشرف لأنها تملك مسارات فعلية مستقلة.
- **سلامة البيانات:** يحذف الترحيل إعداد الدور ومنح صفحاته فقط، ويرفض التنفيذ إذا وجد أي حساب مستخدم مرتبطاً بالمفتاح؛ لا يحذف مستخدمين ولا يعيد تصنيفهم تلقائياً.
- **واجهة الإدارة:** يعرض جدول الأدوار الأدوار الفعلية فقط، ويخفي نقاط AJAX والصفحات التابعة، وتكون الأدوار المحددة مسبقاً مقفلة بينما يظل التعديل متاحاً للأدوار المخصصة التي ينشئها المدير.
- **الرجوع:** يعاد تعريف المفتاح فقط بالتزامن مع تنفيذ بوابة ومصادقة وصلاحيات واختبارات له؛ لا يعاد كاسم محجوز منفرد.

## ADR-038 — أدوار إدارية حسب القسم فوق صفحات الأدمن نفسها

- **الحالة:** معتمد ومنفذ في 2026-07-22؛ طُبقت migration على قاعدة التشغيل المحلية بعد إثبات عدم وجود مفاتيح أو حسابات متعارضة، ثم طابقت منح الصفحات العقد البرمجي.
- **القرار:** تُسجل أدوار `student_affairs_manager` و`transport_manager` و`roles_permissions_manager` كأدوار `admin_like` في `staff_roles`، وتستخدم صفحات الأدمن الأصلية نفسها بلا نسخ أو بوابات موازية. يحدد `staff_role_pages` الصفحات المرئية فقط، بينما يضيف `AdminRolePageCatalog` نقاط AJAX والصفحات التابعة اللازمة تلقائيًا عند قراءة الصلاحيات.
- **حدود الصلاحية:** مسؤول شؤون الطلاب يملك عناصر قائمة شؤون الطلاب كاملة بلا نطاق فصول؛ مسؤول الحركة والتنقلات يملك عناصر قائمة النقل كاملة؛ مسؤول الأدوار والصلاحيات يملك `school_settings.php` و`student_accounts.php` و`staff_accounts.php`. لا يرث أي دور منها بقية صفحات الأدمن، ولا يتحول إلى `admin` أو `super_admin`.
- **التوجيه والواجهة:** تستخدم أدوار شؤون الطلاب والحركة والصلاحيات لوحة الترحيب المشتركة `role_dashboard.php` كصفحة هبوط إلزامية، وتعرض اللوحة خدمات الدور الممنوحة فقط. يختار الدور المخصص خارج العائلات المراجعة أول صفحة تفاعلية مسموحة بدل إعادة التوجيه إلى لوحة إدارة غير ممنوحة. يعرض محرر الأدوار أدوار النظام الثابتة للمعرفة دون زر تعديل، ويخفي نقاط الدعم وصفحات الهبوط الإلزامية من قائمة الصلاحيات.
- **نقاط JSON المشتركة:** لا تُعامل الأدوار المخصصة كـ`admin` عام داخل dispatcher. تُفوض إجراءات حسابات الطلاب وصلات القرابة فقط عندما يثبت `Utilities::roleCanAccessAdminPage()` امتلاك الصفحة المالكة، ويخضع كشف كلمة المرور لصلاحية الصفحة التابعة نفسها.
- **الرجوع:** يعاد الكود السابق، ثم تحذف منح الصفحات والأدوار الثلاثة فقط بعد التأكد من عدم إسنادها لأي مستخدم أو بعد إعادة تعيين الحسابات المتأثرة. لا يوجد تغيير schema أو حذف لبيانات الأعمال.

## ADR-037 — سجلات الحضور والدوام البيومتري تظل مدققة على مستوى النطاق دون تراجع CTRL+Z

- **الحالة:** معتمد في 2026-07-19؛ السلوك الحالي موثّق صراحةً ولا يُغيَّر دون ADR لاحق يرفعه.
- **السياق:** يكتب `StaffAttendanceService` حاليًا في `staff_attendance_audit` (جدول domain مملوك لوحدة HR وفق ADR-012) عبر `logAttendanceAudit()`، ويستدعي `importBiometricRows()` الإصدار `recordEvent` من `AuditService` الذي يكتب في `activity_logs` فقط دون إنشاء سجلات في `undo_log`. النتيجة: عمليات `staff_attendance` (إضافة/تعديل/حذف فردية) واستيراد `staff_biometric_logs` الدفعي غير قابلة للتراجع عبر آلية CTRL+Z المركزية، رغم أن لها مسار تدقيق قبل/بعد مملوكًا للنطاق.
- **القرار:** يبقى `staff_attendance` و`staff_biometric_logs` غير مسجَّلَين في `AuditPolicyRegistry::UNDOABLE_TABLES`، ويفشلان مغلقَين عبر فرع `unregistered_entity` في `directUndoBlockReason()`. تبقى `staff_attendance_audit` مصدر المراجعة الموثّق، وتبقى أزرار الحذف/التعديل في `admin/staff_attendance.php` هي واجهة التصحيح اليدوي. لا تُعدَّل `StaffAttendanceService` لاستدعاء `AuditService::recordInsert/recordUpdate/recordDelete`، ولا يُعدَّل اختبار `admin_operational_audit_contract_test.php` الذي يؤكد علامة `biometric_import_reconciliation_required`.
- **المبررات:**
  - سجلات الحضور والبصمة بيانات زمنية متسلسلة؛ التراجع الفردي عن سجل واحد يخالف طبيعة البيانات (لا يعني غياب السجل أن الموظف لم يحضر).
  - الاستيراد الدفعي للبصمة قد يلمس آلاف الصفوف ويُعيد مزامنة `staff_attendance`؛ تراجع CTRL+Z لمثل هذا الحجم غير عملي وعرضة لسوء الاستخدام.
  - النظام يملك بالفعل مسار تدقيق domain مملوكًا للنطاق (before/after + actor + source) في `staff_attendance_audit`، يفي بمتطلبات المراجعة دون `undo_log`.
- **العواقب:**
  - أي استدعاء لـ`UndoManager::logInsert/logUpdate/logDelete` على `staff_attendance` أو `staff_biometric_logs` يُرجع `false` بصمت ولا ينشئ سجل تراجع؛ هذا هو السلوك المقصود (fail-closed)، وليس خللًا.
  - إتاحة التراجع مستقبلًا تتطلب: تسجيل الجدول في `AuditPolicyRegistry`، إعادة هيكلة `StaffAttendanceService` لاستدعاء `AuditService::recordInsert/Update/Delete` داخل معاملة الاستدعِي، تحديث اختبار `admin_operational_audit_contract_test.php`، إضافة اختبارات تركيز (قالب: `tests/staff_leave_audit_contract_test.php`)، تصنيف `delegated` في `tools/audit_write_coverage_classifications.php`، ورفع ADR لاحق يوثّق سياسة التراجع (فردي أم دفعي ذري).
  - لا أثر بيانات لهذا القرار؛ هو توثيق السلوك القائم فقط.
- **الرجوع:** لا حاجة ل rollback بيانات. rollback البرمجي يعني تنفيذ خطة التراجع الموصوفة أعلاه كـ ADR لاحق مستقل.

## ADR-036 — صفحات الإدارة المشتركة للأدوار ذات النطاق السنوي

- **الحالة:** معتمد ومنفذ مرحليًا في 2026-07-19؛ طُبقت جداول النطاق العامة وتفعيلات الأدوار على قاعدة التشغيل بعد نسخة رجوع، ولا تُفعّل صفحة إضافية قبل اكتمال قيود القراءة والكتابة واختبارها.
- الأخصائي والطبيب وأمين المكتبة يستخدمون صفحات الإدارة نفسها كمصدر عرض ووظيفة وحيد، لا نسخًا مستقلة منها. يسمح `staff_role_pages` بنقطة الدخول فقط، بينما يفرض `ScopedStaffPortalContext` و`StaffAcademicScopeService` نطاق البيانات على الصفحة وكل endpoint تابع لها.
- يملك كل دور نطاقًا سنويًا في `staff_grade_assignments` و`staff_class_assignments`. اختيار الصف يشمل فصوله النشطة، ويكمله التعيين المباشر للفصل. الدور يستمر عند إنشاء عام جديد، لكن تعييناته لا تنسخ تلقائيًا ويبدأ نطاق العام الجديد فارغًا حتى يعتمده الأدمن من `staff_accounts.php`.
- الأخصائي يحمّل `admin_header.php` والقائمة الجانبية ونقاط دخول الإدارة الأصلية نفسها. يثبت `AcademicYear` سياقه على العام النشط الحالي، ويعرض عنصر العام في الشريط العلوي بالشكل الإداري نفسه لكن دون قائمة تبديل أو قبول معامل تبديل يدوي.
- الطبيب يملك خصائص صفحة العيادة كاملة داخل نطاقه. أمين المكتبة يملك خصائص صفحة المكتبة كاملة داخل نطاقه. يبقى الأخصائي في العيادة قارئًا لسجل الزيارات فقط. تعديل ملف الطالب أو نقله بين الفصول من الأخصائي ينشئ طلبًا معلقًا، ويطبق فقط بعد موافقة الأدمن وفحص التعارض والنطاق داخل معاملة مدققة.
- نقاط الدخول العامة القديمة تحت `specialist/` مهايئات مصادقة وإعادة توجيه فقط إلى صفحات الإدارة المشتركة؛ لم تعد تملك عرضًا أو منطق أعمال مستقلاً. يبقى اسم `SpecialistAcademicScopeService` طبقة توافق داخلية فوق النطاق السنوي العام ولا يملك تخزينًا مستقلاً.
- نقطة دخول الأخصائي هي `admin/specialist_dashboard.php`: لوحة ترحيب داخل `admin_header.php` تعرض اسمه، العام النشط، ملخص نطاقه، والخدمات الممنوحة له فقط. يعد مسار اللوحة إلزاميًا للأخصائي مثل `profile.php`، بينما تبقى صفحات العمل نفسها صفحات الإدارة الأصلية. تجمع نقطة الدخول العرض فقط وتقرأ الملخص عبر عقد `SpecialistDashboardQuery` بدل SQL داخل الصفحة.
- يعرض `StudentChangeRequestPresenter` فروق طلبات الطالب على مستوى الحقول الفعلية وبصياغة بشرية؛ لا تطبع صفحة المراجعة JSON خامًا. تُطبّع صيغ الأرقام والبيانات الإضافية القديمة قبل المقارنة، ولا تُعد أرقام الاتصال أو البيانات الإضافية أو أولياء الأمور أو النقل الخارجي تغييرات إلا مع علامة لمس صريحة من النموذج. غياب العلامة، بما في ذلك الطلبات التاريخية الملتبسة، يفشل مغلقًا ويحفظ القيمة الحالية عند الاعتماد بدل تفسير العرض أو الغياب كحذف.
- يملك الأخصائي مسارًا إلزاميًا للقراءة فقط هو `admin/specialist_requests.php` باسم «طلباتي». يقرأ عبر `StudentChangeRequestService::listForSpecialist()` ولا يقبل مراجعة أو كتابة؛ يفرض الاستعلام هوية الأخصائي والعام النشط معًا، ويعرض الحالة وسبب الرفض أو التعارض والمراجع ووقت المراجعة باستخدام `StudentChangeRequestPresenter`. يبقى اعتماد الطلب ورفضه حصريين في `admin/pending_operations.php` للأدمن.
- تقارن طلبات تعديل الطالب القيم الأكاديمية بالمرجع السنوي الفعلي في `student_enrollments` والفصل المرتبط، لا بالحقول القديمة الفارغة في `student_profiles`. كما تُطبع أجزاء الاسم من `users.name` عندما يكون ملف قديم غير مقسم. عند عرض طلب تاريخي، يجوز للمقدم إخفاء فرق `grade_id` الفارغ فقط إذا أثبت أن الفصل لم يتغير وأن الصف المقترح هو صف القيد الحالي نفسه؛ لا يُعدل سجل التدقيق المخزن ولا تُخفى تغييرات الفصل أو الصف الحقيقية.

## ADR-035 — نطاق أخصائي سنوي وبوابة قراءة مقيدة مع طلبات تعديل

- **الحالة:** معتمد ومنفذ في 2026-07-19؛ طُبقت migrations على قاعدة التشغيل بعد حفظ لقطة رجوع مخصصة لأدوار العاملين، كما اختُبرت على قاعدة معزولة منتهية بـ`_test`.
- يحمل المعلم وحده تعيينات `assessment_teacher_assignments.php`. يملك الأخصائي نطاقًا سنويًا واحدًا من `specialist_grade_assignments` و`specialist_class_assignments` تديره `SpecialistAcademicScopeService` من صفحة حسابات العاملين؛ اختيار الصف يشمل فصوله النشطة، والتعيين المباشر للفصل يكمّل ذلك.
- بوابة الأخصائي تستخدم shell الإدارة وصفحاتها الأصلية نفسها، وكل قراءة تمر عبر عقود Attendance وStudents وBehaviorEvaluation وClinic المقيدة بالنطاق السنوي. لا تمنحه إضافة طالب أو أرشفته أو أي صفحة غير مدرجة في `staff_role_pages`.
- تعديل ملف الطالب أو نقله بين فصول نطاق الأخصائي ينشئ `student_change_requests` بحالة `pending` ولا يغيّر الطالب. يعتمد المدير أو يرفض من `admin/pending_operations.php`؛ الاعتماد يتحقق من تعارض نسخة الملف أو الفصل الحالي ثم يفوض الكتابة إلى `StudentProfileCommandService` داخل معاملة مدققة.
- يبقى `specialist_classes` مصدر ترحيل/رجوع تاريخي فقط. القراءات التوافقية تستخدم view اسمها `specialist_active_classes` مشتقة من المصدر السنوي، ومسار الكتابة القديم يفشل مغلقًا. وضع المشرف أصبح دورًا فعالًا مستقلاً ولا يرث دور الأخصائي أو نطاقه.
- rollback البرمجي يعيد نقاط الدخول القديمة مع إبقاء الجداول الجديدة دون استخدام. rollback البيانات يعيد القراءات إلى `specialist_classes` فقط بعد إثبات سلامة نسخة الترحيل؛ لا تحذف migration الجدول القديم.

## ADR-034 — تصنيف الحساب التجريبي ملك لحساب الدخول لا لملف الطالب

- **الحالة:** معتمد ومنفذ برمجيًا في 2026-07-19؛ تطبيق migration على قاعدة التشغيل مشروط بنسخة تعافٍ مجرّبة الاستعادة.
- يملك `users.is_test_account` التصنيف الرسمي/التجريبي لحساب الطالب، وتكون `admin/student_accounts.php` واجهة الإدارة الوحيدة له. لا يقرأ نموذج الملف الأكاديمي هذا الحقل ولا يكتبه.
- تنقل migration مستقلة كل قيمة تجريبية قديمة من `student_profiles` إلى `users`، وتتحقق من اكتمال النسخ قبل إسقاط العمود والفهرس القديمين. لا يحذف النقل طالبًا أو قيدًا أو درجة أو حضورًا.
- ينفذ `StudentAccountClassificationService` التغيير داخل معاملة واحدة مع سجل audit/undo مشترك. تقرأ التهيئة التصنيف من الحساب، ويبقى الحساب التجريبي مستبعدًا من الترحيل الرسمي من دون تعطيل تسجيل الدخول أو تعديل الهوية الأكاديمية.
- إنشاء حزمة التعافي واختبار استعادتها عملية صيانة صريحة طويلة نسبيًا؛ تمنحها صفحة التهيئة مهلة محدودة قدرها 900 ثانية مع استمرار الخادم عند إغلاق التبويب، وتمنع الإرسال المكرر. تبقى حالة النجاح مرهونة باستعادة فعلية وبصمات مطابقة، وتُخزن الملفات المضغوطة أصلًا داخل ZIP دون إعادة ضغط لتقليل زمن الإغلاق.

## ADR-033 — قرارات ترحيل صريحة لمدرسة واحدة دون تسكين فصول آلي

- **الحالة:** معتمد ومنفذ ومثبت على قاعدة التشغيل في 2026-07-18 بعد نسختين مجرّبتي الاستعادة قبل/بعد التغيير؛ لم ينفذ أي rollover فعلي.
- النظام نشر واحد لمدرسة واحدة؛ لا يضاف `school_id` أو tenant أو هيكل SaaS. قابلية الاستمرار لسنوات كثيرة تتحقق بسجلات القيد السنوية والمفاتيح والفهارس، لا بتعدد المدارس.
- يملك `grade_promotion_rules` قاعدة انتقال لكل صف رسمي وزوج عام مصدر/هدف باستخدام IDs فقط. لا يستنتج التنفيذ الانتقال من اسم الصف أو `grade_order` أو ترتيب/عدد الفصول، وتستبعد الصفوف التجريبية بعلامة صريحة قابلة للعكس.
- يملك `student_promotion_decisions` قرارًا دائمًا لكل قيد مصدر: `promoted`, `retained`, `pending`, `graduated`, `transferred_out`, `withdrawn`, أو `excluded_test`. بصمة snapshot تمنع تطبيق قرار على قيد تغير بعد المعاينة، ولا يسمح التنفيذ بتخطي طالب حقيقي.
- الناجح والراسب فقط يحصلان على قيد في العام الهدف؛ يبدأ `class_id` فارغًا ويرتبط القيد بـ`source_enrollment_id` و`promotion_decision_id`. الراسب يبقى في الصف نفسه ويزيد `repeat_count`، وتسكين الفصول عملية لاحقة مستقلة.
- تنسخ الفصول إلى الهدف كمسودات غير نشطة مع السعة. اختلاف عدد الفصول بين صفين لا يمنع التهيئة، وتعرض الموانع مجمعة حسب السبب بدل تكرار رسالة لكل طالب.
- حسابات الطلاب التجريبية والصفوف التجريبية أعلام صريحة قابلة للتعديل ومدققة؛ يجوز للحساب التجريبي وحده أن يبقى بلا مرحلة/صف، ويستبعد من الترحيل ولا يُعامل كتخرج أو نجاح.
- `NewYearWizard` يبقى مهايئ توافق، وصفحة الإدارة هي نقطة التحكم، بينما يملك `NewYearRolloverService` القواعد والقرارات والتنفيذ والتحقق والرجوع. أي كتابة أعمال تسجل عبر بنية التدقيق المشتركة.

## ADR-032 — تهيئة العام كتدفق محمي ثابت مع إثبات استعادة

- **الحالة:** معتمد للتطبيق في 2026-07-18؛ migration على قاعدة التشغيل والنشر الفعلي منفصلان.
- تملك `RecoveryBackupService` حزمة SQL وملفات التطبيق وبيان SHA-256، ولا يمنح receipt حالة `verified` إلا بعد استعادة فعلية إلى قاعدة جديدة منتهية بـ`_test` ومقارنة البنية والأعداد وبصمات محتوى الجداول والملفات.
- تملك `NewYearRolloverService` preflight والتنفيذ والـmanifest والتحقق والرجوع والتفعيل خلف adapter `NewYearWizard` ونقطة الدخول الحالية. لا توجد خيارات نسخ؛ البيانات التاريخية لا تنقل، والعمليات التشغيلية المتغيرة تبدأ فارغة.
- كل target row ينشأ داخل معاملة واحدة ويسجل في `academic_year_rollover_items`. الرجوع قبل التفعيل يحذف هذه المعرفات فقط بترتيب عكسي، ولا يستخدم undo العام أو `INSERT IGNORE`.
- التفعيل منفصل بعد التحقق، ويجعل الهدف نشطًا ويقفل المصدر. `AcademicYearWriteGuard` هو عقد الرفض المشترك لمسارات الحضور والتقييم والدرجات/التقارير والمالية المؤكدة.
- حزم التعافي محمية من retention العام، ولا تُطبق migration أو تهيئة على `educore` أثناء التطوير. إثبات التكامل تم على ثلاث قواعد `_test` مؤقتة ثم حُذفت.

## ADR-030 — تحميل القوائم الإدارية الثقيلة من الخادم مع واجهة DataTables المتوافقة

- **الحالة:** معتمد مرحليًا في 2026-07-16.
- يطبّق النمط حاليًا على قوائم الطلاب والعاملين، والمنقولين والخريجين، والحسابات، والعيادة، والمدفوعات، وأرشيف الطلاب، وسجل تدقيق حضور العاملين، وتعيينات المعلمين. تبقى الجداول الصغيرة، والتبويبات الداخلية، وقوائم التفاصيل على التحميل المعتاد حتى يثبت احتياجها.
- يملك كل موديول query/presenter وendpoint إداريًا رفيعًا متوافقًا مع DataTables، بينما يملك `assets/js/admin-server-side-table.js` سلوك الواجهة المشترك: POST محمي بـCSRF، رسالة التحميل، 50 سجلًا افتراضيًا، خيارات 10/25/50/100/200/500/الكل، ونقل خصائص الأعمدة إلى الصفوف الجديدة.
- أصبحت `admin/transferred_students.php` مالكة لقائمة المنقولين من المدرسة في العام الحالي بدل تحميل `admin/students.php` لكل طلب. يحتفظ adapter محدود بطلبات POST وروابط `add/edit/view` القديمة ويوجهها إلى مالك ملف الطالب المشترك مع نطاق `transferred`؛ وبذلك تبقى عقود URL والنماذج متوافقة دون نسخ منطق الكتابة.
- لا تنفذ نقطة القراءة أي كتابة أو تدقيق أعمال، وتبقى الصلاحية وCSRF عند entrypoint. لكل صفحة جديدة اختبار عقد وقياس حمل قبل إضافتها؛ والرجوع يعيد جدولها المحلي ولا يحتاج schema أو rollback للبيانات.

## ADR-031 — أرشفة هوية الطالب قبل أي حذف نهائي

- **الحالة:** معتمد مرحليًا في 2026-07-16.
- الأرشفة هي الإجراء الاعتيادي في قوائم الطلاب: تضبط `users.deleted_at` وتعطل الحساب، وتحفظ `archived_by` و`archive_reason` و`status_before_archive`، من دون تغيير القيد الأكاديمي أو حذف الدرجات والحضور والمالية والمرفقات.
- تملك وحدة Students عقدي `StudentArchiveService` للكتابة و`StudentArchiveQuery` للقراءة، وتستخدم الوحدات الأخرى `StudentOperationalGuard` لمنع معاملة جديدة لطالب مؤرشف بدل الوصول إلى تفاصيل الأرشفة الداخلية.
- الاسترجاع يعيد حالة الحساب السابقة فقط؛ لا ينشئ قيدًا تلقائيًا في عام دراسي لاحق. الحذف النهائي لا يعمل إلا من صفحة الأرشيف، وبعد إعادة التحقق من كلمة مرور المدير، وكتابة كود الطالب، ومرور 24 ساعة، وثبوت عدم وجود حضور أو درجات أو تقارير أو معاملات مالية أو سجلات رسمية محمية.
- الحذف النهائي سياسة غير قابلة للتراجع ومخصصة للسجلات المنشأة بالخطأ؛ يسجل intent تنظيف المرفقات داخل معاملة الحذف ونتيجة الأثر الخارجي بعد تحديث قاعدة البيانات. Rollback قبل النشر يعيد الطلاب ذوي `archived_by IS NOT NULL` إلى `status_before_archive` ويفرغ حقول الأرشفة، ثم يمكن إزالة الأعمدة والفهرس بالمigration عكسي مراجع.

## ADR-014 — فشل اتصال قاعدة البيانات وسياسة التشخيص الآمنة

- **الحالة:** معتمد في 2026-07-15.
- يبقى `Database::getConnection()` متوافقًا بإرجاع `null` عند فشل الاتصال، ولا ينهي الطلب ولا يطبع تفاصيل PDO حتى عند تفعيل `display_errors`.
- تمر التفاصيل التشخيصية عبر `SafeErrorPolicy` بسجل منظم ومرجع عشوائي، مع إزالة محارف التحكم وحجب القيم التي تبدو أسرارًا.
- لا يحل السجل التشخيصي محل سجلات الأمن أو سجلات الأعمال غير القابلة للتغيير، ولا تُعرض رسالته للمستخدم.
- كل اختبار يتصل بقاعدة MySQL المشتركة يستخدم حارس قاعدة الاختبار الصريح؛ يرفض الحارس اسمًا لا ينتهي بـ`_test` ويرفض بيئة production ويتحقق من اسم قاعدة الاتصال فعليًا.
- متغيرات بيئة العملية التي يمررها المشغّل أو CI لها الأولوية على `.env`، ولا يعيد المحمّل المحلي كتابتها.

## ADR-015 — واجهة قرار الأدوار المتوافقة

- **الحالة:** معتمد مرحليًا في 2026-07-15.
- `AuthorizationFacade` هو موضع القرار النقي للدور الفعلي والدور الفعال للمشرف وقبول الدور المطلوب وصفحات الإدارة، بينما تبقى `Utilities` مهايئ الجلسة وإعادة التوجيه والوصول إلى بيانات الأدوار المخصصة.
- لا تنشئ الواجهة مخطط صلاحيات جديدًا ولا تستبدل صلاحيات Assessment؛ تفوض قرار صفحات الدور المخصص إلى `staff_role_pages` القائم وتحافظ على `admin` و`super_admin` وأوضاع المشرف الحالية.
- أي نقل لاحق لسياسة أعمال متخصصة يتطلب contract خاصًا بالوحدة، ولا يحول facade إلى قائمة صلاحيات عامة غير موثقة.

## ADR-016 — مصادقة hash-first ونافذة ترحيل الحسابات القديمة

- **الحالة:** معتمد مرحليًا في 2026-07-15.
- `password_hash` هو المصدر الملزم متى كان موجودًا؛ فشله لا يسمح بالرجوع إلى كلمة المرور المشفرة القديمة.
- الحسابات بلا hash تمر عبر `PasswordAuthenticator` فقط عند `PASSWORD_LEGACY_LOGIN_ENABLED=true`، ويُنشأ لها hash بعد أول تحقق ناجح. إغلاق النافذة يتم بتغيير البيئة بعد قياس عدم بقاء حسابات نشطة بلا hash.
- كل إنشاء/إعادة تعيين جديد يكتب hash فورًا. يبقى الحقل المشفر مؤقتًا لدعم reveal الإداري الحالي؛ إزالته وسياسة استعادة الحساب قرار مستقل.
- rollback البرمجي يعيد adapter القديم، لكن rollback بيانات غير مطلوب لأن إضافة hashes لا تمحو الغلاف القديم.

## ADR-017 — روابط الرفع وحدود التخزين العام واتساق الملف مع السجل

- **الحالة:** معتمد مرحليًا في 2026-07-16.
- تحفظ جداول الملفات أسماء أو مسارات نسبية فقط؛ الروابط المطلقة الخارجية تُبنى من `APP_URL`، ويبقى `SITE_URL` اسمًا توافقيًا أثناء الانتقال.
- مجلد `uploads/` يبقى سطحًا عامًا للمواد والصور المطلوبة، لكنه يعطل الفهرسة وCGI ومعالجات السكربتات ويحجب امتدادات التنفيذ؛ المرفقات الحساسة تبقى في `storage/private/` وفق ADR-013.
- `FileUploadGuard` يملك التحقق المشترك من خطأ الرفع والحجم والامتداد المزدوج الخطر وMIME الحقيقي وتوليد اسم التخزين العشوائي.
- عند الإضافة أو الاستبدال يُحذف الملف الجديد إذا فشلت كتابة قاعدة البيانات، ولا يُحذف الملف القديم إلا بعد نجاح تحديث السجل. عند الحذف أو التفريغ تُحدّث قاعدة البيانات أولًا ثم يُحذف الملف المرتبط.
- `tools/audit_stored_upload_urls.php` تدقيق CLI للقراءة فقط؛ أي ترحيل بيانات لاحق يتطلب نتيجة فعلية ونسخة احتياطية وmigration مستقلة قابلة للتراجع.
- `tools/upload_policy_manifest.json` هو جرد مراجع لمسارات الرفع وتصنيفها وعلامات عقدها، ويمنع `tools/audit_upload_policy.php --strict` أي uploader مباشر جديد غير مصنف أو إزالة الحماية/التعليمات/اختبارات البوابة. يشغل `composer upload-policy-audit` هذه العقود، وتشغل بوابة CI أمر `composer quality` دون اتصال بقاعدة التشغيل.

## ADR-012 — بيان مراجعة لمسارات POST غير الخاضعة لـ CSRF

- **الحالة:** معتمد في 2026-07-13.
- كل طلب يغيّر الحالة ويعتمد على cookie يمر عبر حارس CSRF المشترك، بما في ذلك إرسال الأنشطة والاختبارات العامة برمز جلسة مجهولة.
- الاستثناء محصور في POST للقراءة فقط أو تبادل bearer token موثّق تشفيريًا، ويسجل بمسار دقيق وفئة وسبب وحماية ومالك وتاريخ مراجعة في `tools/architecture_csrf_exemptions.json`.
- يفشل strict audit عند وجود استثناء تالف أو منتهي أو مكرر أو لم يعد يطابق مرشحًا حاليًا.
- أوقف مسار Teams Context غير الموقّع؛ إنشاء جلسة Microsoft يتطلب توقيعًا صالحًا وclaims إلزامية: `iss` و`aud` و`tid` و`exp`.

## ADR-013 — تخزين مرفقات ملفات الطلاب والعاملين

- **الحالة:** معتمد مرحليًا في 2026-07-13.
- المرفقات الجديدة تحفظ تحت `storage/private/profile_attachments/` بأذونات داخلية، ولا تُنشأ لها روابط مباشرة من `uploads/`.
- التنزيل يمر عبر `admin/profile_attachment.php` بعد التحقق من جلسة الإدارة، وهو مطابق لمصفوفة المستهلكين النشطين المثبتة حاليًا.
- القراءة مزدوجة مؤقتًا: أسماء `private:` من التخزين الخاص، والأسماء القديمة من مجلدات uploads عبر controller نفسه فقط.
- أداة الترحيل dry-run افتراضيًا؛ apply يتطلب snapshot خاصًا واسم قاعدة مطابقًا، وينسخ قبل التحديث ويتحقق بـSHA-256 ويترك المصدر القديم للـrollback.
- بعد ترحيل كل صفوف مرفقات profile المحلية والتحقق من rollback، مُنعت القراءة العامة لمجلدات المرفقات القديمة. لا يُحذف ملف قديم خلال نافذة dual-read/rollback.

## ADR-001 — Modular Monolith عملي وانتقال تدريجي

- **الحالة:** معتمد
- **التاريخ:** 2026-07-12
- **السياق:** التطبيق PHP/PDO بنشر واحد وقاعدة بيانات مشتركة، وتوجد فيه وحدات أعمال حقيقية لكن صفحات وفئات legacy تجمع HTTP وSQL والعرض وقواعد المجال. لا يوجد framework أو router مركزي مثبت يبرر إعادة كتابة واسعة.
- **القرار:** الهدف هو Modular Monolith عملي. تُستخرج use cases تدريجيًا إلى وحدات ذات طبقات Application/Domain/Infrastructure/Presentation، مع الإبقاء على adapters التوافقية القديمة. لا rewrite ولا framework/ORM migration لمجرد إعادة التنظيم.
- **العواقب:**
  - يقل خطر الانتقال ويمكن اختبار كل vertical slice والتراجع عنها منفردة.
  - يبقى بعض التكرار والـadapters مؤقتًا حتى انتقال المستهلكين.
  - لا تُنشأ الشجرة المستهدفة كاملة مسبقًا؛ ينشأ الجزء المطلوب عند أول use case حقيقي.
  - أي انتقال واسع بين الوحدات أو إضافة نمط معماري موازٍ يحتاج ADR جديدًا.

## ADR-002 — إبقاء نقاط الدخول وURLs حسب الدور

- **الحالة:** معتمد
- **التاريخ:** 2026-07-12
- **السياق:** معظم routes مرتبطة بأسماء ملفات مباشرة تحت الجذر ومجلدات الأدوار، كما تعتمد النماذج والروابط وAJAX على هذه المسارات.
- **القرار:** تبقى ملفات الجذر و`admin/`, `teacher/`, `student/`, `specialist/`, `supervisor/`, `external/`, `api/`, `ajax/` و`auth/` نقاط دخول متوافقة أثناء الانتقال. تصبح رفيعة تدريجيًا: bootstrap وأمن وتحويل طلب واستدعاء use case واستجابة.
- **العواقب:**
  - تُحفظ الروابط والعقود الحالية ويصغر blast radius.
  - لا يُعاد تسمية route أو نقله ضمن refactor داخلي بلا redirect/compatibility plan واختبارات callers.
  - قد يبقى rendering أو تنسيق legacy في الصفحة مؤقتًا، لكنه لا يبرر إضافة SQL أو business workflow جديد إليها.
  - نقل document root إلى `public/` قرار نشر مؤجل يحتاج ADR وخطة مستقلة.

## ADR-003 — `AGENTS.md` هو المصدر القانوني لتعليمات المشروع

- **الحالة:** معتمد
- **التاريخ:** 2026-07-12
- **السياق:** `AGENTS.md` هو ملف التعليمات الجذري الموجود والمعلن، بينما توجد وثائق تاريخية أو قوالب قد تتأخر عن التنفيذ.
- **القرار:** يكون `AGENTS.md` الجذري المصدر الملزم الوحيد لقواعد المساعدين والهندسة. تشرح وثائق `docs/` القرارات والبنية، ولا تنشئ قواعد تناقضه. أي constitution أو adapter مدعوم يشير إليه ولا ينسخ محتواه كاملًا.
- **العواقب:**
  - لوصف **السلوك الحالي** يتقدم الدليل التنفيذي على الوثائق الوصفية. أما القواعد المعيارية للكود الجديد والتغيير فتتقدم من `AGENTS.md`؛ كود legacy المخالف يُسجل دينًا ولا يصبح precedent.
  - كل تغيير معياري دائم يجب أن يحدث `AGENTS.md` والوثيقة المركزة ذات الصلة في نفس الدفعة.
  - يمنع تكرار قواعد كاملة في عدة ملفات وما ينتج عنه من drift.

## ADR-004 — migrations هي المسار الوحيد لتغيير schema في الكود الجديد

- **الحالة:** معتمد
- **التاريخ:** 2026-07-12
- **السياق:** توجد migrations مؤرخة، لكن بعض request paths القديمة تنفذ `CREATE TABLE` أو `ALTER TABLE`، بما يسبب drift وlocks وimplicit commits وصعوبة في ضبط الصلاحيات.
- **القرار:** كل تغيير schema جديد يوضع في `database/migrations/` ويُنفذ عبر migration runner محمي وCLI-only. يمنع runtime DDL و`ensureTable`/`ensureColumn` في صفحات أو APIs أو services الطلب. يفحص request code readiness ويعطي خطأ تشغيليًا آمنًا إذا لم تُطبق migration.
- **العواقب:**
  - تصبح الإصدارات قابلة للتتبع والاختبار والتهيئة قبل استقبال traffic.
  - تحتاج كل migration إلى preconditions وidempotence عند الحاجة وخطة rollback أو restore.
  - runtime DDL القديم دين مسجل يُزال وحدة بوحدة بعد اختبارات fresh/partial DB، ولا يُستخدم precedent للكود الجديد.
  - لا تُشغل migrations أو اختبارات كتابية على قاعدة `educore` بلا تصريح وبيئة آمنة.

## ADR-005 — حجب المجلدات الداخلية مع استثناءين انتقاليين

- **الحالة:** معتمد مرحليًا
- **التاريخ:** 2026-07-12
- **السياق:** المشروع تحت web root؛ لذلك أمكن نظريًا طلب source/tools/tests/temp مباشرة. في المقابل، `includes/ajax_handlers.php` endpoint فعلي مستخدم، كما تعتمد روابط قديمة على ملفات داخل `uploads/`.
- **القرار:** تُحجب مباشرة مجلدات `classes/`, `config/`, `database/`, `tools/`, `tests/`, `scratch/`, `tmp/` و`storage/`، وتبقى الأدوات CLI-only. لا يُحجب `includes/` أو `uploads/` بالكامل الآن حتى تُفصل الاعتماديات وتُهاجر الملفات. لا تُضاف endpoints جديدة إلى `includes/`، ولا ملفات حساسة جديدة إلى `uploads/`؛ وجهتها `storage/private/` مع download endpoint مصرح.
- **العواقب:**
  - ينخفض سطح HTTP الداخلي دون تغيير URLs أو نقل ملفات واسع.
  - يبقى خطر متبقٍ ومقصود في `includes/` و`uploads/` ويجب ألا يتحول إلى استثناء دائم غير مراقب.
  - إغلاق الاستثناء يتطلب inventory للـcallers/links، authorization matrix، dual-read أو compatibility migration، واختبارات HTTP/rollback.
  - إعداد document root منفصل يبقى دفاعًا مستقبليًا إضافيًا، لا بديلًا عن الحدود داخل التطبيق.

## ADR-006 — Architecture audit baseline يعمل بنظام ratchet

- **الحالة:** معتمد
- **التاريخ:** 2026-07-12
- **السياق:** المستودع يحتوي دينًا قائمًا مثل الملفات الضخمة وruntime DDL ومرشحات POST تحتاج مراجعة، وفشل كل build بسبب الدين القديم سيمنع اعتماد البوابة.
- **القرار:** `composer architecture-audit` يقارن النتائج بخط أساس مراجع على مستوى مسارات الملفات: يمنع دخول ملف جديد إلى مجموعة دين، ويمنع فقدان حماية مجلد داخلي أو تعذر قراءة ملف ممسوح. وضع report يعرض الدين الحالي؛ لا يمثل finding وحده إثبات ثغرة. baseline آلية ratchet وليس allow-list دائمة، ولا تدّعي الأداة قياس تفاقم الدين داخل ملف مدرج أصلًا.
- **العواقب:**
  - يمكن منع التراجع فورًا مع إصلاح الدين تدريجيًا.
  - تبقى مراجعة diff يدوية لازمة لاكتشاف زيادة DDL/POST branches أو نمو ملف موجود أصلًا في baseline.
  - لا تُضاف مخالفة جديدة إلى baseline لمجرد تمرير strict؛ توسيعه يحتاج تغييرًا منفصلًا ودليلًا وقرارًا موثقًا.
  - عند إصلاح finding قائم يُحذف من baseline في نفس الدفعة حتى لا يعود بصمت.
  - كل تغيير PHP أو حدود ويب أو baseline يشغل الفاحص مع lint والاختبارات ذات الصلة.

## ADR-007 — لا adapters لأدوات الذكاء الاصطناعي دون تنسيق مثبت

- **الحالة:** معتمد
- **التاريخ:** 2026-07-12
- **السياق:** المصدر المؤكد هو `AGENTS.md`، ولم يُثبت أن ملفات تعليمات خاصة بـClaude أو Gemini أو Copilot أو Cursor مستخدمة فعليًا في هذا المستودع. إنشاء صيغ متوقعة قد يضيف مصادر متعارضة لا تقرؤها الأدوات أصلًا.
- **القرار:** لا تُنشأ tool-specific instruction adapters إلا بعد إثبات اسم الملف وصيغته وآلية تحميله في أداة مستخدمة فعليًا. عند الحاجة يكون adapter رفيعًا يشير إلى `AGENTS.md` ويضيف أقل قدر خاص بالأداة، ولا يكرر الدستور كاملًا.
- **العواقب:**
  - يقل drift وتبقى التعليمات قابلة للمراجعة في موضع واحد.
  - قد لا تحصل أداة غير معروفة على توجيه تلقائي حتى يُثبت تكاملها؛ هذا مقبول أفضل من اختراع تنسيق غير مدعوم.
  - إضافة adapter مستقبلًا تحتاج اختبار تحميل موثق وتحديث هذا السجل إذا أنشأت التزامًا جديدًا.

## قرارات ما زالت مؤجلة

لا تعتمد الموضوعات التالية ضمن القرارات أعلاه: نقل document root إلى `public/`، شكل authorization interfaces النهائي، تسمية PSR-4 التفصيلية، سياسة retention/encryption للمرفقات، توحيد audit stores، أو إعادة تصميم schema المالية. كل منها يحتاج أدلة واختبارات وADR مستقلًا قبل التنفيذ.

## ADR-008 — ملكية دورة قيد الطالب داخل خدمة تطبيق

- **الحالة:** معتمد
- **التاريخ:** 2026-07-13
- **السياق:** كانت `admin/students.php` تنفذ مباشرةً سياسة حالة القيد وحفظ النقل الخارجي ومزامنة القيد وقفل التقييم وفصل درجات الطالب، وتكرر فحص وجود جداول البنية داخل نقطة الدخول.
- **القرار:** يملك `StudentEnrollmentService` تنسيق دورة القيد وآثارها على النقل والتقييم، بينما تبقى `admin/students.php` نقطة دخول متوافقة تجمع الطلب وتستدعي الخدمة. يبقى `StudentEnrollment` بوابة تخزين سجل القيد الحالية حتى استخراج repository أصغر في مرحلة لاحقة.
- **العواقب:**
  - لا تتغير URLs أو أسماء POST أو الجلسات أو SQL الناتج.
  - تُختبر سياسة حالات القيد دون HTTP أو MySQL، وتبقى اختبارات render حارسة لعقد الصفحة.
  - أي مستهلك جديد لدورة القيد يستخدم الخدمة بدل نسخ SQL أو السياسة إلى صفحة أخرى.
  - لا تنفذ الخدمة DDL؛ عدم وجود الجداول الاختيارية يؤدي إلى no-op متوافق كما كان سابقًا.
  - قراءات الاسم والفصل ولقطة النشاط والتحقق من هدف الطالب مملوكة لـ`StudentProfileRepository` بدل SQL داخل نقطة الدخول.
  - يضمن `User::saveStudentProfile()` و`saveStaffProfile()` اتساق الاسم المشتق، ويعيد حفظ مشتقات عمر الطالب من تاريخ الميلاد.

## ADR-009 — مخطط شؤون العاملين يجهز قبل الطلب

- **الحالة:** معتمد
- **التاريخ:** 2026-07-13
- **السياق:** كانت `admin/staff.php` تشغل migration كاملة وأربع عمليات `ALTER TABLE` أثناء كل طلب، مع تجاهل بعض أخطاء المخطط.
- **القرار:** تنتقل الأعمدة القديمة المتبقية إلى migration مؤرخة، ويتحقق `StaffSchemaGuard` للقراءة فقط من الجداول والأعمدة المطلوبة. عدم الجاهزية يفشل بوضوح ويعالج تشغيليًا بتشغيل migrations، ولا يصلح المخطط داخل HTTP.
- **العواقب:**
  - أزيل `admin/staff.php` من خط أساس runtime DDL.
  - يحتاج النشر إلى تشغيل migration runner قبل إعادة فتح الحركة.
  - اختبارات staff التي قد تهيئ schema تعمل فقط على قاعدة `_test` عبر الحارس المشترك.

## ADR-010 — خدمة دورة العمل الوظيفية

- **الحالة:** معتمد
- **التاريخ:** 2026-07-13
- **السياق:** كانت صفحة العاملين تملك تطبيع JSON للحالات والحركات، اشتقاق الملخص الحالي، وحذف/إعادة إدراج سجلات التاريخ مع SQL مباشر واعتماد مخفي على الجلسة.

  - حذف أكثر من 350 سطرًا من قواعد وSQL دورة العمل من `admin/staff.php`.

## ADR-016 — نسخ تقييمات السلوك snapshots داخل مخطط ثابت

- **الحالة:** معتمد
- **التاريخ:** 2026-07-13

## ADR-017 — إيقاف النسخ التلقائي داخل مخطط الإنتاج

- **الحالة:** معتمد
- **التاريخ:** 2026-07-13
- **السياق:** كان `DbAutoBackup` غير مستخدم داخل المستودع ويثبت MySQL EVENT/PROCEDURE تنشئ جداول `backup_*` في قاعدة الإنتاج نفسها؛ هذا ليس backup مستقلًا ويزيد schema drift والحجم ونطاق الصلاحيات.
- **القرار:** تحذف migration `20260713_decommission_db_auto_backup.php` الكائنين القديمين. يبقى الكلاس adapter توافقية قرائية ترفض اعتبارهما مثبتين، وتظل النسخ الفعلية مسؤولية مسار SQL backup المنفصل.
- **العواقب:** أصبح runtime DDL صفرًا، ولن تعمل أي جدولة خارجية كانت تعتمد سرًا على EVENT القديم بعد تطبيق migration. يلزم استخدام نسخ خارج قاعدة الإنتاج مع اختبار استعادة.
- **الرجوع:** إعادة الجدولة تتطلب ADR جديدة ووسيط نسخ مستقلًا؛ لا يعاد إنشاء جداول snapshots داخل مخطط الإنتاج.

## ADR-018 — أوامر ملف الطالب خلف حد تطبيقي

- **الحالة:** معتمد مرحليًا
- **التاريخ:** 2026-07-14
- **السياق:** جمعت `admin/students.php` تصنيف HTTP والتحقق وبناء payload وإنشاء/تعديل المستخدم والملف والقيد وأولياء الأمور وسجلات Activity/Undo داخل handler واحد، مع تكرار كبير بين الإضافة والتعديل.

  - يمكن تطوير واختبار كل حد بعيدًا عن HTML، ويصبح فصل views لاحقًا أقل اقترانًا بمنطق الكتابة.

## ADR-026 — دفعات Undo صريحة بدل التجميع الزمني

- **الحالة:** معتمد
- **التاريخ:** 2026-07-15
- **السياق:** كان التراجع الجماعي يستنتج ارتباط السجلات من تطابق المستخدم والوصف والجدول ووقوعها خلال ثانيتين، ما قد يضم عملية مستقلة إلى التراجع نفسه.
- **القرار:** يضيف المخطط `undo_log.batch_id` اختياريًا ومفهرسًا. تنشئ العمليات المركبة المعرّف عشوائيًا وتضعه صراحة في كل سجلاتها، ولا يجمع `UndoManager` السجلات ذات `batch_id = NULL` مطلقًا.
- **العواقب:**
  - تبقى توقيعات التسجيل القديمة متوافقة لأن معامل الدفعة اختياري.
  - النقل الجماعي وتحديث ملف الطالب/الموظف المركب يتراجعان ذريًا، بينما تبقى العمليات المنفردة مستقلة مهما تقاربت زمنيًا.
  - يلزم تشغيل `20260715_undo_explicit_batches.php` قبل استخدام الكود الجديد.
  - rollback يعيد الكود أولًا ثم يحذف الفهرس والعمود؛ السجلات القديمة لا تحتاج تحويل بيانات.

## ADR-027 — تهيئة العام الجديد ترحيل موجّه لا استنساخ بيانات

- **الحالة:** معتمد مرحليًا في 2026-07-15.
- ينشئ معالج العام سياقًا سنويًا جديدًا ويستخدم خرائط معرفات صريحة؛ لا يستنسخ قاعدة البيانات ولا ينسخ الحركات والنتائج والتدقيق التاريخي.
- تبقى الهوية والملفات والمرجعيات العامة والأصول التشغيلية في موضعها، بينما تنسخ الإعدادات السنوية فقط بعد إعادة ربط اعتمادياتها، وتبدأ معاملات العام الهدف فارغة.
- أي جدول بلا `academic_year_id` ومرتبط بفصل أو نشر مؤرخ لا يدخل النسخ التلقائي قبل إثبات مالكه وسياسته؛ التفاصيل في `docs/new-academic-year-data-policy.md`.
- لا يفعّل العام الهدف قبل تقرير تحقق مستقل، ويكون الرجوع محصورًا في الصفوف التي يسجلها manifest للعملية دون تعديل المصدر.
- تبقى المالية وتكليفات المعلمين والجدول وأرصدة إجازات العاملين قرارات أعمال اختيارية حتى اعتماد قواعدها واختبارات قاعدة معزولة.

## ADR-028 — نواة موحدة للتدقيق والتراجع مع سياسات صريحة

- **الحالة:** معتمد مرحليًا في 2026-07-16، ويمنع تعميم التنفيذ قبل اجتياز بوابة الاعتماد في `docs/architecture-audit/16-audit-undo-system-roadmap.md`.
- يبقى `ActivityLog` و`UndoManager` مهايئين متوافقين للصفحات القائمة، بينما تملك وحدة `src/Modules/Operations/Audit` سياق الطلب وسياسات الكيانات والحقول الحساسة وحساب الفروق.
- كل حدث جديد يحمل `request_id`، ويمكن ربط أحداث العملية المركبة بـ`batch_id`؛ لا تعد الحزمة قابلة للتراجع إذا كان أي عنصر فيها غير مؤهل أو سبق تنفيذه.
- لا تخزن snapshots التراجع كلمات المرور أو tokens أو المفاتيح والأسرار. حذف سجل يحمل بيانات اعتماد لا يستعاد مباشرةً حتى يتوفر تخزين مشفر معتمد؛ يسجل الحدث دون عرض تراجع مضلل.
- المدفوعات المالية reversal-only: يسجل تاريخها ولا يسمح بحذفها عن طريق محرك التراجع العام.
- ينفذ التراجع داخل transaction مع قفل سجلات المحرك والكيانات وفحص الحالة والتعارض، ويسجل التراجع نفسه في `activity_logs` قبل commit.
- إعادة العمل لعملية متراجع عنها تستخدم اللقطات نفسها ولا تنشئ مسار كتابة موازيًا: يعيد `UndoManager` فحص السياسة والحالة الحالية، يقفل الدفعة، ينفذها بالترتيب الأصلي كاملة أو لا ينفذ شيئًا، ثم يعيد سجلها إلى حالة `pending` ويسجل حدث `redo` داخل المعاملة نفسها. تبقى أحداث `undo` و`redo` سجلات تدقيق غير قابلة لأن تصبح مراسي لتراجع أو إعادة جديدة، ولا تتاح إعادة العمل للسياسات التي تمنع التراجع المباشر.
- نقل الأعمدة والفهارس الجديدة مملوك لـ`20260716_audit_undo_engine_v2.php`. لا ينفذ request code أي DDL.
- فحص `tools/audit_write_coverage.php` دليل جرد أولي وratchet مستقبلي، وليس إثباتًا منفردًا لتغطية runtime كاملة.
- اكتمل جرد كتابة الخادم عند صفر مراجعات، وتفوض واجهة `User` دعم اللقطات وترقية بيانات الدخول إلى `UserAuditSupport` مع إبقاء API التوافقي في `UserProfileFacadeTrait`؛ لا ينشئ الاستخراج مسار تدقيق موازٍ.
- اختبارات MySQL الكتابية تستخدم نسخة مخطط بلا بيانات في قاعدة صريحة منتهية بـ`_test`. لا تعد سلسلة الترحيلات التاريخية bootstrap لقاعدة فارغة؛ يظل علاج هذا الدين قرار تهيئة مستقلًا ولا يبرر تشغيل الاختبارات على `educore`.
- الرجوع: تعطيل تنفيذ التراجع أولًا، ثم إعادة المهايئات السابقة؛ تبقى أعمدة السجل الإضافية additive ولا تحذف أثناء rollback التشغيلي.

## ADR-029 — بوابة مستقبلية موحدة لحماية التدقيق والتراجع والمسودات

- **الحالة:** معتمد في 2026-07-16.
- **السياق:** يستخدم المشروع مساعدين ومحررات متعددة، وقد تضيف التغييرات المستقبلية صفحات وجداول وحقولاً وعمليات كتابة لا تعرف تفاصيل المحرك الحالي. الاعتماد على قراءة التوثيق وحدها لا يمنع تجاوز المحرك أو تكرار سلوك المسودة والتراجع محليًا.
- **القرار:** يبقى `AGENTS.md` مصدر العقد الإلزامي، ويصبح `composer quality` مدخل الجودة الوحيد في CI. يضم هذا المدخل lint والتوثيق وسياسة الرفع والمعمارية وماسح تغطية الكتابات وتدقيق واجهة الإدارة. يثبت اختبار التوثيق وجود العقد والأوامر وربط Workflow بها، بحيث يؤدي حذف أي طبقة إلى فشل آلي.
- **العواقب:**
  - كل مرشح كتابة جديد يظهر في `audit-write-coverage` ولا يمر: تنهي الأداة التنفيذ برمز فشل ما دام `AUDIT_REVIEW_REQUIRED` أكبر من صفر، حتى يصبح المرشح مسجلاً أو مفوضاً أو `false_positive` مراجعاً بدليل. استعلامات `SELECT ... FOR UPDATE` التي لا تملك كتابة تصنف صراحةً ولا تُخفى بتوسيع قاعدة الفحص.
  - الحقول الجديدة في الكيان المغطى تدخل في diff، مع مراجعة إلزامية للحجب والتسمية؛ أما الجداول الفرعية والملفات والآثار الخارجية فتحتاج سياسة صريحة.
  - تستخدم النماذج المؤهلة مكونات المسودة ورسالة التراجع المشتركة، وتتحول إضافة role/form جديد إلى تغيير في عقد التغطية واختباره.
  - حماية الفرع في منصة الاستضافة يجب أن تجعل فحص `Quality gates / php-quality` مطلوباً؛ الملف داخل المستودع يعرّف الفحص، لكن إعداد منع الدمج مسؤولية المنصة.
  - rollback البرمجي يعيد scripts والـWorkflow واختبار العقد معًا؛ لا يوجد أثر بيانات لهذا القرار، ولا يجوز تنفيذ rollback منفرد يترك تعليمات بلا بوابات أو بوابات بلا تعليمات.

## 2026-07-20 — Teacher training portal is an intentional SPA exception to the teacher_header.php rule

- Decision: `teacher/training.php`, `teacher/training_my.php`, and `teacher/training_course.php` retain their self-contained `<!DOCTYPE html>` shell and do NOT migrate to `includes/teacher_header.php` / `includes/teacher_footer.php`, despite the AGENTS.md "Teacher Page Structure — MANDATORY" rule that forbids standalone teacher HTML pages.
- Reason: these three pages form a cohesive single-page-application portal, not isolated standalone pages. They share `assets/css/training-common.css`, `assets/js/script.js`, `particles.js`, a dark-mode toggle, and a `quick-nav` that navigates between pages via `fetch` + `DOMParser`, swapping only `.page-content`, `.header-card`, and `.quick-nav`. Certificate PDF/image generation depends on this SPA state via `html2canvas`/`jsPDF`. Migrating to `teacher_header.php` would: (a) break SPA navigation because `DOMParser` would not find `.page-content`/`.header-card`/`.quick-nav` in the shared header output; (b) remove the quick-nav, which is the portal's entire navigation UX; (c) duplicate the navbar (the shared header ships its own); (d) break the certificate generation path. The AGENTS.md rule was written assuming isolated standalone pages and did not contemplate a self-contained SPA portal.
- Compatibility: the portal still satisfies the spirit of the rule's intent — it loads Bootstrap RTL, Font Awesome, jQuery, DataTables, and the centralized `buttons.css`-compatible styling via `training-common.css`; CSRF is enforced via `includes/csrf.php`; sessions are bootstrapped via `includes/session_config.php` + `Utilities::validateSession('teacher')`; activity/audit compliance is met through `AuditService` (in `Training::enrollTeacher`) and `ActivityLog` (in the admin training pages). No parallel auth, validation, or audit stack is introduced.
- Scope: the exception is limited to the three training-portal pages listed above. Any new teacher page that is NOT part of this SPA must follow the standard `teacher_header.php` / `teacher_footer.php` pattern. The exception does not extend to admin pages.
- Consequence: future changes to the shared teacher header/footer (new nav links, CSS, JS) do NOT automatically apply to the training portal — they must be mirrored into `training-common.css` / `script.js` manually if desired. The portal's session bootstrap was normalized to use `includes/session_config.php` (no page-local `session_start()`).
- Rollback: no rollback needed; this ADR documents a decision NOT to perform a migration. If a future redesign of the training portal decommissions the SPA pattern, the pages should be migrated to the shared header/footer and this ADR retired.
## 2026-07-20 — Training system score/audit/security remediation

- Decision: `classes/Training.php` now writes `training_enrollments.score` (computed as the average of best attempts per active unit) inside `updateEnrollmentProgress()`, fixing the previously-broken `AVG(score)` statistics in `getAdminStats()` / `getTeacherStats()` / `training_reports.php`. `issueCertificate()` accepts `score = null` and reads the actual enrollment score instead of a hardcoded `100`. `submitAttempt()` validates unit ownership against the teacher's enrollment. `createAttempt()` enforces `MAX_ATTEMPTS_PER_UNIT = 3` and blocks retries after a passed attempt. `verifyCertificateByNumber()` matches case-insensitively. Certificate numbers use a 12-char random suffix (`bin2hex(random_bytes(6))`) instead of 4 chars from `uniqid()`.
- Reason: the `training_enrollments.score` column was never written by any method, so all average-score statistics returned 0. The hardcoded `score = 100` on non-quiz completion printed misleading pass rates on certificates. No attempt limit and no unit-ownership check allowed unbounded retries and a cross-course authorization gap. Case-sensitive certificate lookup failed on lowercase input. Predictable 4-char cert suffixes enabled enumeration of public verification.
- Audit/ActivityLog compliance: `admin/training_programs.php` and `admin/training_courses.php` now call `ActivityLog::logCreate/logUpdate/logDelete` for programs, courses, units, and questions. Four new target types (`training_program`, `training_course`, `training_unit`, `training_question`) are registered in `ActivityLog::getTargetLabel()`. Admin pages now follow the PRG pattern end-to-end (including the error path).
- Security: `verify_certificate.php` uses a new file-based `classes/RateLimiter.php` (15 lookups/minute/IP) stored under `storage/framework/rate_limits/` (protected by the existing `storage/.htaccess` `Require all denied`). Rate-limited requests return HTTP 429 with a user-facing message. `teacher/training.php` and `teacher/training_course.php` now follow PRG (POST → session message → redirect → exit) instead of rendering directly after POST. `training_my.php` now boots via `includes/session_config.php` (no page-local `session_start()`). The certificate verify link in `training_my.php` uses `APP_URL` instead of the legacy `SITE_URL`.
- Accepted risks (documented in code, no fix): (1) no `end_date` enforcement on courses is by design — `training_courses` has no `end_date` column, courses stay open until an admin disables them; (2) unit `content` is rendered as raw HTML by a trusted admin — an HTML purifier at input time is recommended for future hardening but no new dependency is introduced now.
- Rollback: revert the commits; no schema migration is involved (the `score` column already existed). New certificate numbers use the longer format; pre-existing certificates keep their original numbers and still verify via the case-insensitive `UPPER()` lookup.

## 2026-07-24 — DataTables action return uses a centralized one-shot bridge and progressive row actions (expanded system-wide 2026-07-26)

- Decision: `assets/js/datatable-state.js` is the single owner of DataTables action-return state. It remembers paging, page length, global search, and ordering in memory during the visit, writes them to `sessionStorage` only for a non-cancelled same-page `POST` or semantic full-page row action, and consumes the stored value on the first following list load. Source, action, and inferred canonical list contexts are linked aliases deleted together; `data-datatable-return-url` provides an explicit return context for exceptional documented flows. Shared admin and teacher headers load it before DataTables initialization (`specialist_header.php` delegates to the admin header); confirmed standalone teacher DataTables pages load the same asset explicitly.
- Navigation semantics: changing the table display alone does not persist anything. Leaving the page normally, returning later, or refreshing manually starts from the table defaults. Same-page POST bridges expire after two minutes. A row-action link identified by a standard action class or `action` plus an approved entity ID opens a 30-minute journey so a full edit form can be completed; ordinary table links are not captured, and exceptional links can opt in/out explicitly.
- Scope and privacy: the bridge is namespaced by a one-way session/portal fingerprint, normalized page context, stable table identity, and a schema fingerprint. The allow-list excludes row selection, extension payloads, modal state, credentials, and column visibility; the existing `admin_table_actions.js` remains the sole owner of column settings. Legacy `educore:datatable-state:v1:` persistent entries are removed automatically.
- Compatibility: server-side and client-side DataTables inherit the same callbacks without changing endpoints, request fields, CSRF, SQL, POST handlers, or PRG. Tables may opt out with `data-datatable-return-state="false"`; cross-endpoint POST forms must opt in explicitly with `data-datatable-return="true"` only when their documented redirect returns to the source list. AJAX mutations retain paging with `ajax.reload(null, false)`, while result-changing filters intentionally reset paging.
- Stable row context: action forms and links identify the target row by entity identity rather than scroll coordinates. Approved row data attributes and fields remain primary contracts, and same-origin action-link query IDs provide centralized coverage for legacy/server-side presenters. Identity matching respects priority order to avoid a related link ID winning over the clicked action ID. After PRG or a full-page return, the bridge waits for the relevant DataTables draw, resolves that identity, scrolls only when needed, focuses and announces the row, and applies a short centralized highlight that respects reduced-motion settings. If the mutation legitimately removes the row from the result set, the table position is retained without guessing a replacement row.
- Progressive AJAX: `assets/js/datatable-state.js` exposes an explicit opt-in submit adapter for eligible single-row modal writes, while `classes/Ajax/DataTableActionResponder.php` centralizes JSON/PRG response negotiation without owning business writes. The existing server handler remains the sole write owner and returns JSON only for the negotiated `datatable_ajax=1` XMLHttpRequest; ordinary requests retain PRG. The first reference migration is `admin/staff_accounts.php` for credentials, role access, and status actions, reusing the same authorization, transaction, audit, and CSRF path and refreshing the server-side table without resetting paging. Upload, import, batch, finance, and external-effect flows remain PRG unless separately specified and tested.
- Future enforcement: `composer datatable-state-audit` inventories direct PHP initializers and mapped embedded student/staff/class-list initializers, rejects page-local state callbacks and reset-display controls, verifies shared and standalone asset coverage, asserts the full-page action-link journey, includes enrolled students as a server-side reference flow, and executes the JavaScript behavior test. It is part of `composer quality`, and the root instructions and concise coding rules carry the same ownership contract.
- Rollback: remove the shared asset references and the asset itself, remove the dedicated quality gate and documentation markers, then revert this ADR. No database or persisted server data rollback is required.

## ADR-032 — خريطة انتقال الفصول تحفظ جماعة الصف وتفصل الراسبين

- **الحالة:** معتمد في 2026-07-28.
- **السياق:** كان الترحيل ينسخ الفصل داخل الصف نفسه ثم ينشئ جميع قيود الناجحين والراسبين بلا فصل. هذا يحفظ البنية لكنه يفقد جماعة الفصل التي يرغب المستخدم في استمرارها إلى الصف الأعلى، ويجعل تسكين جميع الناجحين عملاً يدويًا.
- **القرار:** يملك `class_rollover_mappings` خطة مراجعة لكل زوج أعوام وفصل مصدر. نوع `cohort` ينشئ فصلًا في الصف المحدد بقاعدة الانتقال وبالاسم والسعة القابلين للتعديل، ونوع `entry_template` ينشئ فصلًا فارغًا لأول صف دخول أو لاستكمال فرق عدد الفصول بين الدفعات. يستطيع المستخدم تعطيل إنشاء فصل أو تعطيل تسكين طلابه تلقائيًا قبل المعاينة.
- **الطلاب:** الطالب المقيد الناجح يتبع فصل مجموعته فقط عند وجود خريطة `cohort` مفعلة للتسكين؛ الناجح بلا فصل مصدر أو الذي اختير له التنظيم اليدوي يبقى بلا فصل. الراسب يبقى في صف المصدر بلا فصل، والخريج والمنقول والمنقطع لا يحصلون على قيد هدف. القرار المعلق يظل مانعًا للتفعيل.
- **الحماية:** أسماء الفصول المكررة داخل الصف الهدف والسعة الأقل من عدد الناجحين تمنع التنفيذ. تدخل الخريطة في بصمة المصدر، وتتحقق الروابط مستقلًا من أن الفصل المعيّن مملوك لتشغيل التهيئة وفي العام والصف الهدف الصحيحين.
- **التدقيق والرجوع:** حفظ الخريطة يمر عبر `AuditService`، والفصول والقيود الناتجة تظل مملوكة لـmanifest التهيئة وتحذف بترتيب الرجوع القائم قبل التفعيل. الترحيل `20260728_class_rollover_mappings.php` additive وطُبّق على `educore` في 2026-07-29 بعد نسخة احتياطية كاملة موثقة.
- **الواجهة:** أضيفت خطوة «خريطة الفصول» إلى `admin/academic_year_setup.php` باستخدام مكونات Bootstrap وطبقة الإدارة المركزية فقط؛ لا توجد هوية بصرية أو CSS محلي جديد.

## ADR-033 — التصنيف التجريبي للهيكل الأكاديمي مركزي وموروث

- **الحالة:** معتمد في 2026-07-29.
- **السياق:** كان الصف وحساب الطالب فقط قابلين للتصنيف التجريبي، ولذلك لا يمكن إنشاء مرحلة أو فصل تجريبي كاملين، كما يمكن أن تتسرب عناصر تجريبية إلى تهيئة العام عند الاعتماد على علامة الصف وحدها.
- **القرار:** تملك `ExperimentalAcademicScopePolicy` القاعدة المركزية. لكل مرحلة وصف وفصل علامة مباشرة قابلة للعكس، والحالة الفعالة تورث نزولاً: المرحلة تجعل صفوفها وفصولها تجريبية، والصف يجعل فصوله تجريبية. يظل `users.is_test_account` استثناءً مستقلاً على مستوى الطالب. تعرض الواجهات الفرق بين «تجريبي مباشر» و«تجريبي موروث» دون نسخ العلامة الموروثة إلى الأبناء.
- **سلامة الانتقال:** يمنع تحويل نطاق يضم طلابًا رسميين إلى تجريبي، كما يمنع تحويل نطاق يضم حسابات تجريبية إلى رسمي؛ يسمح بتغيير النطاق الفارغ. تنطبق الحماية كذلك عند نقل صف بين المراحل أو فصل بين الصفوف.
- **تهيئة العام:** تستبعد المعاينة والخطة والتنفيذ حسابات الاختبار وكل طالب يرث التصنيف من مرحلته أو صفه أو فصله، كما لا تنشئ خريطة فصول من أي نطاق تجريبي. تعتمد جاهزية الصفحة على migration ولا تنشئ مخططًا أثناء طلب الويب.
- **النطاق المؤجل:** ربط هذا التصنيف بأثر مالي أو إشعارات أو تقارير تاريخية محمية ليس ضمن هذا القرار؛ يحتاج كل مالك نطاق إلى سياسة وعقد واختبارات منفصلة قبل تغيير سلوكه.
- **التدقيق والرجوع:** الإضافة والتعديل تستخدمان مسار التدقيق/التراجع القائم لكي تلتقط الحقول الجديدة ضمن before/after. يملك `20260729_academic_structure_experimental_scope.php` الأعمدة والفهارس additive، وطُبّق على `educore` في 2026-07-29 بعد نجاح استعادة حزمة التعافي `2a27f50841e71c7e5e7338dc2b2fbbc3` داخل قاعدة معزولة. الرجوع البرمجي يعطل الاستعمال أولاً؛ لا تحذف الأعمدة ذات البيانات إلا بترحيل رجوع منفصل وبعد نسخة احتياطية.

## 2026-07-23 — Finance module: unified sub-ledger, GL in v1, reversal-only, maker-checker

- Decision: a new incremental `src/Modules/Finance` module is established with a unified sub-ledger truth source (`finance_subledger_accounts` + `finance_subledger_transactions` + `finance_subledger_lines`) covering BOTH students and staff via `party_type` and `bucket_code`. Balances (`outstanding_due`, `unapplied_credit`, `net_account_position` for students; `payroll_payable`, `advance_receivable`, `settlement` for staff) are computed EXCLUSIVELY from `SUM(amount_delta)` per bucket — never from domain-table sums or a fixed list of table names. Full double-entry GL is in scope for v1 (chart of accounts, journal entries/lines, account-mapping, control accounts, vouchers, budget). Every posted operation creates its domain record + sub-ledger transaction/lines + GL journal (1:1 via `source_idempotency_key`) inside the same transaction; failure of any rolls back the whole operation. Reversals create new `posted` transactions with opposite deltas (`original + reversal = 0`; original never excluded from SUM; `is_reversed` is derived). Sub-ledger `status` is `draft|posted` only (no `reversed`). Refunds are NOT auto-subtracted: `refund_allocation` restores outstanding_due; `refund_unapplied_credit` shrinks credit. Discount rules are versioned with `scope_charge_type_key` (`ALL` or specific) and MariaDB-safe activation via `FOR UPDATE` (no partial index). `staff_advance_installments` is the primary repayment schedule source. `payroll_periods` unique by `finance_period_id+start_date+end_date` (not name). General vouchers (expense/other_income/cash_transfer) in v1; AP/supplier explicitly out of scope. MANDATORY maker-checker for receipt reversal, refund, write-off, manual journal, import posting, payroll approval/payment, period reopen, manual/exception discounts. Money is integer piaster minor units (EGP); no PHP float for financial math. `FinancePeriodGuard` extends `AcademicYearWriteGuard`. Cross-module Query contracts owned by source modules (StudentEnrollmentQuery→Students, StaffEmploymentQuery→StaffHr, BusSubscriptionQuery→Transport, AcademicYearQuery→AcademicStructure).
- Reason: the legacy finance code (`fee_payments.php`, `staff_financial_data.php`) had no unified ledger truth source, no reversal-only enforcement at the write layer, audit after commit, client-computed net salary, float money math, editable balance columns, and no GL. The user approved full GL in v1 and resolved all business decisions (D-1..D-4, C2, U1).
- Compatibility: legacy admin pages remain HTTP entrypoints; they become thin adapters that delegate to Finance services while preserving URLs, POST fields, and JSON contracts. `AuditService`/`UndoManager`/`ActivityLog` reused; no parallel audit path. `storage/private/db_backups` NOT used as a truth source; schema inspected only from `*_test`.
- Compatibility completion (2026-07-28): fee structure/calculator/collection/DataTable/staff-finance requests now translate field-for-field into application services in execute mode. Posted discounts that were not part of the original charge create an immutable credit-note adjustment, sub-ledger movement, and balanced GL journal; discounts already included in the charge remain metadata-only to prevent double credit. Same-day legacy salary changes create immutable `staff_compensation_contracts.version_number` revisions. Compatibility provenance is recorded in `finance_legacy_compatibility_mappings`.
- Ownership correction (2026-07-28): `student_buses.php` writes are owned by `src/Modules/Transport` through `LegacyStudentBusAssignmentService`; unassignment archives the annual row and bulk updates validate before writing. `bus_report.php` remains a Transport report and `statements.php` remains an official-document workflow, so both pass through unchanged instead of being redirected to Finance. This is a compatibility requirement, not an exception.
- Consequence: future finance work builds on the unified sub-ledger; no parallel student-ledger table is allowed. The resync workflow (spec-only commit → adopt main changes in reviewed commit → merge/rebase → overlap check) must complete before any code on the seven overlapping files.
- Rollback: code rollback disables Finance services/adapters; data rollback uses reversal batches and manifest-owned migration rollback (DROP new tables only, never legacy).

## ADR-050 — ملخص بيانات العامل الحالي read model توافقي فوق السجل الوظيفي

- **الحالة:** معتمد في 2026-07-29.
- **القرار:** يظل `staff_status_history` و`staff_job_movements` سجلي الأحداث التاريخية، بينما تحفظ أعمدة `staff_profiles` الوظيفية الملخص الحالي الذي تعتمد عليه القوائم والتقارير القديمة. عند فتح التعديل، تُستكمل الحقول الناقصة فقط في حدث الحالة الفعال من ملخص الملف؛ أي قيمة تاريخية صريحة لا تُستبدل. تستخدم أنواع التعاقد القياسية المفاتيح `permanent|temporary|parttime|other` في التخزين، وتبقى القيمة المخصصة نصًا كما أدخلها المستخدم.
- **التوافق:** لا تتغير URLs أو أسماء حقول POST أو شكل JSON. مصدر واحد يزوّد قائمة المسميات والأقسام لكل من PHP وJavaScript، ويستمر `staff_profiles` في خدمة القراء القدامى. يطبّق المصدر قاموسًا واحدًا يدمج «مدير مرحلة/منسق إداري/رئيس قسم/مدرس أول/منسق قسم» في «معلم»، و«مسؤول المكتبة» في «أمين مكتبة»، و«أخصائي اجتماعي/أخصائي نفسي» في «أخصائي»، و«مشرف حسابات/مدير حسابات» في «محاسب». تمر كل قوائم العاملين والحضور والمالية والتعيينات والتقييمات والبحث وعقود القراءة المشتركة عبر هذا المصدر قبل العرض، وتوسّع الفلاتر القيمة القانونية إلى مرادفاتها المخزنة أثناء فترة الانتقال. يعامل المصدر «قسم الإعلام» كقيمة محذوفة، ويحوله إلى `NULL` في القراءة والحفظ والترحيل. الترحيل `20260729_staff_employment_summary_consistency.php` ينشئ الحدث الحالي عند غياب السجل، ويملأ القيم الفارغة فقط ويطبّع أنواع العقود والمسميات عبر كل من الملخص وسجل الحالة والحركات، ويمكن تشغيله أكثر من مرة دون مضاعفة أو طمس قيمة غير مشمولة بالقاموس.
- **الحدود:** لا يغير هذا القرار أولوية حدث حالة مقابل حركة وظيفية عند تساوي/اختلاف التواريخ؛ تغيير قاعدة الحسم بين السجلين يحتاج قرار أعمال واختبارًا مستقلاً.
- **الرجوع:** يمكن التراجع عن كود التوافق بإزالة hydration وإعادة القوائم المحلية. التراجع عن backfill بعد تشغيله يتم باستعادة نسخة قاعدة البيانات السابقة للترحيل، لأن تحويل قيمة صحيحة لاحقًا إلى `NULL` بالتخمين غير آمن.

## ADR-051 — اكتمال بيانات الطالب يجمع قراءتين مستقلتين للملف والسجل السنوي

- **الحالة:** معتمد في 2026-07-29.
- **السياق:** كانت صفحة الاكتمال تقرأ العام الحالي فقط، وتخلط الفصل بالصف، وتخفي الطالب الذي لا يملك سجل قيد، وتحسب بطاقات الإحصاء بشروط تختلف عن الجدول. كما كان تخصيص الأوزان يكتب مباشرة في ملف JSON من طلب الويب بلا تدقيق أو تراجع.
- **القرار:** يملك `StudentCompletenessReadRepository` قراءة القائمة والإحصاءات والفلاتر. تبقى نسبة «اكتمال الملف» مشتقة من الملف الدائم وبيانات أولياء الأمور والمرفقات وفق الحقول المكوّنة، بينما تُقيّم «سلامة السجل السنوي» مستقلاً من `student_enrollments` للعام المختار: سجل مفقود، بنية ناقصة، تسكين غير متسق، انتظار فصل، أو سجل سليم. تستخدم القائمة والإحصاءات مصفوفة الفلاتر نفسها.
- **السنوات والنطاق:** تعتمد الصفحة حصريًا على العام المختار من الشريط العلوي المشترك عبر `AcademicYear::getCurrent()`، ولا تعرض مرشح عام مستقلًا ولا تقبل نقطة AJAX عامًا بديلًا من الطلب؛ ويمكن استعراض الأعوام السابقة بتغيير العام من الشريط العلوي. لا تُسند السجلات المفقودة تاريخياً بالتخمين؛ تظهر حالة السجل المفقود في العام الحالي فقط عند بقاء ملخص الملف مقيداً. يطبق `ScopedStaffPortalContext` نطاق الفصل ويفشل مغلقاً، وتُستبعد الحسابات والبنية التجريبية الموروثة افتراضياً مع فلاتر صريحة لإظهارها.
- **الإعدادات:** يبقى `config/student_fields_config.json` تعريفاً موثوقاً للمفاتيح والمصادر. تحفظ الواجهة الأولوية والوزن فقط في `settings.student_completeness_fields_v2` عبر `StudentCompletenessConfigService`، وتكتب الإعداد وسجل `AuditService`/Undo في معاملة واحدة. لا ينشئ القرار مخططاً ولا يكتب إلى ملف من الويب.
- **التوافق والرجوع:** تبقى مسارات الصفحة وAJAX وأسماء الإجراءات `datatable_data`, `stats`, و`save_fields_config`. الرجوع يعيد المهايئ السابق ويحذف قيمة الإعداد اختيارياً عبر مسار إعدادات مدقق؛ لا يوجد ترحيل قاعدة بيانات أو فقد لتاريخ الطلاب.

## ADR-052 — رقم البصمة مصدره ملف العامل مع مرآة توافقية للحضور

- **الحالة:** مستبدل في 2026-07-30 بالقرار ADR-053 بعد إثبات أن حقول الهوية مستقلة.
- **السياق:** كانت صفحات أجهزة البصمة والحضور تستخدم `users.employee_code` كمعرف للجهاز، بينما أضاف ملف العامل `staff_profiles.biometric_id` وعرضه دون ترحيل أو مزامنة. أدى ذلك إلى إخفاء 246 قيمة موجودة، وإلى حفظ الفراغ `''` داخل فهرس فريد وعرض أخطاء PDO الخام للمستخدم.
- **القرار:** يصبح `staff_profiles.biometric_id` مصدر الحقيقة لرقم البصمة. تملك `StaffBiometricIdentityService` الكتابة المتزامنة داخل معاملة المالك، وتبقى `users.employee_code` مرآة توافقية مؤقتة لقراء الحضور والأجهزة. القراءات خلال نافذة التوافق تستخدم قيمة الملف ثم المرآة القديمة عند غيابها. لا يتغير اسم حقل POST القديم `employee_code` في صفحات الأجهزة.
- **سلامة الحفظ:** تتحول القيمة الفارغة إلى `NULL`، ويُرفض التكرار قبل الكتابة مع بقاء القيود الفريدة حماية سباق نهائية. تعرض `StaffProfileErrorPresenter` رسائل عربية ثابتة وتضع تفاصيل PDO في السجل الآمن فقط. تستخدم صورة العامل `FileUploadGuard` واسمًا عشوائيًا، ويفشل الحفظ كله إذا تعذر نقل الصورة. تشترك تغييرات الملف وسجل الحالة والحركات في `UndoManager` batch واحد.
- **الحقول المخصصة والملكية:** أصبحت `religion` و`marital_status` و`contract_type` في `staff_profiles` حقول `VARCHAR(100)` حتى تحفظ قيمة «أخرى» دون إسقاط صامت من ENUM. لا يعرض نموذج العامل ملخصات الرواتب أو الإجازات؛ تبقى قراءتها وكتابتها داخل Finance و`StaffLeaveService`.
- **الترحيل والرجوع:** يطبع `20260730_staff_profile_data_consistency.php` الفراغات، يرفض التعارض بين المصدرين، وينقل المرآة القديمة إلى المصدر الجديد بصورة idempotent. طُبّق محليًا بعد نسخة SQL كاملة، فنُقلت 246 قيمة بلا تعارض. الرجوع يتطلب استعادة النسخة السابقة؛ إعادة الحقول إلى ENUM قد تفقد قيمًا مخصصة صحيحة.

## ADR-053 — فصل كود العامل الداخلي عن رقم البصمة ومعرف الحضور القديم

- **الحالة:** معتمد في 2026-07-30، ويستبدل جزء الهوية في ADR-052.
- **السياق:** أثبت ترحيل `20260707_staff_biometric_and_ministry.php` والكود المولّد أن `staff_profiles.employee_code` كود داخلي بصيغة `E{YYYY}{NNNN}` وأن `staff_profiles.biometric_id` رقم جهاز مستقل. كما أن `users.employee_code` حقل توافق قديم للحضور وليس مرآة لأي منهما. أثبتت نسخة ما قبل الإصلاح وجود صفر أرقام بصمة و246 قيمة توافق قديمة؛ لذلك كان نسخ القيم بينها افتراضًا خاطئًا.

- **الترحيل والرجوع:** يعكس `20260730_staff_profile_identity_separation.php` النسخ الخاطئ المثبت بالنسخة الاحتياطية، ويعيد توليد الأكواد التجريبية غير المطابقة بترتيب ثابت مع إبقاء قيمها القديمة في `users.employee_code`. الرجوع متاح من نسخة SQL السابقة.

- **مركز الاستثناءات:** يقرأ `AttendanceExceptionQueryService` سجلات البصمة التي تحتاج مراجعة، وأحدث نسخة غير محسومة لكل يوم، وفروق التشغيل الظلي `LEGACY_*` عبر عقد Attendance قرائي مستقل. لا تنضم هذه القراءة إلى جداول ملفات العاملين، ولا تعرض هوية البصمة أو موضع الحمولة الخام أو المرفق أو سبب المطابقة الداخلي. سطح `admin/hr_attendance_exceptions.php` يوجه المسؤول إلى مدخل المراجعة المتوافق ولا يكتب أو يعتمد أو يصحح أي سجل؛ لذلك يظل تصحيح البيانات تحت المالك المتخصص ومسار التدقيق القائم.
- **بوابات التوافق للحضور:** يبقى `admin/staff_biometric_import.php` على مساره القديم فقط في وضع `off`. في أي وضع طرح جديد يقبل ملف البصمة معرف الجهاز ووسيلة الإدخال والمنطقة الزمنية، ثم يمرر الدليل الخام إلى `AttendanceEventIngestor` دون تحويل `user_id` أو كود موظف ودون مزامنة `staff_attendance`. تظل الصفحة تعرض هوية مقنّعة في المعاينة وتوجّه السجلات غير المربوطة والمتعارضة إلى مركز الاستثناءات. أما `admin/staff_attendance.php` فيعرض ملخصًا قرائيًا للاستثناءات أثناء الطرح، ويحجب الحفظ والحذف في وضع `official` بدلاً من كتابة السجل القديم؛ التعديل الرسمي لا يمر إلا بمسار تصحيح Attendance الموثق.
- **سياسات الأذونات ودفتر الحصة:** يملك `Staff` نوع الإذن ونسخه المؤرخة ونطاقاتها والطلب وشرائح الأشهر ودفتر الحصة. يبدأ الطلب مسودة فقط، ويثبت عند الإرسال نسخة السياسة والموظف/سير العمل ومعرّف إعادة المحاولة وتوزيع الدقائق بالكامل على الأشهر. نسخة السياسة المنشورة لا يعاد تحريرها؛ يسمح فقط بانتقالها إلى `retired` دون تغيير القواعد، وتبقى نطاقاتها تاريخًا غير قابل للتعديل حتى بعد التقاعد. تبقى معرفات التعيين وسير العمل مراجع scalar مجمّدة تتحقق منها عقود المالك عند الإرسال لأن مخطط سير العمل يأتي لاحقًا في ترتيب migrations.
- **حل السياسة الفعالة:** يقرأ `PermissionPolicyResolver` نوع الإذن من `PermissionPolicyReadRepository` ثم يأخذ لقطة التعيين المؤرخة من `StaffAssignmentAtDateQuery` عند بداية فترة الطلب؛ لا يعتمد على ملف عامل حالي أو عضوية مجموعة حاضرة. يطبق ترتيب النطاق `global → job_title → org_unit → group → staff` ثم الأولوية وبداية السريان، ويعيد `PERMISSION_POLICY_CONFLICT` مغلقًا مع نسخ السياسات المتساوية بدلاً من اختيار إحداها. مهايئ PDO يقرأ جداول سياسة Staff فقط ويستقبل اللقطة من العقد.
- **دورة طلب الإذن:** يملك `PermissionRequestService` فقط كتابة مسودة العامل وإرسالها وسحبها وإلغاء الطلب المعلق. تثبت الخدمة أن العامل هو صاحب الطلب ثم تستدعي `PermissionRequestAuthorization` لشرط الأهلية الحالية والاستثناء الرجعي واستثناء الحصة، فلا يصبح الدور القادم من المتصفح دليلاً. المسودة لا تحمل سياسة أو سير عمل مصطنعًا؛ الإرسال يحل السياسة والتعيين المؤرخين، ويأخذ لقطة `PermissionSubmissionWorkflowResolver`، ويقسم الفترة على حدود الشهور، ويستخدم `PermissionRequestOverlapQuery` المقفل بدل قراءة جداول إجازة أو مأمورية خاصة بوحدة أخرى. بعد الحجز يستدعي الإرسال `ApprovalWorkflowSubmissionGateway` في المعاملة نفسها ثم يربط instance الدائم بالطلب بقفل متفائل؛ غياب البوابة أو فشل الربط يفشل مغلقًا ولا يترك طلبًا معلقًا بلا مسار اعتماد. مهايئ PDO الحالي يعرض تعارضات الأذونات المملوكة لـStaff فقط؛ يضاف دمج الإجازات والمأموريات لاحقًا عبر هذا العقد نفسه لا عبر وصلة SQL عابرة للوحدات.
- **حل مسار الاعتماد والتفويض:** يملك `ApprovalWorkflowResolver` تحويل النسخة المنشورة الفعالة إلى لقطة مراحل ومعتمدين قبل إنشاء instance. يقرأ التعريف عبر `ApprovalWorkflowDefinitionQuery`، وعلاقة المدير الأصلية المؤرخة عبر `ManagerHierarchyAtDateQuery`، وعضوية الدور النشطة التي تُثبت وقت الإرسال عبر `ApprovalRoleAssigneeQuery`. يبقى `PdoManagerHierarchyQuery` محايدًا لنوع الطلب ولا يختار نائبًا مبكرًا؛ يملك `ApprovalDelegationQuery` وحده التفويض لأن لديه نوع المورد ونوع الإذن والنطاقات، فيفاضل بين global/unit/group/request-type/staff ويرفض التعارض أو JSON غير الصحيح. القرار بالإنابة يحفظ المعتمد الأصلي في `acting_for_user_id` ولا تتبع الخدمة سلسلة إنابات. غياب المدير لا يمر إلا إلى `fallback_user_ids` المنشورة في المرحلة أو يفشل مغلقًا؛ لا يوجد اختيار عشوائي لإداري.
- **حالة الاعتماد الذرية:** يملك `ApprovalWorkflowService` الانتقالات `submit/decide/reassign/escalate` عبر `ApprovalWorkflowRepository` فقط؛ تحفظ instance والمراحل والمعتمدين والقرار/حدث التصعيد وحدث التدقيق في معاملة واحدة. تستخدم المرحلة وinstance إصدار قفل متفائلًا مع `FOR UPDATE` في MySQL، ويتحقق مفتاح إعادة المحاولة من المورد والنسخة واللقطة المجمدة أو من المعتمد والقرار والتعليق، فلا تتحول الإعادة ذات الحمولة المختلفة إلى نجاح صامت. تصمم قواعد النصاب والتعادل والرفض من اللقطة، ويعني `same_actor_rule=merge` استبعاد المعتمد المكرر من المرحلة اللاحقة ووسمها كمندمجة؛ إذا لم يبق معتمد تتخطاها الخدمة بدل أن تطلب القرار نفسه مرتين. لا تكتب طبقة PDO قرارًا تجاريًا مستقلاً. لمورد `permission_request` يملك `PermissionApprovalOutcomeHandler` وحده انتقال النتيجة النهائية وحركات الحصة append-only (استهلاك أو تحرير/حجز ثم استهلاك)، ويفشل المورد غير المعروف أو الطلب/الحجز المتقادم مغلقًا؛ فشل التدقيق أو معالج نتيجة المورد يؤدي إلى rollback كامل.
- **صندوق المعتمد:** لا يقرأ سطح المدير جميع طلبات العاملين ثم يفلترها في PHP. يملك `AssignedApprovalInboxReadRepository` إسقاطًا مقيدًا عند قاعدة البيانات لـ`assignee.status=eligible` و`step.status=active` و`instance.status=pending` وتسلسل المرحلة الجاري فقط، ثم يزيل `AssignedApprovalInboxQuery` أي لقطة خام أو سبب خاص من النتيجة. يعيد الصندوق فقط معرّفات المورد والقفل واسم المرحلة وموعدها ودليل `acting_for` المجمّد، ويعامل JSON الفاسد كفشل مغلق لا كسجل جزئي.
- **عرض قرار المدير:** `ManagerApprovalInbox` مكوّن Presentation بياناتي فقط؛ لا يملك SQL أو جلسة أو قرارًا أو صلاحية. يستقبل من المدخل المعتمد صفوف الصندوق وأسماء العاملين ومفاتيح idempotency صادرة من الخادم وCSRF، ويعرض الموافقة مباشرة ورفضًا بمودال Bootstrap يفرض سببًا. عداد لوحة المدير رابط مقيد للصندوق نفسه، ولا يُمرَّر `staff_user_id` أو اللقطة الخام في أي نموذج. يظل `admin/hr_center.php` مدخل التوافق: لا يعرض هذا المسار الجديد إلا في `display|official`، ويستدعي الصندوق المقيد للحساب الحالي فقط؛ في `official` تحجب إجراءات الاعتماد السريعة القديمة بدل أن تنافس حالة الاعتماد الذرية.
- **إشعار الاعتماد:** يملك `ApprovalNotificationService` نية إشعار محايدة عند إسناد مرحلة أو إعادة إسنادها أو تصعيدها؛ لا يضع سبب الطلب أو مرفقه أو لقطة المورد في النص أو metadata. يمرر النية إلى `StaffNotificationPort` الذي يكتب inbox ثم retryable outbox بمفتاح حدث/إعادة محاولة ثابت لكل مستلم. يركب `StaffModuleFactory` المنفذ على PDO و`AuditService` نفسيهما، لذلك يفشل إرسال نية outbox انتقال الاعتماد بدل أن يترك مرحلة نشطة بلا تنبيه؛ لا يستدعي المسار أي مزود push مباشرة.
- **إعادة التحقق الحي للاعتماد:** لا تتحول لقطة المعتمد المجمدة إلى صلاحية دائمة. يمر قرار أو إعادة إسناد أو تصعيد الإنتاج عبر `ApprovalTransitionAuthorization` قبل أي كتابة؛ فيتحقق `PdoApprovalActorEligibilityQuery` من الحساب النشط ومن سريان تكليف المدير الأساسي عند علاقة مدير، ويعيد `PdoApprovalDelegationRevalidationQuery` فحص التفويض المحدد بهويته والطرفين وفترته نصف المفتوحة. يبقى المعتمد الأصلي دليلاً تاريخيًا ولا يعاد حل المسار، لكن الحساب الموقوف أو الخدمة المنتهية أو التفويض الملغى/المنتهي يفشل مغلقًا. أما إعادة الإسناد/التصعيد فتتطلب مديرًا مخولًا حيًا وتمنع استهداف حساب غير نشط.
- **إدارة المسار والتفويض:** يملك `ApprovalWorkflowAdministrationService` وحده إنشاء workflow/version/stage والتفويض وتغيير حالاتهم عبر `ApprovalWorkflowAdministrationRepository`. كل نسخة تبدأ مسودة ولا تعدل النسخة المنشورة؛ النشر يتحقق من وجود مرحلة، ومن عدم التداخل، ويغلق فقط النسخة المنشورة المفتوحة السابقة عند بداية نسخة مفتوحة أحدث داخل المعاملة نفسها. التفويض النشط لا يقبل تداخلًا في النطاق نفسه، ولا يحذف عند الإيقاف أو الإلغاء؛ عند إعادة التفعيل يعاد فحص الحسابين والمدة والتداخل. يسجل التدقيق معرفات ونطاقات وhash للسبب لا نصه الحر. `admin/hr_approval_workflows.php` مدخل Admin مصرح/CSRF/PRG لا يملك SQL، ويستعمل مودالات Bootstrap لإجراءات النشر والحالة.
- **بوابة العامل ومسوداتها:** يعرض `StaffSelfServiceRequests` نموذج بيانات فقط من `Presentation` ولا ينفذ SQL أو يقرر أهلية أو يقبل `staff_user_id` قابلًا للتغيير؛ محول البوابة يشتق العامل من الجلسة ويعيد فحص الخدمة للملكية في كل POST. المدخل المشترك `staff_hr_portal.php` لا ينشئ مكدس دخول أو دورًا جديدًا، بل ترتبط به بوابات المعلم والأخصائي والمشرف والإدارة الحالية، ويعيد `StaffPortalEligibilityQuery` إثبات الخدمة بصرف النظر عن الدور النشط. يمر عرض أنواع الإذن والإجازة والأرصدة والطلبات عبر `StaffSelfServicePortalReadRepository` داخل Staff، بينما يركب `StaffModuleFactory` كتابة الإذن على `PermissionRequestService` ودورة الإجازة على `LeaveRequestService` و`LeavePolicyReadRepository`؛ وتدخل مواعيد العمل وأثر التغطية من Attendance فقط عبر `LeaveWorkdayCalendarQuery` و`AttendanceCoverageChangeGateway`. إنشاء المسودة وإرسالها المباشر يجريان في معاملة واحدة حتى لا يبقى حفظ جزئي عند فشل السياسة أو الرصيد أو مسار الاعتماد. لا تقبل دورة الإجازة `supporting_document_ref` من المتصفح؛ المرفق الطبي مورد خاص مستقل يديره `LeaveAttachmentService`. النموذج يحمل CSRF وintent ومفاتيح idempotency/نسخة متوقعة من الخادم، ويعرض الأخطاء عبر أكواد مجال عربية بدل SQL أو trace. يدعم `form-safety.js` السمة الاختيارية `data-draft-scope` حتى لا تعود مسودة عاملٍ سابق عند استخدام أكثر من حساب في المتصفح نفسه، مع بقاء مفاتيح النماذج القديمة متوافقة.
- **ارتق في بوابة العامل:** يعرض المدخل المشترك فقط `ErtaqInboxQuery::forRequester` ويشتق مقدم الطلب من الجلسة. يسمح `StaffErtaqSelfServicePolicy` بإنشاء تذكرة العامل والرد عليها فقط، ويفرض سرية `restricted` ورؤية الرسالة `requester`، ويمنع اختيار طالب آخر أو ملاحظة داخلية أو تصعيد عاجل من حقول المتصفح.
- **قرار المدير من صندوقه:** لا يعرض `staff_hr_portal.php` إلا خطوات `AssignedApprovalInboxQuery::forAssignee`، ويبني إجراءات القرار من `step_id` ونسخة القفل التي أعادها الخادم. يستدعي POST خدمة `ApprovalWorkflowService::decide` بهوية الجلسة ووقت الخادم بعد CSRF وقدرة صندوق المدير؛ وتعيد الخدمة فحص أهلية المكلّف والتفويض لحظة القرار قبل نشر أي أثر للإذن أو الإجازة.
- **مهايئ الأذونات القديم:** يبقى `admin/permissions.php` مدخل التوافق لجدول `staff_permissions` وحقوله ومعرّفات نموذجه وأفعاله القديمة. ينسق HTTP والجلسة وCSRF وPRG فقط، بينما يملك `LegacyPermissionCompatibilityService` التحقق والحفظ والتعديل والحذف داخل معاملة واحدة عبر عقدي `LegacyPermissionRepository` و`LegacyPermissionAuditWriter`. يركب `StaffModuleFactory` مهايئ PDO وكاتب `AuditService` الداعم للتراجع، ولذلك يفشل حفظ التدقيق العملية ولا تسرب الصفحة SQL أو تفاصيل الاستثناء للمستخدم. هذا المهايئ ليس مسارًا موازيًا لطلبات الخدمة الذاتية الجديدة؛ يظل انتقاله إلى `staff_permission_requests` ومراحل الاعتماد قرار طرح صريح بعد اكتمال سير العمل.
- **سلامة الحصة والتدقيق:** حساب الحصة ذاكرات عدّاد قابلة لإعادة البناء من حركات append-only وليست مصدر الحقيقة. تربط قاعدة البيانات كل حركة بالطلب والشريحة والعامل ونوع الإذن والشهر المطابق، وتمنع الحركة للمسودة أو المسودة المسحوبة أو الحساب المغلق، وتلزم كل حركة عادية بعدد ودقائق شريحة الطلب الشهرية نفسها. لا تسمح سياسة ذات حد شهري بتعطيل الحجز عند الإرسال، ولا تسمح بمسح/تحرير حركة أو إعادة فتح حساب مغلق. يملك `PermissionQuotaLedger` القفل المتسلسل لحساب الشهر ومفتاح إعادة المحاولة وتحديث العدادات والحركة والتدقيق الذري؛ يعيد محاولة التعارض العابر فقط عندما يملك المعاملة، ولا يسمح باستثناء السقف إلا لدقائق مخولة وموثقة وضمن الحد. يسجل الطلب الاستثناء الفعلي مرة واحدة فقط بعد الحجز الناجح، لا كوسم مرسل من العميل. يحجب تدقيق الطلب السبب والوسم الحر ومرجع المرفق ولقطة السياسة وسبب الاستثناء، ولا توجد عملية direct undo لطلب أو دفتر إذن؛ التراجع يتم بخدمة الحالة وحركة عكسية موثقة.
- **التشغيل والرجوع:** التفعيل يمر بـ`off → shadow → compare → display → official`، والرجوع يعيد القارئ إلى adapter القديم دون حذف البيانات الجديدة. لا إسقاط للحقول أو الجداول القديمة ضمن هذه الميزة.
- **التدقيق والتراجع:** تسجل موارد Staff-HR الجديدة في `AuditPolicyRegistry` بسياسة مغلقة افتراضيًا ومن دون direct undo على مستوى الجدول، لأن صلاحية التراجع تعتمد على حالة الصف وتاريخ نفاذه. المسودات المستقبلية لا تصبح قابلة للتراجع إلا بسياسة أدق واختبار مستقل. محتوى «ارتق» والتحقيق والبيانات الطبية والمرفقات الخاصة يُحجب بحسب نوع الكيان من تفاصيل التدقيق ولقطات التراجع، ويشارك سجل التدقيق معاملة كتابة العمل ويفشلها إذا تعذر حفظه.
- **القبول:** كل اختبار كتابة يستخدم قاعدة تنتهي بـ`_test` وحارس `STAFF_HR_TEST_MARKER`. حزمة القبول موسومة وقابلة للاستعادة ضمن manifest فقط، وتبقى للمستخدم بعد تجربة المتصفح؛ لا seed أو reset على قاعدة فعلية.

## ADR-055 — فصل نية تعيين المعلم عن تفعيله التشغيلي

- **الحالة:** معتمد في 2026-08-02.
- **السياق:** قد تُنشأ تعيينات المعلمين قبل ربط المادة بالصفوف والفصول في بداية العام، وكان رفض الحفظ يجبر الإدارة على إعادة إدخالها لاحقًا ويزيد خطر النسيان.
- **القرار:** تحفظ `teacher_subject_assignments.requested_active` رغبة الإدارة، بينما يبقى `is_active` الحالة التشغيلية. إذا لم يوجد ربط مادة نشط ومتوافق في `subject_grade_assignments` تحفظ المهمة بحالة معلقة مع `pending_reason=missing_subject_link` ولا تمنح صلاحيات الرصد أو المراجعة. يفعّل `AssessmentTeacherAssignmentActivationService` المهمة تلقائيًا عند إنشاء/تعديل/تفعيل ربط المادة، ويعيد تعليقها عند زوال الرابط. التعطيل اليدوي يبقى تعطيلًا مقصودًا ولا يعاد تفعيله تلقائيًا.
- **النطاق والتدقيق:** اختيار الصف بالكامل يخزن كـ`grade_id` مع `class_id=NULL` ولا يُفكك إلى الفصول القائمة، لذلك تشمل الفصول التي تنشأ لاحقًا عند وجود رابط صف كامل. تجري كتابة روابط المادة وحالات تعيين المعلمين وسجلات التدقيق في معاملة واحدة وبمعرّف دفعة مشترك، وأي فشل في التدقيق يعيد المعاملة.
## ADR-075 — حزمة قبول Staff-HR تجريبية محروسة واستعادة baseline إلى هدف معزول

- **الحالة:** معتمد ومنفذ ومثبت باختبار تكامل في 2026-08-11؛ كل تشغيل مقيد بقاعدة ينتهي اسمها بـ `_test` ولا يُسمح بالكتابة إلى `educore`.
- بيانات القبول حتمية ومملوكة للنطاق Q01–Q33، وتستخدم نطاق `example.test` ومعرفات موظف تبدأ بـ `E2099` منفصلة عن أرقام البصمة، ولا تتضمن كلمات مرور أو هواتف أو أرقاما قومية أو مسارات حقيقية.
- أداة البذر تفشل مغلقة ما لم تكن البيئة `test/testing` والعلامة `integrated-staff-hr` واسم قاعدة الطلب والاتصال كلاهما `_test`. لا تنفذ DDL وقت التشغيل، وتستقبل كلمة مرور القبول من متغير بيئة ثم تخزن التجزئة فقط.
- كل صف يتم إنشاؤه يسجل في manifest دفعة ترحيل مع عدد وتحقق checksum؛ إعادة البذر تتحقق من الملكية ولا تنشئ نسخا مكررة.
- يلتقط البذر حزمة baseline موثقة قبل أول صف تجريبي، ثم يسجل الحزمة وجميع الموارد التمثيلية في manifest الدفعة. تشمل الموارد أحداث بصمة matched/unmatched، طلبات وأرصدة الأذونات والإجازات، يوم حضور رسمي، قرارًا وتأديبًا وتظلمًا متسقين، وتذاكر «ارتق» العادية والمقيدة والعاجلة.
- لا تحذف الاستعادة صفوف قاعدة المصدر. يضيف `RecoveryBackupService::restorePackageToIsolatedDatabase()` عقدًا عامًا صغيرًا يعيد الحزمة المتحققة إلى **قاعدة جديدة وفارغة** تنتهي بـ `_test` ويحتفظ بها. يقبل replay على الهدف نفسه فقط عندما تكون الحزمة `verified` ويطابق fingerprint الكامل؛ الهدف الموجود أو المتغير يفشل مغلقًا.
- تبقى قاعدة المصدر كما هي، ولا تُحذف Trigger أو تُعطل حراسة السجل ولا يُحذف سجل بالتخمين. بعد نجاح المقارنة يحوّل مشغل القبول الإعداد إلى قاعدة baseline الجديدة؛ هذه خطوة تشغيلية صريحة وليست side effect لأداة الاستعادة.
- أثبت اختبار التكامل 27 فحصًا: الرفض قبل الاتصال لاسم `educore` أو العلامة الخاطئة، تكرار البذر بلا ازدواج، الملكية الدقيقة للموارد، رفض منفذ تابع للحزمة، الاستعادة إلى هدف جديد، replay ثابت، بقاء بيانات baseline غير المملوكة، وغياب بيانات العرض من الهدف. قواعد الإثبات المؤقتة وحزمها تحذف فقط إذا أنشأها الاختبار نفسه.

## ADR-076 — دور الموظف يملك خدمة ذاتية فقط وصندوق القرار يتبع الإسناد الفعلي

- **الحالة:** معتمد بعد القبول الحي في 2026-08-11.
- **السياق:** كان `StaffActiveRoleService` يرفض دور `employee` صراحةً، فيتعارض ذلك مع متطلب دخول العامل لطلب الإذن والإجازة و«ارتق». كما كان ظهور صندوق القرار مقصورًا على علاقة مدير مباشر/إداري، فلا يراه HR عندما تسنده مرحلة workflow مسماة له رغم أن استعلام الصندوق والقرار كلاهما يعيدان التحقق من الإسناد.
- **القرار:** يبقى `employee` دورًا حصريًا لا يجتمع مع دور آخر، لكنه يتجه إلى `staff_hr_portal.php` فقط ولا يحصل على أي صفحة إدارة. تتطلب البوابة حسابًا نشطًا وملف عامل وتعيينًا فعالًا، وتشتق self-scope من الجلسة. يُعرض صندوق الاعتماد لكل عامل مؤهل، لكن محتواه يأتي حصريًا من `assignedApprovalInbox()->forAssignee(actor)` والقرار يمر بخدمة الاعتماد التي تعيد فحص actor والقفل والأهلية؛ العامل غير المسند يرى صندوقًا فارغًا ولا يستطيع اتخاذ قرار.
- **التوافق والسلامة:** شاشة حسابات العاملين تسمح بإعداد بيانات دخول employee وتفعيله ولا تمسح بياناته عند تعيين الدور. يظل الدور حصريًا، وتبقى أدوار المعلم/الأخصائي/الإدارة ومساراتها دون تغيير. الرجوع البرمجي ممكن بإعادة رفض الدور وإخفاء بيانات الدخول، لكنه سيكسر الخدمة الذاتية المطلوبة ولا يمس تاريخ الطلبات.

## ADR-077 — عمليات حزمة القبول تبقى CLI وإعادة محاولة الاستعادة مشروطة بسلامة الحزمة

- **الحالة:** معتمد بعد إثبات Q30/Q31/Q33 الحي في 2026-08-11.
- **القرار:** لا تُنشأ صفحات ويب للبذر أو الترحيل أو استعادة baseline. يشغّل منفذ القبول المحلي المالكين المحروسين في `tools/` كعمليات CLI بأسماء قواعد `_test` والعلامة الصريحة، بينما تبقى إجراءات العامل والمدير والتقرير عبر HTTP والجلسات والأدوار وCSRF المعتادة. الأدلة تحفظ الإيصال والـchecksum والأعداد فقط ولا تحفظ كلمة المرور أو Cookies أو رموز CSRF.
- **إعادة المحاولة:** يمكن لـ`RecoveryBackupService` إعادة محاولة receipt حالته `failed` فقط عندما يكون `failure_code=restore_verification_failed` وتوجد بصمتا الحزمة والبيان. لا يقبل فشل إنشاء الحزمة أو حزمة ناقصة. كل إعادة محاولة تعيد فحص SHA-256 والبيان والملفات، وتستخدم قاعدة جديدة منتهية بـ`_test`، ثم تقارن fingerprint الكامل قبل منح `verified`.
- **الفصل والرجوع:** فاعل الاستعادة يجب أن يكون خارج manifest الحزمة، ولا يجوز لحساب تجريبي تابع لها استعادتها. يمكن الرجوع بمنع حالة failed مرة أخرى، لكن ذلك يعيد العطل التشغيلي ولا يغير أي بيانات عمل أو حزمة محفوظة.

## ADR-078 — إعادة احتساب يوم الحضور تنشر خلفًا مكتمل الأدلة فقط

- **الحالة:** معتمد ومثبت حيًا في Q32 على قاعدة قبول معزولة في 2026-08-11؛ لم تُستخدم قاعدة `educore` للاختبار.
- **القرار:** ينشئ `AttendanceRecalculationService` يوم الخلف أولًا بصفته غير رسمي، ثم يضيف المقاطع والأسباب، ويكمل جولة إعادة احتساب مرتبطة صراحة بجولة اليوم السابق، وبعد نجاح ذلك ينشر اليوم رسميًا ويسجل التدقيق داخل المعاملة نفسها. لا يجوز نشر اليوم قبل أدلته التابعة، ولا إنشاء جولة مكتملة بلا `supersedes_run_id` عندما يوجد يوم سابق، ويجب أن تتطابق نسخة محرك اليوم مع نسخة الجولة المكتملة.
- **عقد المستودع:** يضيف `AttendanceRecalculationRepository::publishRecalculatedDay()` خطوة نشر صريحة بعد حفظ الأدلة بدل تحميل `insertRecalculatedDay()` مسؤوليتين متعارضتين مع حواجز قاعدة البيانات. يبقى calculator version جزءًا من بصمة المرشح، بينما تستخدم حقيقة اليوم نسخة محرك خدمة إعادة الاحتساب التي تقارنها المشغلات بالجولة.
- **بيانات القبول:** يجب أن تنشئ الحزمة الحتمية نسخة جدول منشورة، أيامًا، ونطاقًا قابلاً للحل قبل أي رحلة إعادة احتساب؛ وجود اسم policy وحده ليس جدولًا تشغيليًا صالحًا. الرجوع يكون بإيقاف سطح إعادة الاحتساب أو إعادة adapter القديم مع تعطيل الرحلة، ولا يتضمن تعديل الأيام الرسمية المنشورة أو حذف أدلة التدقيق.

## ADR-079 — إنشاء النتيجة الرسمية الأولى منفصل عن إعادة الاحتساب وقراءات واجهة البصمة بعقود صغيرة

- **الحالة:** معتمد ومثبت حيًا في Q03 وQ04–Q07 على قاعدة قبول معزولة في 2026-08-11؛ لم تُستخدم قاعدة `educore` للاختبار.
- **القرار:** يظل `recalculate()` مقصورًا على يوم رسمي موجود، ويضيف `AttendanceRecalculationService::calculateInitial()` نية صريحة لإنشاء النسخة الرسمية الأولى فقط. ترفض النية الأولى وجود يوم رسمي، وترفض إعادة الاحتساب غيابه. كلاهما يحسب من السياسة والبصمات والتغطيات المؤرخة، يحفظ اليوم والأسباب والمقاطع، يكمل الجولة، ينشر النتيجة، ويسجل التدقيق داخل معاملة واحدة. الجولة التي لا تغير بصمة اليوم لا تستهلك رابط `supersedes_run_id` الفريد لأنها لا تنشئ خلفًا رسميًا؛ الجولة التي تغير اليوم فقط ترتبط بجولة السلف.
- **واجهة البصمة:** تحصل `admin/staff_biometric_import.php` على وسائل الحضور النشطة من عقد القراءة `AttendanceEntryMethodQuery` الذي تنفذه بنية Attendance، بدل إجبار المستخدم أو منفذ القبول على معرفة رقم داخلي. يبقى الحفظ مملوكًا لـ`AttendanceEventIngestor`، وتظل الهوية الخام محجوبة من أدلة القبول.
- **نقل القبول:** يحل مشغّل HTTP التحويل النسبي مقابل عنوان الطلب الحالي مع فرض same-origin، ويدعم multipart بحدود آمنة لرفع ملفات CSV التجريبية الحقيقية. لا ينشئ هذا القرار endpoint للاختبار ولا يتجاوز الجلسة أو CSRF أو فحص الرفع.
- **النتيجة والرجوع:** أثبتت الرحلات الوردية الليلية والعطلة، duplicate/unmatched الخام، وإذن التأخير والانصراف والمأمورية مع إعادة تشغيلها دون مضاعفة. الرجوع يعطل زر «إنشاء النتيجة الأولى» وعقد قائمة وسائل الحضور ويعيد حجب هذه الرحلات؛ لا يحذف أيامًا رسمية أو أحداثًا خامًا أو سجلات تدقيق منشورة.

## ADR-080 — بوابة الإجازات تقرأ الحسابات المفتوحة وتربط المرفق الطبي مرة واحدة عبر مالك خاص

- **الحالة:** معتمد ومثبت حيًا في Q11 وQ12 على قاعدة قبول معزولة في 2026-08-11؛ لم تُستخدم قاعدة `educore` للاختبار.
- **القرار:** يعرض عقد `StaffSelfServicePortalReadRepository` أرصدة الإجازات ذات الحالة `open` فقط، ويحمل مع كل طلب متطلبات المرفق من نوع الإجازة على الخادم. المسودة التي تتطلب تقريرًا تعرض حالة «مطلوب» وإجراء رفع خاص؛ ولا يقبل المتصفح مرجع تخزين أو مسار ملف. يركب `StaffModuleFactory::leaveAttachments()` المستودع والتخزين الخاص والتفويض والتدقيق، وتعالج نقطة الدخول نية `upload_medical_attachment` بعد الجلسة وCSRF واشتقاق العامل من الجلسة.
- **سلامة الملف والمعاملة:** يفحص `FileUploadGuard` الاسم وMIME الحقيقي والحجم، ويولد اسمًا عشوائيًا تحت `storage/private/leave_attachments`. تحفظ قاعدة البيانات مرجع `private:` فقط؛ وعند فشل البيانات الوصفية أو التدقيق يحذف الملف الجديد، ولا يحذف الملف السابق قبل نجاح استبداله.
- **الزمن ومسار الاعتماد:** نافذة الإشعار تحسب الدقائق الكاملة المنقضية كي لا تحوّل ثواني ساعة الخادم طلبًا صالحًا إلى خطأ، بينما تبقى فترات العمل الدقيقة محمية بالحساب الصارم. يسمح حارس الطلب بربط `workflow_instance_id` مرة واحدة فقط من `NULL` إلى قيمة أثناء `pending_approval` ثم يعيده غير قابل للتغيير، فلا تفشل معاملة إنشاء المسار ولا يمكن استبدال الدليل لاحقًا.
- **الرجوع:** يمكن إخفاء سطح الرصيد/الرفع أو إعادة adapter القراءة السابق دون حذف حساب أو حركة أو مرفق. لا يتضمن الرجوع جعل التخزين عامًا أو تعديل دليل اعتماد منشور.
## ADR-081 — Discipline operational evidence uses a separate least-privilege query contract

- **Status:** Accepted and live-proven by Q13/Q29 on 2026-08-13.
- **Decision:** `DisciplineCaseOperationsReadRepository` is separate from the safe administrative case-index repository. It may expose only action-enabling identifiers, optimistic lock values, decision sequence values, and verified evidence reference identifiers for an already-authorized normal case. It must not widen the safe list projection with investigation narratives, witness material, protected attachments, or unrestricted case evidence.
- **Authorization and writes:** Presentation code obtains operational facts through `DisciplineCaseOperationsQuery`; every mutation still passes the dedicated discipline authorization and application service, CSRF, optimistic locking, shared audit transaction, and lifecycle invariants. Close/reopen and temporary-measure decisions append facts and never rewrite immutable prior decisions.
- **Rollback:** The operational controls can be hidden and the query adapter removed without changing stored case history or the existing safe case index.

## ADR-082 — Ertaq urgent routing is server-owned and conflict-aware

- **Status:** Accepted and live-proven by Q14/Q28 on 2026-08-13.
- **Decision:** A portal user may declare immediate risk, but may not select a protection team, recipient, or manager. The application forces highly restricted visibility and urgent priority, resolves the eligible protection route on the server, and excludes the requester, declared/accused parties, and conflicted current direct or administrative managers. Case-management visibility is `protection_team`, not a caller-supplied generic team scope.
- **Read boundary:** `ErtaqUrgentInboxReadRepository` exposes neutral routing and acknowledgement metadata only to an authorized protection persona. Conversation and case-management authorization remain separate contracts. Collective parties and links are written atomically; withdrawal is a request state that retains the original ticket and immutable conversation history.
- **Rollback:** The urgent inbox and immediate-risk portal control can be disabled without deleting tickets, routes, parties, messages, withdrawal requests, or audit evidence.

## ADR-083 — Schedule workflow references remain scalar across migration owners

- **Status:** Accepted after clean-install migration verification on 2026-08-13.
- **Decision:** `staff_schedule_change_requests.workflow_instance_id` is an indexed scalar reference validated by the Staff approval-workflow application contract. It does not carry a physical foreign key to `staff_approval_instances`, because the schedule migration sorts before the workflow-foundation migration on a clean installation. This preserves the documented migration order and avoids coupling one owned schema file to a table that does not yet exist.
- **Integrity:** Schedule commands must still validate workflow existence, resource binding, state, and authorization before persistence; the scalar boundary is not permission to accept arbitrary identifiers. Contract coverage verifies the index and the absence of the order-breaking FK.
- **Rollback:** Disabling schedule-change consumers leaves both schedule and workflow histories intact. No table drop or data rewrite is required.

## ADR-084 — Notifications keeps one compatible controller with guarded presentation fragments

- **Status:** Accepted after strict architecture and live-page verification on 2026-08-13.
- **Decision:** `admin/notifications.php` remains the sole compatible HTTP controller and owner of authentication, CSRF, request fields, SQL orchestration, redirects, and public behavior. Its large presentation is composed from guarded internal fragments under `includes/`; direct requests to those fragments fail closed unless the controller defines `EDUCORE_NOTIFICATIONS_PAGE`.
- **Compatibility:** Form actions, names, identifiers, modal contracts, DataTable identifiers, and shared header/footer ownership are unchanged. A focused extraction contract and a signed-in browser check verify the composition without exercising a write.
- **Rollback:** The fragments can be inlined back into the same controller without a route, schema, session, permission, or data migration.
