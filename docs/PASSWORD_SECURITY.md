# الحالة الفعلية لأمان كلمات المرور

> هذه الوثيقة تصف التنفيذ الحالي المثبت من المصدر، لا المعمارية المرغوبة. آخر تحقق: 2026-07-15.

## مسار تسجيل الدخول الحالي

- `User::usernameExists()` يقرأ الغلاف القديم و`password_hash` دون فكهما داخل lookup.
- `User::login()` و`User::verifyPassword()` يفوضان إلى `PasswordAuthenticator`. إذا وجد hash فهو المصدر الوحيد، ولا يسمح فشله بالرجوع إلى الغلاف القديم.
- الحساب بلا hash يقبل مؤقتًا عند `PASSWORD_LEGACY_LOGIN_ENABLED=true`؛ بعد تحقق legacy ناجح يُكتب hash فورًا.
- إنشاء بيانات اعتماد جديدة أو إعادة تعيينها يكتب hash فورًا إضافة إلى الغلاف القابل للفك المطلوب حاليًا لميزة reveal الإدارية.

إغلاق نافذة legacy يتم بعد قياس عدم بقاء حسابات نشطة بلا hash، ثم ضبط المتغير إلى `false`. لا يلزم حذف الغلاف القديم في الخطوة نفسها.

## عرض كلمة المرور إداريًا

- `admin/ajax/get_password.php` يتطلب جلسة admin وطلب POST ورمز CSRF، ويعيد استجابة `no-store`.
- يعرض النسخة القابلة للفك عندما تكون موجودة، وقد يحدّث تشفيرها/الـhash ويسجل عملية العرض في `audit_logs`؛ لذلك اختبار هذا endpoint قد يكتب بيانات ولا يُشغّل على قاعدة `educore` أثناء التدقيق.
- وجود نسخة قابلة للفك لتلبية الاسترجاع الإداري يزيد أثر اختراق قاعدة البيانات أو مفاتيح التشفير، ويجب أن يبقى قرارًا منتجيًا موثقًا لا افتراضًا معماريًا.

## الدين المتبقي

قرار إلغاء reveal الإداري وحذف النسخة القابلة للفك مؤجل إلى سياسة استعادة حسابات مستقلة. كما يجب مراقبة نسبة الحسابات النشطة التي ما زالت بلا hash قبل إغلاق نافذة legacy في الإنتاج.

## إدارة المفاتيح

- تبقى مفاتيح التشفير خارج Git وتُقرأ من `.env`/مخزن أسرار معتمد.
- لا تُطبع كلمات المرور أو المفاتيح أو تفاصيل فك التشفير في responses أو logs.
- أي تدوير مفاتيح أو تعديل بيانات اعتماد يحتاج جردًا، نسخة احتياطية قابلة للاستعادة، migration قابلة للتكرار، وتحققًا من كل تنسيق legacy مستخدم فعليًا.
