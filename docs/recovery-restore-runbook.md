# دليل تشغيل نسخة التعافي وتهيئة العام

## قبل التنفيذ

1. أعلن نافذة صيانة قصيرة وأوقف إدخال الحضور والدرجات والمدفوعات أثناء إنشاء النسخة والتنفيذ.
2. طبّق migrations المعتمدة بأداة النشر المعتادة، ولا تنفذ DDL من صفحة الويب.
3. أنشئ العام الهدف بتواريخ صحيحة واتركه غير نشط وفارغًا.
4. علّم الصفوف التجريبية وحسابات الطلاب التجريبية من صفحاتها قبل إعداد القرارات؛ لا تستخدم العلامة لإخفاء طالب حقيقي.
5. افتح `admin/academic_year_setup.php`، اختر المصدر والهدف، واحفظ قاعدة انتقال صريحة لكل صف رسمي: صف هدف أو تخرج.
6. حدّد الاستثناءات (راسب، معلق، منقول، منسحب، متخرج) ثم اضغط حفظ القرارات والمعاينة.
7. أصلح كل مجموعة موانع؛ لا يُقبل قرار معلق أو طالب حقيقي بلا مرحلة/صف أو بيانات مسبقة في الهدف.

## إثبات قابلية الاستعادة

1. من الصفحة، أنشئ حزمة التعافي **بعد** حفظ القواعد والقرارات النهائية، وإعادة التحقق من كلمة مرور المدير وعبارة التأكيد.
2. ينتج النظام SQL وملفات `uploads` و`storage/private` وبيان SHA-256 داخل `storage/backups/recovery/`.
3. ينشئ النظام قاعدة جديدة منتهية بـ`_test`، يستعيد SQL، ويتحقق من البنية والأعداد وبصمة محتوى كل جدول وبصمات الملفات.
4. لا تعتبر النسخة صالحة إذا فشل dump أو ZIP أو hash أو import أو cleanup؛ لا تتجاوز الحالة يدويًا.
5. احتفظ بمفتاح الحزمة ووقت التحقق وسجل النشاط، ولا تنقل الحزمة إلى مسار عام.

## التهيئة والتحقق

1. نفّذ التهيئة فقط بعد ظهور receipt بحالة `verified` وبصمة حالية مطابقة.
2. التنفيذ ينشئ التقويم والفصول وإسنادات المواد وبنية التقييم كمسودات داخل معاملة واحدة، وينشئ قيودًا للناجحين والراسبين فقط. كل قيد طالب جديد يبدأ بلا فصل ويرتبط بقيد المصدر وقرار الترحيل؛ لا يفعّل الهدف.
3. نفّذ «تحقق مستقل». يجب أن تتطابق أعداد التنفيذ والـmanifest والجداول، وألا توجد مراجع يتيمة أو معاملات تاريخية في الهدف.
4. عند الفشل لا تحاول تعديل target يدويًا. عالج السبب ثم استخدم الرجوع الموجّه إذا بقي الهدف غير نشط وبلا معاملات تشغيلية.

## الرجوع قبل التفعيل

1. أعد التحقق من كلمة مرور المدير واكتب عبارة الرجوع المطلوبة.
2. يحذف النظام فقط target IDs المسجلة في `academic_year_rollover_items` وبالترتيب العكسي للاعتماديات.
3. تحقق من بقاء المصدر كما هو ومن عودة جداول الهدف المدارة إلى الصفر.
4. لا يتاح الرجوع التلقائي بعد التفعيل أو بعد ظهور حضور/درجات/مدفوعات أو معاملات تشغيلية في الهدف.

## التفعيل وبعده

1. فعّل فقط تشغيلًا بحالة `verified` وبعد مراجعة التقرير.
2. التفعيل يجعل الهدف نشطًا ويقفل المصدر ضد كتابات الحضور والتقييم والدرجات والتقارير والمدفوعات المحمية.
3. احتفظ بحزمة التعافي المرتبطة بالتشغيل وفق `docs/backup-retention-policy.md`.
4. قبل أول يوم تشغيل، سكّن الناجحين والراسبين يدويًا/بأداة التسكين في فصول الهدف وراجع السعات. ثم راقب العام الحالي، أعداد القيود، صلاحيات المعلمين، نوافذ الرصد، الجدول، النقل، والرسوم—فهذه المجالات تبدأ فارغة عمدًا.

## استعادة كارثية يدوية

1. لا تستعد فوق قاعدة التشغيل مباشرة. أنشئ قاعدة جديدة معزولة أولًا.
2. تحقق من SHA-256 للحزمة و`manifest.json` و`database.sql` وكل ملف.
3. استعد SQL إلى القاعدة المعزولة، وقارن تقرير الجداول والبصمات قبل أي cutover.
4. خطط cutover منفصلًا مع نسخة حالية أخرى، نافذة توقف، تغيير إعداد اتصال قابل للرجوع، واختبار دخول وقراءة سجلات الطلاب.
5. لا تحذف قاعدة أو ملفات التشغيل القديمة حتى اعتماد القراءة والكتابة على البديل ووجود مسار رجوع موثق.
