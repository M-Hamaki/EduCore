# دليل تشغيل ونشر منظومة Staff-HR

## 1. الهدف والمالك

يتم الانتقال تدريجيًا داخل الـmodular monolith الحالي. تملك وحدة Staff الهيكل والطلبات والموافقات والإجازات والتأديب وارتق، وتملك Attendance الدوام والبصمات والاحتساب والتقارير. Finance وNotifications وOperationsAudit مستهلكون عبر العقود الموثقة فقط.

متغير التشغيل الوحيد هو `STAFF_HR_MODE`. القيمة الافتراضية والآمنة هي `off`، وأي قيمة غير معروفة يجب أن تفشل مغلقة.

## 2. أوضاع التشغيل

| الوضع | الحساب الجديد | عرضه | اعتباره رسميًا | الرجوع للقديم |
|---|---:|---:|---:|---:|
| `off` | لا | لا | لا | نعم |
| `shadow` | نعم | لا | لا | نعم |
| `compare` | نعم | للمخول في شاشة الفرق فقط | لا | نعم |
| `display` | نعم | لنطاق تجريبي محدد | لا | نعم |
| `official` | نعم | نعم | نعم | لا داخل القراءة العادية |

لا يجوز القفز من `off` إلى `official`. يتم تغيير القيمة في إعداد البيئة وإعادة تحميل الخدمة وفق إجراء النشر المعتاد، ولا تضاف أزرار أو وسائط HTTP لتغييرها.

## 3. بوابة ما قبل التشغيل

1. نسخة SQL كاملة ونسخة ملفات خاصة مع checksums واختبار استعادة.
2. قاعدة clone معزولة ينتهي اسمها بـ `_test` لتجربة migrations والرجوع.
3. نجاح characterization للمسارات والحقول والجلسات والجداول القديمة.
4. نجاح اختبارات Staff-HR المركزة، وتدقيق الكتابات والرفع والمعمارية والجودة.
5. عدم وجود تعارضات سياسة أو هوية بصمة أو مديرين غير محسومة؛ الصفوف غير الصالحة تدخل quarantine.
6. اعتماد مالك العمل لقيم الإجازات والتأديب والاحتفاظ والصلاحيات قبل `official`.
7. تعيين مسؤول تنفيذ، مسؤول مراجعة مختلف، نافذة تغيير، موعد رجوع، وقناة حادث.

## 4. `off` إلى `shadow`

- طبق migrations الإضافية فقط؛ لا حذف أو إعادة تسمية لمصادر legacy.
- نفذ backfill بدفعة لها idempotency key وmanifest وcheckpoint وresume token.
- شغل الحساب الجديد دون تغيير التقرير الرسمي أو كتابة نتائج رسمية.
- راقب: عدد أحداث البصمة الخام، mapping غير المعروف، الأيام المحسوبة، exceptions، وزمن الدفعة.
- التوقف: أي كتابة إلى هدف غير مصرح، فشل تدقيق، فقد حدث خام، أو اختلاف أعداد غير مفسر.

## 5. `shadow` إلى `compare`

- قارن القديم والجديد لكل عامل/يوم، وليس بنسبة إجمالية فقط.
- صنف كل فرق: سياسة، عطلة، وردية ليلية، duplicate، بصمة ناقصة، هوية، إذن، إجازة، أو تصحيح مؤرخ.
- نفذ دورتين تمثيليتين على الأقل تشملان عطلات ونقلًا وظيفيًا وإقفال شهر.
- يلزم تطابق 100% للسيناريوهات الحرجة Q01–Q30 أو تفسير واعتماد الفرق كتابة.
- لا تعرض محتوى طبي أو تأديبي أو شكوى ضمن شاشة المقارنة أو التصدير.

## 6. `compare` إلى `display`

- فعّل نطاقًا صغيرًا محددًا: قوة أو مجموعة تجريبية، مع تاريخ بداية وانتهاء ومسؤول دعم.
- تعرض الواجهة النتيجة الجديدة مع علامة واضحة، ويبقى fallback القديم متاحًا.
- اختبر العامل والمدير وHR وFinance وSuper Admin، وانتهاء الجلسة والصلاحية أثناء الاستخدام.
- راقب زمن صندوق المدير والتقارير، ورسائل 403/404/409، وطلبات إعادة الاحتساب.
- لا يوجد dual-write يدوي داخل صفحات الأدوار.

## 7. `display` إلى `official`

لا ينتقل النطاق إلا بعد:

- نجاح Q01–Q33 من الواجهة على حزمة القبول.
- تطابق totals والتفاصيل والمقام، وتفسير جميع الفروق.
- إقفال وإعادة فتح مدققين، وتجربة أثر متأخر وعكس مالي idempotent.
- تجربة رجوع موثقة واستعادة baseline ثم إعادة رحلة العامل ← الاعتماد ← التقرير.
- توقيع مسؤول التنفيذ والمراجع ومالك العمل على watermark وchecksum والوقت.

افتح نافذة cutover عبر المنسق بوضع `capture` أو `freeze` المعلن. لا تنتقل إلى `new_only` قبل اكتمال batches وعدم وجود quarantine مفتوح وتطابق counts/checksums.

## 8. المراقبة بعد التفعيل

- exceptions غير المحسومة وأحداث البصمة المتأخرة وغير المربوطة.
- queue الموافقات والتنبيهات والآثار المالية المتأخرة أو المعادة.
- زمن تقرير 500 عامل، واستخدام الذاكرة، وأي N+1.
- عدد أيام official بلا سبب/مصدر أو ذات نسخة متعارضة.
- محاولات IDOR وCSRF والوصول للمرفقات الخاصة والتصدير الحساس.
- فشل audit أو outbox يمنع الكتابة المرتبطة ولا يعامل كتحذير فقط.

## 9. الرجوع التشغيلي

1. أوقف توسيع النطاق وأعلن وقت بداية الحادث.
2. أعد `STAFF_HR_MODE` إلى آخر وضع آمن: غالبًا `display` ثم `compare` أو `off` حسب الضرر.
3. أعد القارئ إلى legacy adapter، وأوقف consumers المتسببة مع إبقاء outbox.
4. أغلق نافذة cutover أو نفذ rollback عبر manifest الدفعة للموارد القابلة للعكس فقط.
5. في حزمة قبول Staff-HR لا تحذف أحداث البصمة أو الطلبات أو الحركات أو الحضور الرسمي أو التأديب أو «ارتق». استخدم `staff_hr_acceptance_restore.php` لإعادة baseline الموثق إلى قاعدة جديدة `_test` ثم تحقق من بصمتها قبل تحويل إعداد القبول إليها.
6. لا تستخدم `TRUNCATE` أو حذفًا حسب prefix أو إسقاط migrations أثناء الحادث.
7. لا تعدل بصمات الخام ولا تحذف القرارات أو القيود المالية؛ أنشئ تصحيحًا/عكسًا رسميًا.
8. صالح watermark والأعداد والـchecksums وحدد فترة التأثر والعاملين المتأثرين.
9. سجل القرار والسبب والمنفذ والمراجع في التدقيق وتقرير الحادث.

## 10. حالات التوقف الإلزامي

- قاعدة الهدف أو marker أو ملكية manifest غير مثبتة.
- فشل backup restore أو انتهاء مهلة الرجوع.
- فرق غير مفسر في حساب رسمي أو أثر مالي.
- self-approval أو اتساع نطاق مدير أو تسرب مرفق/شكوى.
- كتابة legacy أثناء `freeze` أو كتابة غير ملتقطة أثناء `capture`.
- فشل بوابات الأمن أو العمارة أو تغطية الكتابات.
- رحلة متصفح حرجة `failed` أو `blocked` دون قرار مانع معتمد.

## 11. سجل تغيير الوضع

يسجل لكل انتقال: الوضع السابق والجديد، النطاق، وقت البدء والانتهاء، actor والمراجع، backup/checksum، migration batch، reconciliation watermark، نتائج Q01–Q33، قرار الاستمرار/الرجوع، والعيوب المعروفة. لا تسجل كلمات المرور أو Cookies أو tokens أو تفاصيل سرية.
